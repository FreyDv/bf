# ADR-002: Domain-Driven Hexagon - обязательная архитектура каждого backend

## Context

Владелец потребовал, чтобы каждый backend безусловно следовал правилам репозитория Sairyss/domain-driven-hexagon, и чтобы ИИ при планировании и реализации не мог от них отойти. Источник сам называет свои правила рекомендациями и предупреждает, что для простого CRUD архитектура избыточна.

## Options considered

- Оставить рекомендацией и ссылкой на пример - отклонено владельцем.
- Извлечь все рекомендации README в нумерованные, не привязанные к стеку правила, загружать их в каждую сессию и проверять машиной - выбрано.

## Decision

Все рекомендации README извлечены в правила `.claude/rules/architecture-rules.md` (группы PRG, STR, DEP, APP, DOM, VAL, ERR, ADP, INF, ENF, TST) и протокол сессии `.claude/rules/ai-protocol.md` (AIP-1..6): оба файла грузятся в каждую сессию; каждый план backend содержит раздел `Architecture conformance`; конфликт с правилом - остановка, а не решение на месте. Отклонение допустимо только записью ADR с идентификатором правила, модулем и причиной. Границы проверяет инструмент контроля зависимостей в CI (ENF-1), выбираемый стековым ADR; до его появления backend-код не пишется. Правило-классификатор PRG-1/PRG-2 не даёт применять всё слепо к модулям-CRUD.

## Consequences

- Плюс: правила проверяются машиной, а не памятью; план обязан показать соответствие.
- Минус: больше файлов и отображений; ему противостоят PRG-3/PRG-4 (никаких абстракций впрок).

## Confirmation

ENF-1 (проверка границ в CI), ревью по AIP-6 навыком `ddd-review`, раздел `Architecture conformance` в каждом плане.

## Revisit when

Модуль оказывается чистым CRUD без бизнес-правил (тогда исключение записывается отдельным ADR по PRG-2) либо появляется второй стек backend.
