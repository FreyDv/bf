# ADR-002: Domain-Driven Hexagon - обязательная архитектура каждого backend

## Context

- Владелец потребовал, чтобы каждый backend безусловно следовал правилам Sairyss/domain-driven-hexagon, и чтобы ИИ при планировании и реализации не мог от них отойти.
- Источник сам называет свои правила рекомендациями и предупреждает, что для простого CRUD архитектура избыточна.

## Options considered

| Вариант | Итог |
|---|---|
| Рекомендация и ссылка на пример | отклонён владельцем |
| Все рекомендации README - нумерованные правила без привязки к стеку, грузятся в каждую сессию, проверяются машиной | выбран |

## Decision

1. Правила: `.claude/rules/architecture-rules.md` (группы PRG, STR, DEP, APP, DOM, VAL, ERR, ADP, INF, ENF, TST).
2. Протокол сессии: `.claude/rules/ai-protocol.md` (AIP-1..6). Оба файла грузятся в каждую сессию.
3. Каждый план backend содержит раздел `Architecture conformance`.
4. Конфликт с правилом - остановка, а не решение на месте.
5. Отклонение - только ADR с идентификатором правила, модулем и причиной.
6. Границы проверяет инструмент в CI (ENF-1, выбран в ADR-014); до него backend-код не пишется.
7. Классификатор PRG-1/PRG-2 не даёт применять всё слепо к модулям-CRUD.

## Consequences

- Плюс: правила проверяет машина, а не память; план обязан показать соответствие.
- Минус: больше файлов и отображений; ограничивается PRG-3/PRG-4 (никаких абстракций впрок).

## Confirmation

ENF-1 (проверка границ в CI), ревью по AIP-6 навыком `ddd-review`, раздел `Architecture conformance` в каждом плане.

## Revisit when

- Модуль оказывается чистым CRUD без бизнес-правил: исключение записывается отдельным ADR по PRG-2.
- Появляется второй стек backend.
