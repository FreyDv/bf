# ADR-025: Domain-Driven Hexagon - обязательная архитектура каждого backend-сервиса

## Context

Владелец потребовал, чтобы каждый backend-сервис безусловно следовал правилам из репозитория Sairyss/domain-driven-hexagon. Скелеты сервисов ещё не содержат бизнес-логики, поэтому раскладку можно ввести до появления кода (кроме модуля `identity` в `auth`, ARCH-1). Эталон сам говорит, что его правила - рекомендации, а для простого CRUD архитектура избыточна (DDH-1, DDH-107).

## Options considered

- Не вводить архитектуру - отклонено владельцем.
- Ввести как рекомендацию - отклонено: «безусловно».
- Ввести как обязательную с проверкой в CI - выбрано.

## Decision

Каждый модуль backend-сервиса строится по Domain-Driven Hexagon: вертикальные срезы по use case, `domain` свободен от фреймворка, порты и адаптеры, CQS через `@nestjs/cqrs`, `Result` для бизнес-ошибок, модель персистентности отдельно от доменной. Правила - `docs/standards/domain-driven-hexagon/rules.md` (DDH-1..128), форма для этого стека - `bf-mapping.md`, жёсткие правила - `.claude/rules/backend-architecture.md`; границы проверяет `pnpm deps` (один набор правил на все Nest-приложения). Единственное зафиксированное исключение - плоский модуль `auth/identity`, миграция в раскладку - ARCH-1.

## Consequences

- Плюс: правила проверяются машиной, а не памятью.
- Минус: больше файлов; соблазн строить абстракции впрок - ему противостоит правило DDH-22/DDH-106.

## Confirmation

`pnpm deps`, ревью по чек-листу `bf-mapping.md` §10, навык `bf-architecture-review`.

## Revisit when

Модуль оказывается чистым CRUD без бизнес-правил (тогда исключение для этого модуля записывается отдельным ADR) либо появляется второй стек backend.
