# ADR-028: Сборка образов в CI: BuildKit, кэш GHA, amd64, матрица по затронутым

## Context

- ADR-018: образ при merge в `main`, тег по SHA.
- ADR-026: реестр GHCR; ADR-027: устройство образа.
- Нужно решить: чем собирать, как кэшировать, что собирать на PR.

## Options considered

| Вопрос | Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|---|
| Кэш | `type=gha` | бесплатно, без настройки | лимит около 10 ГБ на репозиторий, общий для приложений | выбран |
| Кэш | `type=registry` в GHCR | не вытесняется | лишние пакеты, их чистить | отклонён |
| Кэш | без кэша | проще | минуты на каждую сборку | отклонён |

## Decision

1. Сборка: `docker/build-push-action` на BuildKit, кэш `type=gha`.
2. Платформа только `linux/amd64` (узлы DO); multi-arch и QEMU нет.
3. Матрица по приложениям, только затронутым (определяет Turborepo, ADR-009).
4. Публикация только на `main`. На PR - сборка без публикации, только если менялись Dockerfile или зависимости приложения.
5. Тег: SHA коммита (ADR-018); `latest` не публикуется. Метки OCI (`source`, `revision`, `created`) через `docker/metadata-action`.
6. SBOM и provenance включены флагами buildx.
7. Actions закреплены по digest (backlog CI-2); права job минимальные, `packages: write` только в job публикации.
8. Пункт 4 дополняет ADR-018 (там образ собирается при merge): сборка на PR без публикации ловит поломку Dockerfile до слияния.

## Consequences

- Плюс: повторные сборки быстрые; плохой Dockerfile не доходит до `main`.
- Минус: кэш вытесняется при превышении лимита - сборка замедляется, не ломается.
- Минус: CI на PR удлиняется, когда менялись зависимости.
- Дальше: workflow сборки (CI-2).

## Confirmation

Workflow в репозитории; обязательные проверки `main` (GUARD-2) включают сборку на PR; ревью: новое приложение входит в матрицу.

## Revisit when

- Кэш регулярно вытесняется и сборки замедляются (тогда `type=registry`).
- Узлам кластера нужен arm64.
- Время CI на PR неприемлемо владельцу.
