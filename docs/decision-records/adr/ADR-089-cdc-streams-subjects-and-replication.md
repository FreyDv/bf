# ADR-089: CDC: один слот, стримы `BF` и `CDC`, subject, outbox `deo`, heartbeat

## Context

- ADR-021, ADR-023: Debezium читает слот и публикацию; список таблиц явный, в SQL-файле с функциями.
- ADR-025 п. 8 и п. 10: outbox `domain_event_outbox`, subject `BF.<AGGREGATE>.<LIFECYCLE>.<EVENT>`.
- ADR-033 п. 5: один стрим `BF` с subject `bf.>`.
- Владелец разделил события на бизнесовые (доменные события из outbox) и сервисные (изменения таблиц).
- Факты: один Debezium Server читает один слот, но пишет в любые subject; два стрима NATS не могут делить subject; `FOR TABLES IN SCHEMA` требует суперпользователя, которого на DO нет; `CREATE TEMP TABLE` в логическую репликацию не попадает.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Стримы | `BF` и `CDC` | один `BF` на всё (ADR-033 п. 5): бизнесовое и служебное в одной куче |
| Слоты | один слот, один Debezium | два слота: нужны два процесса Debezium |
| Состав публикации | собирается сам из схемы | явный список (ADR-023 п. 4): забытая таблица молча не публикуется |
| Проверка в кластере | постоянный heartbeat | временная таблица от Job после выката: DDL на рабочей базе, разовая проверка |
| Смещения Debezium | схема `debezium`, таблицу создаёт миграция | в `app`: пришлось бы исключать из публикации |

## Decision

1. **Один Debezium Server, один слот `bf_slot`, публикация с тем же именем** (ADR-023 п. 3 в силе). Слот, публикацию и роль создают миграции (ADR-088). **Заменяет** раздел «Postgres (SQL-файл)» ADR-023, п. 1-5.
2. **Публикация** = все таблицы схемы `app` плюс `public.cdc_heartbeat`. Схема `debezium` не входит. Список пересобирает повторяемый шаг после каждого прогона миграций (ADR-088 п. 7); форма - `FOR TABLE`. **Заменяет** ADR-021 п. 4 и ADR-023 п. 4 («каждая таблица добавляется явно»).
3. **`REPLICA IDENTITY FULL`** - на всех таблицах `app`, кроме `deo`; у `deo` остаётся по первичному ключу. Выставляет повторяемый шаг, и только там, где значение другое.
4. **Outbox - одна таблица `app.deo`** с колонками ADR-025 п. 8. Она только дописывается: у роли `app` на `deo` только INSERT (и USAGE на sequence `seq`), без SELECT, UPDATE, DELETE, TRUNCATE. **Заменяет** имя `domain_event_outbox` в ADR-025 п. 8. Уборка старых строк - новое решение.
5. **Стримы.** `BF`: subject - список агрегатов (`ORDER.>`, `COURSE.>`, ...), агрегат добавляется в список вместе с его первым событием. `CDC`: `bf.>`. Оба описаны в git (NATS-5); лимиты хранения решает NATS-5 с владельцем. **Заменяет** в ADR-033 п. 5 «стрим `BF` (subject `bf.>`)» - в кластере и локально.
6. **Subject.**
   - `BF`: `<AGGREGATE>.<LIFECYCLE>.<EVENT>`, три токена, верхний регистр, `LIFECYCLE` - `CREATED`, `UPDATED`, `DELETED` (ADR-025 п. 5), например `ORDER.CREATED.PLACED`. Тело - новое состояние. Заголовок `Nats-Msg-Id` = `event_id`, NATS отбрасывает дубли. **Заменяет** ADR-025 п. 10.
   - `CDC`: `bf.<схема>.<таблица>`, операция в теле. Отметок транзакций и `pg_logical_emit_message` нет.
7. **Маршрут в Debezium.** Маршрутизатор outbox (`EventRouter`) применяется только к `bf.app.deo` (предикат `TopicNameMatches`): subject из колонки `subject`, `payload` раскрывается. Удаления строк `deo` он отбрасывает, изменения пишет в лог как предупреждение (debezium.io, Outbox Event Router). В `CDC` строки `deo` не идут. Остальные таблицы идут по имени.
8. **Heartbeat.**
   - `public.cdc_heartbeat` (`id`, `ts`), одна строка; создаёт миграция.
   - Debezium раз в минуту выполняет `UPDATE public.cdc_heartbeat SET ts = now() WHERE id = 1` (`heartbeat.action.query`). Изменение приходит в `CDC` на `bf.public.cdc_heartbeat`, а слот продвигается и тогда, когда приложение ничего не пишет.
   - Служебное сообщение Debezium идёт на `bf.debezium.cdc_heartbeat` (`topic.heartbeat.name`).
9. **Права роли `debezium`** (по запросам Debezium 3.7.0):

   | Объект | Право |
   |---|---|
   | роль | LOGIN, REPLICATION; без CREATEROLE, CREATEDB, BYPASSRLS |
   | база `bf` | CONNECT |
   | схемы `app`, `public` | USAGE |
   | таблицы `app` | нет: при `snapshot.mode=no_data` Debezium читает только каталоги |
   | `public.cdc_heartbeat` | `SELECT (id)`, `UPDATE (ts)` |
   | схема `debezium` | USAGE, без CREATE |
   | `debezium.debezium_offsets` | SELECT, INSERT, DELETE |

   Тест в CI запускает Debezium ровно с этими правами. Если без SELECT на `app` он не работает, SELECT добавляется правами по умолчанию, и владелец получает об этом сообщение.
10. **Смещения.** Схема `debezium` и таблица `debezium_offsets` по DDL самого Debezium создаёт миграция. Debezium подключается с `currentSchema=debezium`: найдя таблицу, он `CREATE` не выполняет. **Уточняет** ADR-023 «Развёртывание» п. 2.
11. **Алерты:** WAL слота - предупреждение на 5 ГБ, критичный на 15 ГБ; нет свежего `bf.public.cdc_heartbeat` дольше 5 минут; отставание потребителя стрима (порог - с владельцем, когда появится первый потребитель).
12. **Проверка.**
    - CI на `bf_test`: изменение тестовой таблицы доходит до `CDC`; вставка в `deo` доходит до `BF` с subject и `Nats-Msg-Id`.
    - Кластер: heartbeat приходит постоянно.
    - Это ответ на TEST-5: доставка проверяется в CI.

## Consequences

- Positive: потребитель бизнеса подписывается на `BF` и не видит служебного; новая таблица `app` попадает в `CDC` без правки списка.
- Positive: heartbeat - постоянная проверка цепочки и защита от роста WAL при пустой базе.
- Negative: каждый новый агрегат - правка subject стрима `BF`, иначе публикация его события падает.
- Negative: `FULL` пишет в WAL всю старую строку на каждое изменение и удаление.
- Negative: таблица `deo` растёт без предела, пока нет уборки; алерт диска 80% уже есть (ADR-086).

## Confirmation

- Тест доставки в CI (п. 12) и тест прав роли `debezium` (п. 9).
- `pnpm migrations:check`: публикация после прогона содержит ровно таблицы п. 2.
- Алерт heartbeat в Grafana.

## Revisit when

- Нужна уборка `deo` или её размер подходит к 10% диска базы.
- Debezium не успевает за записью, или одному слоту нужны два независимых потребителя.
- DO даёт суперпользователя (тогда `FOR TABLES IN SCHEMA`).
