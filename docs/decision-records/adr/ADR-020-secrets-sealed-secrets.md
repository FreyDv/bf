# ADR-020: Секреты: Sealed Secrets в кластере, GitHub Secrets только для CI

## Context

- ArgoCD берёт состояние из Git (ADR-019); приложениям нужны пароль БД, ключ OpenAI, токены.
- Секреты в репозитории открытым текстом запрещены (красный флаг 5).
- Доставка секрета должна быть воспроизводима из репозитория (R3) и не ломать GitOps.
- CI нужен токен реестра образов.

## Options considered

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Sealed Secrets | шифр в Git, расшифровка контроллером; один контроллер; бесплатно | закрытый ключ - критичная точка | выбран |
| SOPS + age | шифр в Git; бесплатно | сложнее настройка ArgoCD (плагин) | отклонён |
| External Secrets + хранилище (Vault/OpenBao, Infisical, Doppler, облачный менеджер) | гибче | ещё один сервис и расход | отклонён |
| Руками через `kubectl` | - | не воспроизводим | не рассматривался |
| `kubectl apply` из CI | - | учётные данные кластера в GitHub; ломает модель ArgoCD | не рассматривался |

## Decision

**В кластере.**
1. Зашифрованные значения - `deploy/apps/<app>/secrets.yaml`; чарт `app` создаёт из них SealedSecret (ADR-019).
2. Один секрет на приложение со многими ключами, как `.env`; подключается целиком через `envFromSecrets`.
3. Отдельный секрет - только если часть значений нужна не всем процессам приложения.

**Ключи.**
1. Пару ключей создаёт контроллер.
2. Открытый сертификат - `deploy/sealed-secrets/pub-cert.pem`; шифруем только с `--cert`, не по сети.
3. Закрытый ключ - копией в менеджере паролей владельца, не в репозитории и не в чате; копия обновляется после ротации.
4. Область секрета строгая (имя и namespace); cluster-wide не используется.

**Источник значений.**
1. Рядом с `src` приложения: `.env` (локально) и `.env.production` (боевые); оба в `.gitignore` и `.dockerignore`.
2. Локальный `.env` в прод не шифруется никогда.
3. Скрипт `secrets:seal` приложения вызывает общий `scripts/seal-secret.ts` (`node`): шифрует **весь** `.env.production` через `kubeseal --raw` с сертификатом из репозитория, без доступа к кластеру, и пишет `deploy/apps/<app>/secrets.yaml`.
4. `.env.production` читается встроенным разбором Node, без новой зависимости.
5. В репозиторий можно коммитить `.env.example` с именами ключей без значений.
6. Менеджер паролей владельца - резервная копия значений.

**GitHub Secrets** - только токен реестра образов; доступен только job'у при merge в `main`, не проверкам PR. Секретов приложения и боевых учётных данных БД в GitHub нет (ADR-018).

**Утечка закрытого ключа** - меняются сами значения (пароль БД, ключ OpenAI), а не только шифрование: старые файлы остаются в истории Git.

## Consequences

- Плюс: секреты воспроизводимы из репозитория; PR и CI не видят открытых значений; ничего платного.
- Минус: каждое шифрование меняет все строки `secrets.yaml` - diff по каждому ключу и перезапуск подов (шифрование только названных ключей владелец отклонил).
- Минус: боевые значения на диске в `.env.production`; его утечка - утечка секретов.
- Минус: потеря закрытого ключа - перевыпуск всех секретов из первоисточников.
- Минус: значение нельзя прочитать обратно из кластера или файла.
- Дальше: установка контроллера (backlog SEALED-1) со сверкой деталей, взятых по памяти (флаги `kubeseal`, период ротации, метка ключа), и происхождения существующей пары ключей; скрипт `seal-secret.ts` (SECRETS-1).

## Confirmation

gitleaks в CI (GUARD-2); ревью: каждое значение в `secrets.yaml` зашифровано, ключи совпадают с `values.yaml`; контроллер падает при несовпадении имени или namespace.

## Revisit when

- Секретов или людей с доступом больше, чем удобно хранить в Git (тогда External Secrets).
- Проект Sealed Secrets перестаёт поддерживаться.
- Утечка закрытого ключа.
