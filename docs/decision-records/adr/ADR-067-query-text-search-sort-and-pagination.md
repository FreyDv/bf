# ADR-067: Поиск по подстроке, сортировка и пагинация списочных query (дополняет ADR-024)

## Context

- ADR-024 описал только фильтр: 12 операторов, `defineFilter`, вход `{ filter }`. Сортировку, пагинацию и текстовый поиск он отложил на QUERY-2; ADR-050 п. 4 и ADR-051 «Revisit when» ссылаются туда же.
- Пакет `@bf/query-filter` (entry `core`, `zod`, `drizzle`) есть, потребителя нет: `specs/capability-map.json` пуст, в `apps/backend/src` нет модуля со списочным query.
- Без контракта первый list-модуль придумает свой вход, и второй модуль сделает иначе; правила QRY нужны раньше кода.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Объём | запись и правила QRY-21..26; код - с первым list-модулем | код сейчас: без потребителя, спекулятивно (PRG-3, PRG-4) |
| Форма записи | новая запись, ADR-024 в силе (как ADR-050, ADR-051) | заменить ADR-024: меняется только дополнение |
| Поиск | оператор `contains` в фильтре, набор `Op.Text` | ключ `search` по нескольким полям; полнотекстовый поиск: нет продуктового требования; `ilike` с шаблоном от клиента: клиент управляет `%`, `_` и стоимостью запроса |
| Набор операторов | новый `Op.Text = [contains]` | добавить в `Op.String`: QRY-4 запрещает менять общий набор, поиск включится на каждом строковом поле |
| Вход | необязательные `sort` и `page` рядом с `filter` | внутри `filter`; плоские `limit`, `offset`, `orderBy` |
| Пагинация | `offset`/`limit` с потолками | keyset-курсор: нет экрана с бесконечной прокруткой и больших таблиц |

## Decision

1. **Только контракт.** Код в `@bf/query-filter` пишется вместе с первым list-модулем, по этой записи и правилам QRY-21..26 (`.claude/rules/query-filter-rules.md`).
2. **`contains`** - тринадцатый оператор (QRY-2): подстрока без учёта регистра. Значение - литерал: сервер экранирует `\`, `%`, `_` и передаёт `'%' || значение || '%'` параметром в `ILIKE ... ESCAPE '\'`, без `sql.raw` (QRY-15). Только на `str`, длина значения 1..200. NULL не находится (QRY-14). Внутри фильтра по связи работает как любое условие (EXISTS, QRY-11).
3. **`Op.Text = [contains]`** - новый набор, поле включает поиск явно: `str(Op.String, Op.Text)`. `Op.String` не меняется.
4. **Вход query:** `{ filter?, sort?, page? }`, `.strict()`, все ключи необязательны; клиент, который шлёт только `{ filter }`, работает как раньше. `toZod(S)` описывает только `filter`; `sort` и `page` - соседние ключи DTO запроса.
5. **`sort`:** массив 1..3 элементов `{ field, direction: 'asc' | 'desc' }`. Поля - из отдельного списка сортируемых полей query (сортируемое не равно фильтруемому), только столбцы корневой таблицы. Сервер всегда добавляет последним ключом первичный ключ `asc`, чтобы порядок был стабильным; NULL всегда последними (`NULLS LAST`) при обоих направлениях. Без `sort` порядок - по первичному ключу.
6. **`page`:** `{ limit?, offset?, total? }`. `limit` по умолчанию 20, максимум 100; `offset` 0..10 000; query может только ужесточать (как QRY-16). `total: true` добавляет в ответ общее число строк (`COUNT` того же `WHERE`); без него `COUNT` не выполняется.
7. **Ответ списка:** `{ items, total? }` в `*.response.dto.ts` (ADP-3, ADP-4); `total` есть, только когда запрошен.
8. **Где код:** типы и описание сортировки - `core`, схемы `sort`/`page` - `zod`, `ORDER BY`/`LIMIT`/`OFFSET` строит read-адаптер модуля; `compile` по-прежнему отдаёт только условие `WHERE`. Хелпер в `drizzle` - когда он понадобится двум модулям.
9. **Отложено:** индекс `pg_trgm` (миграция первого модуля, где объём оправдывает; DDL применяет человек, AGENTS.md red flag 1); `bigint` (ADR-050 п. 4); `ё` = `е`, морфология, акценты, полнотекстовый поиск и ранжирование - до продуктового требования в спеке первого list-модуля; сортировка по полю связи - отдельной записью.

## Consequences

- Positive: у первого list-модуля готов вход, ответ и лимиты; модули не разойдутся; клиенты старого входа не ломаются.
- Negative: контракт не проверен кодом; первая реализация может найти ошибку в записи - тогда правится новой записью.
- Negative: `offset` дорожает на больших смещениях, отсюда потолок 10 000; `contains` без индекса - последовательный просмотр.
- Negative: под локалью `en_US.UTF-8` у `bfdb` `ILIKE` различает `ё` и `е`; пользователь, набравший «елка», не найдёт «ёлка».

## Confirmation

Review only сейчас. С первым list-модулем: тесты тулкита на `contains` (экранирование, длина, NULL) и на `sort`/`page` (allowlist, tie-breaker, потолки) на реальном Postgres (QRY-18), behavioural-тесты query (TST-1).

## Revisit when

- Первый list-модуль: реализация по этой записи; расхождение - новой записью.
- Экран с бесконечной прокруткой или таблица, где `offset` 10 000 мал: keyset-курсор.
- Спека требует поиск по нескольким полям сразу, `ё` = `е` или морфологию: ключ `search` или полнотекстовый поиск.
