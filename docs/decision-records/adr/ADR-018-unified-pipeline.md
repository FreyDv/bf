# ADR-018: Единый конвейер для всех приложений: pre-commit, CI на PR, CI при merge

## Context

- В монорепо несколько приложений (ADR-008, ADR-009); свои проверки у каждого - расхождение границ и стиля.
- Владелец хочет один подход: одни и те же шаги локально, в PR и при merge.
- Владелец хотел проверять миграции в PR на боевой БД (применить в транзакции, откатить). Против:
  - красный флаг 1: запись в удалённую БД только человеком или механизмом деплоя;
  - блокировки на боевых таблицах даже при откате;
  - боевые учётные данные в каждом прогоне PR;
  - не работает с `CREATE INDEX CONCURRENTLY`.

## Options considered

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Миграции на пустом Postgres в service container | без секретов и риска для прода | не видит проблем реальных данных | выбран |
| Клон прода из бэкапа | ловит проблемы данных | платный временный кластер, токен DO в CI | отклонён |
| Миграции на боевой БД в PR | - | см. Context | отклонён |
| Менеджер git-хуков: lefthook | - | новая зависимость | выбран владельцем |

## Decision

**Контракт приложения.**
1. Одинаковые имена скриптов: `typecheck`, `lint`, `test` (unit), `test:e2e`, `build`; недостающие Turborepo пропускает.
2. Prettier и dependency-cruiser (ADR-014) - корневые задачи.
3. Своего конвейера у приложения нет; от него нужны только Dockerfile и Helm-значения (ADR-019).

**Pre-commit (lefthook).** Затронутые пакеты и staged-файлы, по порядку, стоп на первой ошибке:
`tsc` -> `prettier --write` -> `eslint --fix` -> границы.
1. Исправленные файлы возвращаются в индекс.
2. Хук обходим (`--no-verify`), поэтому гарантия - CI; агентам обход запрещён.

**CI на PR** (только затронутое, ADR-009):
`tsc` -> `prettier --check` -> `eslint` -> границы -> unit -> e2e -> миграции.
1. e2e - против реальной тестовой БД и NATS в service containers (TST-2, TST-3).
2. Миграции - только если в PR менялись их файлы: чистый Postgres 18, миграции `main`, затем миграции PR; красный при любой ошибке.
3. В PR нет файлов `down` (ADR-013).
4. Боевых учётных данных БД в CI нет вообще.

**CI при merge в `main`.**
1. Тот же набор шагов без миграций.
2. `build` и образ каждого приложения в реестр с тегом по SHA коммита, не `latest` (R21).

## Consequences

- Плюс: одни правила для всех приложений.
- Плюс: PR не получает ни доступа к проду, ни блокировок на нём.
- Минус: пустая БД не ловит проблемы реальных данных (долгие блокировки, уникальность).
- Минус: `--fix` в хуке меняет файлы автоматически.
- Минус: `CREATE INDEX CONCURRENTLY` не вписывается в транзакционный запуск - нужно отдельное правило.
- Дальше: workflow CI и lefthook (backlog CI-2, HOOKS-1); реестр образов (CI-1); обязательные проверки `main` (GUARD-2).

## Confirmation

Конфиг lefthook и workflow CI в репозитории; обязательные проверки `main` включают эти шаги (GUARD-2); ревью: новое приложение использует те же имена скриптов.

## Revisit when

- Миграция, прошедшая проверку, ломает прод (тогда клон прода из бэкапа).
- Время CI на PR превышает приемлемое владельцу.
- Появляется второй разработчик и хук мешает.
