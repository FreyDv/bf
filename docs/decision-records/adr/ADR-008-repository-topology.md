# ADR-008: Топология: монорепо, модульный монолит, несколько точек входа

## Context

- Один владелец, одна команда, общий релизный цикл.
- Нужны кроны и воркеры-консьюмеры, но не отдельные сервисы с отдельными кодовыми базами.
- ADR-002 требует модулей по домену и общения только через фасады и сообщения (DEP-5).

## Options considered

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Монорепо, модульный монолит | один релиз; модули по DDD; несколько точек входа из одного кода | процессы масштабируются вместе | выбран |
| Монорепо с несколькими сервисами (как в прототипе) | независимое масштабирование | больше инфраструктуры без второй команды | отклонён |
| Полирепо | - | нет общего релизного цикла; одному человеку мешает | отклонён |

## Decision

1. Один pnpm-монорепозиторий.
2. Backend - модульный монолит, модули по ADR-002 (STR-1..9).
3. Из одной кодовой базы собираются несколько точек входа: HTTP API, воркеры-консьюмеры очереди, кроны.
4. Точки входа - отдельные процессы, но не отдельные сервисы: общий код, общие модули, общий релиз.
5. Модуль выделяется в сервис только по сигналу из `Revisit when`.

## Consequences

- Плюс: один деплой, один набор версий; кроны и воркеры без отдельных репозиториев.
- Минус: процессы одной кодовой базы масштабируются вместе с её зависимостями.
- Минус: границы держит только инструмент проверки (ADR-014).
- Дальше: структура пакетов и приложений - в ARCHITECTURE.md при первой спеке.

## Confirmation

Проверка границ в CI (ADR-014, backlog ENF-1).

## Revisit when

- Появляется вторая команда с отдельным циклом релизов.
- Модулю нужно независимое масштабирование, которого не даёт отдельная точка входа.
