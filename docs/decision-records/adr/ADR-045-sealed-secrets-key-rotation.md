# ADR-045: Sealed Secrets: чарт 2.22.0 в kube-system, автообновление ключа выключено, ротация вручную

| **Author** | агент |
| **Decided by** | агент по поручению владельца (2026-11-12): владелец написал в чате «постарайся все делать сам без моих подтверждений»; варианты ниже выбрал агент, владелец их по отдельности не подтверждал |
| **Tags** | security, secrets, deploy |

## Context

- ADR-020 выбрал Sealed Secrets, оставил копию закрытого ключа одну (менеджер паролей владельца) и требует обновлять её после ротации. ADR-037 отложил период ротации на SEALED-1.
- Апстрим по умолчанию создаёт новый ключ каждые 30 дней (флаг контроллера `--key-renew-period`, в чарте `keyrenewperiod`; `"0"` отключает). Старые ключи остаются и расшифровывают старые SealedSecret; `kubeseal --fetch-cert` отдаёт самый новый. Источник - README апстрима, на кластере не проверено.
- Копия, снятая до новой ротации, не расшифрует то, что запечатано новым ключом: при ротации раз в 30 дней копию надо обновлять каждые 30 дней, иначе она молча устаревает. Команда из двух человек, напоминаний и автоматики нет.
- Ротация не защищает прошлое: SealedSecret в истории Git расшифровывается старым ключом, поэтому при утечке ключа меняются сами значения (ADR-020). Новый ключ защищает только значения, запечатанные после утечки старого.
- Чарт - новая зависимость (красный флаг 3 AGENTS.md); ADR-020 выбрал инструмент, но не версию, место и форму установки. Правила версий - ADR-005; исключение ADR-034 на этот чарт не распространяется.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Ротация ключа | A. автообновление выключено (`keyrenewperiod: "0"`), ротация вручную раз в год и при подозрении на утечку | B. умолчание 30 дней: копия ключа устаревает молча, а выгода мала (прошлое не защищено); C. другой период (90 дней): число без основания, та же молчаливая устарелость |
| Место и имя | A. `kube-system`, `fullnameOverride: sealed-secrets-controller`: умолчания `kubeseal` работают без флагов | B. отдельный namespace: каждый вызов `kubeseal` и бэкапа с `--controller-namespace`, лишний шаг в `scripts/seal-secret.ts` |
| Форма установки | A. один файл Application в `deploy/argocd/`, значения inline, первый `kubectl apply` владельцем | B. два источника (чарт и values из нашего репозитория): ArgoCD не подключён к репозиторию (RUNBOOK-1); C. root app-of-apps: это работа RUNBOOK-1 |

## Decision

1. **Чарт** `sealed-secrets` 2.22.0 (appVersion 0.41.2), репозиторий `https://bitnami.github.io/sealed-secrets`, в `deploy/argocd/sealed-secrets.yaml`. Выпущен 2026-10-26, окно ADR-005 (7 дней) пройдено с 2026-11-02. Новая версия проходит то же окно и меняется в Application вместе с версией `kubeseal` в runbook.
2. **Контроллер** в `kube-system`, `fullnameOverride: sealed-secrets-controller`. Application: значения inline, `ServerSideApply=true`, автосинхронизация без `prune`; первый `kubectl apply` - владелец (RUNBOOK-1 ещё не подключил репозиторий к ArgoCD).
3. **Автообновление ключа выключено:** `keyrenewperiod: "0"`. Контроллер создаёт первую пару при первом старте; что после перезапуска число ключей не растёт, владелец проверяет на кластере (runbook, шаг 5 установки; по README апстрима не очевидно).
4. **Ротация вручную:** раз в год и при любом подозрении на утечку. Порядок - в `docs/runbooks/malinina-kubernetes.md`: новый ключ, обновление `deploy/sealed-secrets/pub-cert.pem`, перешифровка секретов, обновление копии в менеджере паролей (все ключи с меткой `sealedsecrets.bitnami.com/sealed-secrets-key`, не только новейший). При утечке ключа - ещё и смена самих значений (ADR-020).
5. **Сертификат** `deploy/sealed-secrets/pub-cert.pem` меняется только при ротации; первый коммит - владелец после установки (SEALED-2).
6. **Строка на первую ротацию** - в бэклоге владельцу (SEALED-3): без неё «раз в год» остаётся словами.

## Consequences

- Positive: одной копии ключа хватает надолго, она не устаревает молча; флаги `kubeseal` без `--controller-*`; один файл, ничего не ждёт RUNBOOK-1.
- Negative: ключ живёт бессрочно; утечка открывает все значения, запечатанные им (при ротации раз в 30 дней открылись бы те же старые значения, но не новые). Отход от умолчания апстрима, принят осознанно.
- Negative: ротация раз в год - человеческая задача и может быть забыта; цена забытого - ключ просто старее, а не поломка.
- Negative: свои объекты лежат в `kube-system`, которым управляет DO; пересечения имён с компонентами DO на кластере не проверялись (до первого `apply` сверяет владелец, порядок в runbook).
- Negative: версия чарта проверена только `helm template`; на кластере не ставилась и не синхронизировалась (SEALED-2).
- Делегирование: решено агентом по поручению владельца; владелец вправе оспорить любой пункт новой записью.
- Follow-ups: SEALED-2 (установка, сертификат, копия ключа), SEALED-3 (первая ротация), SECRETS-1 (скрипт шифрования).

## Confirmation

`pnpm charts` рендерит чарт с версией и значениями из Application (`scripts/charts-check.ts`), `pnpm charts:test` проверяет, что в Deployment есть `--key-renew-period "0"`, имя и namespace контроллера, CRD SealedSecret; CI запускает обе проверки при изменении `deploy/argocd/`. Остальное - ревью и runbook.

## Revisit when

- Доступ к закрытому ключу получает больше двух человек, или копия ключа переезжает в хранилище с автоматическим бэкапом: тогда автообновление снова дёшево.
- Утечка закрытого ключа.
- Апстрим меняет поведение ротации или ключей.
- Вышел чарт новее 2.22.0, прошедший окно ADR-005 (меняется версия, не решение).
