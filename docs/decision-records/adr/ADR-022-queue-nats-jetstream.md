# ADR-022: Очередь: NATS JetStream в кластере, одна реплика с PVC

## Context

- Очередь нужна для двух задач: события из Debezium (ADR-021) и задачи воркеров (ADR-008).
- Владелец назвал NATS JetStream и хочет запускать его в своём кластере (ADR-017).
- Бюджет облака - $100-150 в месяц, предпочтение тому, что дёшево простаивает (со слов владельца; записи нет - backlog BUDGET-1).
- NATS уже используется в e2e через service containers (ADR-018).
- Другие брокеры (Kafka, RabbitMQ, облачные очереди) не сравнивались; взвешивались только топология и хранение.

## Options considered

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| 1 реплика, PVC | дёшево; данные переживают перезапуск пода | единственный узел | выбран |
| 3 реплики (кластер NATS) | отказоустойчиво | втрое больше подов и томов; потребности в доступности пока нет | отклонён |
| 1 реплика без диска | ещё дешевле | перезапуск теряет неотданные сообщения; для событий недопустимо | отклонён |

## Decision

1. Очередь - NATS JetStream в кластере: одна реплика, файловое хранилище на PVC.
2. Один JetStream на события (ADR-021) и задачи воркеров (ADR-008).
3. Ставится сторонним Helm-чартом с точной версией в `deploy/argocd/` под ArgoCD (ADR-019, ADR-005).
4. Клиентская библиотека Node входит в это решение; пакет и версия закрепляются при первом использовании.

## Consequences

- Плюс: дёшево; один компонент на события и задачи; данные переживают перезапуск; тип очереди в CI и проде совпадает.
- Минус: единственный узел - пока под не поднялся, ничего не доставляется.
- Минус: недоступный NATS останавливает Debezium, а слот копит WAL (ADR-021).
- Минус: потеря тома - потеря необработанных сообщений.
- Минус: том DO привязан к узлу; перенос пода - простой.
- Минус: постоянно работающий под в бюджете.
- Дальше: стримы и subject'ы, хранение и повторы, раздельные стримы, размер тома и мониторинг, создание стримов при деплое - по мере появления потребителей.

## Confirmation

Только ревью. Версия чарта закреплена (ADR-005); e2e против реального NATS (ADR-018). Мониторинга и проверки тома в CI нет.

## Revisit when

- Требование доступности, которое один под не выдерживает.
- Неподтверждённые сообщения теряются из-за потери тома.
- Данные не помещаются на том.
- Для одной из двух задач JetStream перестаёт подходить и их приходится разделить.
