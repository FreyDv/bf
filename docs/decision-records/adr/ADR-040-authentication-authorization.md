# ADR-040: Аутентификация и авторизация: пароль и серверные сессии, права как данные

## Context

- ADR-037 закрыл оси Authentication и Authorization именованной отсрочкой в AUTH-1. Эта запись её закрывает: строки «Authentication» и «Authorization» таблицы ADR-037 читаются теперь вместе с ней. Текст ADR-037 не меняется.
- Известно от владельца (2026-11-11, `docs/PRODUCT.md`, BDR-001): два раздельных аккаунта, Даня и Валерия; права Валерии раздаёт Даня позже; покупатель без аккаунта ведёт заказ по номеру телефона. ChatGPT через MCP не публикует, не платит и не удаляет без владельца; полный список его вызовов отложен до первой MCP-спеки.
- Рамки уже приняты: Postgres и Drizzle (ADR-013), API - tRPC, MCP - отдельный driving adapter к тем же командам и запросам (ADR-012, ADP-2), один origin `malinina.ca` (ADR-038 п. 2), лимит частоты на ingress, IP клиента за балансировщиком не проверен (ADR-037, INGRESS-1), авторизация вне фильтра вызывающего (QRY-17), домен без крипто-библиотек и фреймворков (DEP-3, DEP-6).
- Новая зависимость требует записи (ADR-005, п. 5); новый платный сервис владелец исключил по умолчанию (бюджетный потолок со слов владельца, ADR-022).
- Кода авторизации, схемы БД и спеки нет: запись фиксирует решения, не реализацию.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Механизм входа | своя реализация: пароль, сессии в Postgres, без новых зависимостей | библиотека Better Auth: новая зависимость под ADR-005, релизы почти ежедневно (1.7.20-1.7.22 за 2026-11-10..12 по реестру npm), совместимость с NestJS 12 и tRPC не проверена; вход для MCP она обещает отдельным плагином и дополнительными пакетами (по её документации, мной не проверено). Внешний провайдер идентификации (платный сервис или свой кластер): цены не изучались, для двух пользователей избыточен, расходится с предпочтением владельца без платных сервисов |
| Хэш пароля | argon2id из `node:crypto` | пакет `@node-rs/argon2`: лишняя зависимость, когда рантайм её не требует |
| Сессия | серверная, в Postgres, непрозрачный токен в cookie | подписанный cookie без хранения (отзыв всё равно требует состояния, плюс новый ключ подписи как секрет); JWT в заголовке `Authorization` (токен в JS-доступном хранилище; отзыв так же труден; same-origin вебу не нужен) |
| Модель прав | права как данные: набор именованных разрешений на аккаунт | две жёсткие роли в коде (раздать права «позже» нельзя без релиза); готовый движок политик (новая зависимость без проблемы, которую она решает, PRG-4) |
| Где проверять | в приложении | RLS в базе: приложение работает под `doadmin` с `BYPASSRLS` (`docs/runbooks/bfdb-postgres.md`, DBSEC-3), а общий слой для tRPC и MCP и QRY-17 требуют проверки выше драйвера |
| Лимиты на вход | лимит на ingress плюс счётчик неудачных попыток по аккаунту в Postgres с нарастающей задержкой | жёсткая блокировка аккаунта: посторонний запер бы Даню; прикладная библиотека лимитов: ADR-037 её не запрещал, но счётчик по аккаунту и не зависит от непроверенного IP клиента, и пишется без зависимости |

## Decision

1. **Механизм.** Своя реализация. Пароль хэшируется argon2id из `node:crypto` (`crypto.argon2`, `argon2Sync`; есть в Node 26, на котором закреплён репозиторий, ADR-007; [документация Node](https://nodejs.org/docs/latest-v26.x/api/crypto.html); наличие функции проверено запуском на 26.13.0, текст документации не сверялся). Новых зависимостей нет. Крипто (хэш, сравнение, выдача токена) живёт в infrastructure-адаптере за портом (PRG-3: изоляция технологии и тестовый шов, DEP-3, DEP-4, DEP-6); домен ни `node:crypto`, ни фреймворк не видит. Параметры argon2id задаёт адаптер и хранит рядом с хэшем, чтобы смена параметров не ломала старые хэши; значения - в коде, смена не требует новой записи.
2. **Сессия.** Серверная, в Postgres. В браузер уходит непрозрачный токен в cookie с префиксом `__Host-`: `HttpOnly`, `Secure`, `SameSite=Lax`. Простой 7 дней, абсолют 30 дней; числа настраиваются без новой записи. Отзыв - удаление строки сессии; «выйти везде» - удаление всех строк аккаунта. CSRF: `SameSite=Lax` плюс проверка `Origin` на изменяющих запросах; запросы чтения состояния не меняют (APP-10). Next.js при серверном рендере передаёт cookie в `/api`.
3. **Аккаунты и пароли.** Аккаунты создаёт и пароли сбрасывает команда оператора. Она работает в кластере против `bfdb` и выполняется владельцем; агент её не запускает (красный флаг 1 в `AGENTS.md`). Начальный пароль не передаётся аргументом shell и не логируется: он читается со stdin или генерируется и показывается один раз. Поле пароля входит в список скрываемых полей pino (ADR-032 п. 4). Второй фактор - отдельная строка бэклога после SPEC-1 (AUTH-2).
4. **Модель прав.** Права - данные: набор именованных разрешений на аккаунт. Аккаунт владельца (Даня) держит все разрешения; остальные аккаунты получают именованные разрешения от Дани; у Валерии на старте разрешений нет, пока Даня их не выдаст (слова владельца 2026-11-11). Что значит `scope` в QRY-17 для каждого действующего лица, определяет спека возможности; общее производство - один scope для обоих аккаунтов.
5. **Где проверяется.** Аутентификация - в driving adapter (tRPC, MCP, CLI): он получает личность и кладёт её в метаданные команды или запроса (APP-6) и контекст запроса (ENF-5). Разрешение проверяет обработчик через порт (PRG-3: ввод-вывод в БД, тестовый шов с in-memory дублем по TST-5). Scope применяется в `WHERE` вне фильтра вызывающего: `WHERE scope AND (filter)` (QRY-17). Отказ доступа - типизированные коды с модулем в префиксе (ERR-1), результат типа `Result` (ERR-2); адаптер мапит их в транспорт (ERR-4).
6. **Покупатель.** Аккаунта нет; сценарий владельца сохранён: отследить, изменить и отменить заказ по номеру телефона. Как телефон доказывает владение заказом (код, SMS, иное), решает раздел abuse cases спеки заказов, не эта запись. Известный риск: один телефон - вектор перебора номеров (ADR-037, ось Rate limiting); scope покупателя тоже определяет спека заказов.
7. **MCP: принцип.** Клиент MCP получает отзываемый токен, привязанный к аккаунту человека, с подмножеством разрешений этого аккаунта; каждое изменение помечено источником (`agent`), чтобы быть видимым и обратимым (персона `ChatGPT через MCP`). Остальное решает первая MCP-спека: один агентский токен на Даню и Валерию («единый человек») или по одному на аккаунт, протокол (в том числе OAuth для ChatGPT), полный список разрешённых вызовов (`[NEEDS DECISION]` в `docs/personas.md` остаётся).
8. **Лимиты входа.** Периметр - лимит на ingress (INGRESS-1). Внутри - счётчик неудачных попыток по аккаунту в Postgres: задержка растёт с числом неудач, жёсткой блокировки нет, чтобы посторонний не запер Даню. Библиотека не нужна.
9. **Origin админки.** Тот же `malinina.ca`, cookie `__Host-` с `HttpOnly` (ADR-038). Отдельный origin - только по новым требованиям, как записано в ADR-038.
10. **Аудит.** Каждая запись любого действующего лица несёт id актора и источник в метаданных команды (APP-6) и в логе. Устройство журнала аудита целиком принадлежит первой спеке, которой нужен откат.

Не решено здесь, уходит в строку AUTH-3 и спеку доступа: правила пароля (длина, проверка по списку утёкших), сообщение об ошибке входа без утечки, существует ли аккаунт, `Secure`-cookie за балансировщиком и в локальной среде (ADR-033, TRAEFIK-1), отключение аккаунта, что считать потерей доступа Дани помимо команды оператора, чем счётчик попыток считает несуществующие аккаунты.

## Consequences

- Плюс: ноль новых зависимостей и платных сервисов; отзыв сессии и «выйти везде» - удаление строки; одна проверка прав для tRPC и MCP; «Даня раздаёт позже» работает данными, без релиза.
- Минус: безопасность на нашей стороне - хэш, сессии, сброс пароля пишем сами; OAuth-сервер для MCP придётся строить или подключать позже (первая MCP-спека).
- Минус: **решения по безопасности и правам приняты агентом по общему поручению владельца, не по каждому пункту.** `PRODUCT.md` и BDR-001 оставляют деньги, право и безопасность человеку; владелец может опровергнуть любой пункт новой записью, до тех пор действует эта.
- Минус: без второго фактора админка (цены, заказы) защищена паролем, лимитами и счётчиком; общий origin с витриной повышает цену XSS, смягчают `HttpOnly` и CSP (CSP-1) - до AUTH-2 это принятый риск.
- Минус: `synchronous_commit=off` (`docs/runbooks/bfdb-postgres.md`, DBSEC-2) - после сбоя узла последние транзакции могут пропасть: только что удалённая сессия может ожить, а счётчик неудач потерять последние попытки. «Мгновенный отзыв» верен до такого сбоя.
- Минус: чтение сессии из БД на каждый запрос и чистка просроченных строк; для двух пользователей это незаметно.
- Минус: задержка по аккаунту даёт постороннему замедлить вход Дани, но не запереть его; аккаунты сбрасывает только команда оператора, и пока её нет в коде, вход недоступен (AUTH-3).
- Минус: телефон как единственный ключ покупателя остаётся риском перебора, пока спека заказов не назовёт доказательство владения.
- Дальше: AUTH-2 (второй фактор), AUTH-3 (вход и сессии), AUTH-4 (права и проверка); строка PRIVACY-1 про данные покупателя - отдельная.

## Confirmation

Пока ничего: кода нет. Когда он появится: `pnpm deps` ловит `node:crypto` и драйвер вне infrastructure (DEP-3, ADR-014); поведенческие тесты спеки (TST-1) проверяют отказ без сессии, отказ без разрешения, истечение простоя и абсолюта, отзыв, задержку после неудач; тест логов проверяет, что пароль и токен скрыты (ADR-032 п. 4); `ddd-review` читает проверку прав в обработчике и `WHERE scope AND (filter)`. Не подтверждено: что `crypto.argon2` в образе даёт ожидаемое время на узле кластера.

## Revisit when

- Аккаунтов становится больше двух, или появляется внешний пользователь с входом: пересмотреть своё решение против библиотеки или провайдера.
- Первая MCP-спека показывает, что ChatGPT принимает только OAuth и свой сервер дороже библиотеки: новая запись про протокол или механизм.
- Админке нужен отдельный origin (триггер ADR-038), либо найден XSS на витрине, который `HttpOnly` и CSP (CSP-1) не гасят.
- Подбор пароля или кража сессии на деле; либо DBSEC-2 решает `synchronous_commit` иначе: сроки и отзыв пересматриваются.
- Владелец опровергает любой пункт новой записью.
