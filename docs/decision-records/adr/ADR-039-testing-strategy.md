## Context

- R7 и [чек-лист](../../standards/vendor/repository-standards-core/method/checklist.md) требуют записать именованные уровни тестов, где каждый выполняется, и пути, где тесты не обсуждаются.
- Форма тестов уже задана: TST-1..5 (три уровня на срез, отказ на БД без `test` в имени, уборка, дубли портов в кодовой базе), QRY-18 и QRY-20 для фильтров, ADR-025 для outbox. Раннер - Vitest (ADR-016).
- Где тесты идут в CI, решено и не пересматривается: имена скриптов `test` и `test:e2e` (ADR-018), шаг `Unit tests` до подъёма Postgres и NATS, шаг e2e только если `turbo run test:e2e --dry=json` показывает задачу (ADR-036 п. 4).
- Не решено: какой уровень TST-2 идёт каким скриптом; имена и места файлов; изоляция `bf_test`; обязательные пути; уровень тестов фронтенда; судьба adversarial-тестов, которую ADR-037 отдал в TEST-1; чем считаются `deps:test`, `charts:test`, `migrations:test` (они на `node --test`, а не на Vitest).
- Проверка границ (ADR-014) не знает тестов: единственное исключение - `from` правила `not-to-dev-dep-from-prod`. `dep-3-domain-no-libraries` запрещает npm-импорты в `domain/`, поэтому `domain/*.test.ts` с `import ... from 'vitest'` её нарушает; `dep-2-application-no-outer-layers`, `dep-2-infrastructure-only-ports`, `dep-2-adapters-no-domain-no-infrastructure` держат поведенческий тест, который поднимает роутер и доходит до infrastructure. Соглашение «тест рядом со срезом» без записи отступления не проходит `pnpm deps`; ENF-1 запрещает чинить это молча в конфиге.
- Кода нет: `apps/backend` пуст, ни один пакет не определяет `test:e2e`, пресет Vitest берёт `src/**/*.test.ts`.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Уровни и скрипты | три уровня TST-2 на два скрипта: `test` без Docker, `test:e2e` с реальной БД и NATS | третий скрипт `test:integration`: меняет имена ADR-018, лишний шаг CI без потребителя (PRG-3); не называть уровни: развилка R7 остаётся открытой |
| Файлы | рядом со срезом: `*.test.ts` и `*.e2e.test.ts` | зеркальное дерево `test/`: TST-4 его допускает, но разносит файлы, которые меняются вместе (STR-3); путь стандарта (`*.integration.test.ts` по проектам Vitest, `e2e/` в корне): другие имена, чем скрипты ADR-018, а межприложенческих сценариев нет |
| Подключение | строки бэклога | подключить в этом PR: код без потребителя при пустом backend (PRG-3) |
| Границы для тестов | запись отступления здесь, правка конфига отдельной строкой с фикстурами | тесты вне `src/`: конфиг их не видит, но они отрываются от срезов; правка `.dependency-cruiser.mjs` в PR с решением: конфиг меняется только вместе с фикстурами в `deps:test` |
| Изоляция БД | общая `bf_test`, реальные миграции, файлы по очереди | БД из шаблона на воркер: параллелизм, но скрипт и init в compose без потребителя (прав хватает: `doadmin` имеет `CREATEDB`, ADR-033); схема на воркер: усложнение без потребителя |
| Обязательные пути | категории без числового порога | порог покрытия: нужен coverage-провайдер (зависимость и ADR) и стимулирует тест ради цифры; не называть пути: пункт чек-листа пуст |
| Фронтенд | отложить с сигналом | Playwright или jsdom и Testing Library сейчас: новая зависимость, страниц нет |
| Adversarial | оставить отложенным (ADR-037) | property-тесты сейчас: новая зависимость, парсеров и фильтров в коде нет |
| Политики | политики стандарта | nightly и перезапуск флаки-тестов: минуты CI без кода, перезапуск прячет флаки |

## Decision

1. **Уровни и скрипты.** Три уровня TST-2 идут на двух скриптах:

| Уровень | Что | Скрипт | Файл |
|---|---|---|---|
| Доменный unit | агрегаты, объекты-значения, события; без инфраструктуры | `test` | `<имя>.test.ts` |
| Use case | handler с in-memory дублями портов | `test` | `<имя>.test.ts` |
| Type-level и контрактные | типы и схемы контракта (QRY-18, QRY-20, ADR-012), без БД | `test` | `<имя>.test.ts` |
| Поведенческий | через driving adapter на реальной `bf_test` и NATS; тесты фильтров на Postgres (QRY-18: NULL, кванторы) | `test:e2e` | `<имя>.e2e.test.ts` |

   1. Признак границы: тесту нужен Postgres или NATS - это `test:e2e`; `test` их не поднимает и идёт без Docker. Тест с БД в `test` отнесён к уровню неверно.
   2. Пакет, которому нужна `bf_test`, определяет свой `test:e2e` (`turbo.json`: ADR-036 п. 4).
   3. Механизм type-level тестов выбирает строка подключения; новой зависимости он не вводит.
   4. Проверки CI `contracts:check`, `deps`, `charts`, `migrations:check`, `image:check` тестами не называются и в уровни не входят (ADR-035, ADR-014, ADR-019, ADR-036).

2. **Наборы тестов репозитория.** `deps:test`, `charts:test`, `migrations:test` - отдельный вид: проверяют гарды и инструменты репозитория, а не продукт. Они на `node:test`, разрешены только в `scripts/`, идут в job `ci` (и два из них в `lefthook.yml`). В `apps/` и `packages/` тесты только на Vitest.

3. **Файлы.**
   1. Тест лежит рядом с тем, что проверяет, в срезе или на уровне модуля (TST-4, STR-3). Папки `test/` нет.
   2. In-memory дубль порта (TST-5) - файл `<порт>.in-memory.ts` рядом с портом, который он реализует: `application/ports/cycle-read.port.ts` и `application/ports/cycle-read.in-memory.ts`. Дубль не импортирует `vitest`, он обычный файл и подчиняется правилам границ как любой другой.
   3. Пресет `nestVitest` сейчас берёт `src/**/*.test.ts`, то есть и `*.e2e.test.ts`; строка подключения разводит `test` и `test:e2e`.

4. **Границы для тестовых файлов.** Это запись отступления, которую требуют ENF-1 и AIP-1: имя правил, модуль, причина.
   1. Файл `*.test.ts` или `*.e2e.test.ts` может импортировать `vitest` (отступление от DEP-3 для `domain/`) и код, который проверяет, из любых слоёв своего модуля (отступление от DEP-2: поведенческий тест поднимает роутер и доходит до infrastructure).
   2. Остаётся в силе и для тестов: DEP-5 (чужой модуль только через `public/`), DEP-9 (циклы), DEP-8 (срез не импортирует чужой срез).
   3. Для файлов, не являющихся тестами, правила не меняются; ни один такой файл не импортирует тест.
   4. Изменение `.dependency-cruiser.mjs` (исключение по маске имени, фикстуры в `deps:test`) - строка TEST-3, не этот PR; конфиг не ослаблен. Пока строки нет, `pnpm deps` отклоняет доменный тест с `vitest`. Правит тот же файл, что BOUND-1.

5. **Изоляция тестовой БД.**
   1. Одна общая `bf_test` (ADR-033); схема создаётся теми же файлами миграций (`apps/backend/migrations/`, ADR-036), без push схемы.
   2. Файлы `test:e2e` идут последовательно; параллелизма между файлами на одной БД нет.
   3. Тест убирает то, что создал, в БД и в NATS (TST-3).
   4. Отказ запускаться на БД, чьё имя не содержит `test`, - общий хелпер, который выполняется до первого запроса (TST-3).
   5. Кто применяет миграции к `bf_test` перед прогоном (локально и в CI) - строка подключения TEST-2.

6. **Обязательные пути.** Поведенческий тест уровня `test:e2e` обязателен для категорий:
   1. деньги;
   2. доступ и авторизация;
   3. персональные данные;
   4. внешние контракты: tRPC-контракт и интеграции с внешними сервисами, которые назовут спеки;
   5. query с фильтром (QRY-18);
   6. транзакция и outbox по ADR-025: откат на `Result.err` и на исключении не оставляет строк outbox, `change` попадает в `changed`.
   7. Числового порога покрытия нет и coverage-провайдера нет: покрытие - пол на этих путях, не процент.
   8. Какие пути модуля попадают в категории, называет его спека. Критерий приёмки без теста - находка ревью `ddd-review` (TST-1, AIP-6.7).

7. **Фронтенд.** Браузерного и компонентного уровня нет; Vitest во frontend остаётся, `test` проходит с `--passWithNoTests`. Инструмент не выбирается и не называется. Пересмотр - первая спека с критерием приёмки в интерфейсе (строка TEST-4).

8. **Adversarial-тестирование** остаётся «не применимо на старте» (ADR-037, ось Adversarial testing). Этот ADR пункт «пересмотр: TEST-1» ADR-037 закрывает подтверждением; триггер - первая спека, принимающая недоверенный ввод, или первый модуль, разбирающий внешние данные. До тех пор: раздел abuse cases в спеках (ADR-037), QRY-18, TST-1 и TST-2 растут вместе с кодом.

9. **Политики.**
   1. Тест меняется в одном PR со спекой (R11, AIP-5).
   2. Флаки-тест уходит в карантин с владельцем, строка бэклога; перезапуска без конца нет.
   3. Pre-commit Vitest-наборов не гоняет (`lefthook.yml` держит `deps:test` и `charts:test` как проверки гардов); на PR идёт затронутое, на `main` всё (ADR-018).
   4. Nightly-прогона и нагрузочных тестов нет (TST-4: нагрузочные опциональны).

## Consequences

- Positive: на вопрос «в каком скрипте этот тест» один ответ по одному признаку; первый модуль не придумывает своё соглашение; пути денег, доступа и данных названы заранее.
- Positive: шаг `Unit tests` в `ci` идёт до подъёма Postgres и NATS (`ci.yml`), поэтому `test`, которому нужна БД, упадёт в CI сам.
- Negative: соглашение не проверено кодом до первого потребителя; шаг e2e в CI пропускается (задач 0), пока ни один пакет не определил `test:e2e`.
- Negative: до TEST-3 `pnpm deps` отклоняет доменный тест с `vitest`, поэтому первый модуль с доменными тестами ждёт эту строку.
- Negative: Docker-зависимый тест в `test` через стороннюю библиотеку CI не поймает (на раннере Docker есть); такая библиотека - зависимость и ADR (R21), так что ловит её ревью.
- Negative: доставка outbox в NATS через Debezium в CI не проверяется: `local:up` идёт без профиля `cdc` (ADR-036 п. 4). Обязательны строки в `outbox` и откат (п. 6), доставка - строка TEST-5.
- Negative: «критерий без теста» ловит ревью, не машина; числового порога нет.
- Negative: порядок файлов `test:e2e` последовательный, при росте числа файлов прогон дольше.
- Not decided here: бюджет производительности (Lighthouse из стандарта) - строка PERF-1.
- Follow-ups: TEST-2 (подключение), TEST-3 (границы для тестов), TEST-4 (фронтенд), TEST-5 (доставка outbox), PERF-1.

## Confirmation

- Ревью: `ddd-review` (AIP-6.7: три уровня, критерии спеки покрыты, дубли портов) и `pre-pr-review`; признак «нужен Docker - `test:e2e`» и «критерий без теста» проверяет только ревью.
- Машинно: порядок шагов `ci.yml` (unit до `local:up`); шаг e2e после подключения (TEST-2); отказ на БД без `test` в имени - хелпер TST-3 (TEST-2); фикстуры тестовых исключений в `pnpm deps:test` (TEST-3).
- Пока кода нет, остальное - только ревью.

## Revisit when

- Появился первый `test:e2e` и шаг e2e в `ci` выполнился: сверить соглашение о файлах и изоляцию с кодом.
- Последовательный прогон `test:e2e` стал самым долгим шагом job `ci`: вернуться к БД из шаблона или схеме на воркер.
- Первая спека с критерием приёмки в интерфейсе: TEST-4, отдельный ADR на инструмент (зависимость, R21).
- Первая спека, принимающая недоверенный ввод, или первый модуль с разбором внешних данных: adversarial-тесты.
- Первая спека, где доставка события в NATS - критерий приёмки: TEST-5, нужен ли профиль `cdc` в CI.
