# ADR-059: Агент сам работает с непродакшен-кластером без подтверждений

| | |
| --- | --- |
| **Status** | Accepted |
| **Date** | 2026-11-13 |
| **Author** | агент |
| **Decided by** | владелец, в чате 2026-11-13: «тот кластер пока не имеет ни чего и он не совсем продакшен так что ты можешь сам делать все что захочешь; пропиши это в своих правилах которые тебе мешали вызывать там команды» |
| **Tags** | security, process, agent, deploy |

## Context

- ADR-056 п. 1, 2 и 7 поставили `kubectl`, `doctl`, `kubeseal`, `argocd` и изменяющие подкоманды `helm` в `ask` и запретили агенту трогать живой кластер. ADR-047 (Context) повторяет запрет; скилл `backlog-burndown` и workflow `backlog-execute`, `backlog-prepare` тоже.
- Каждая проверка на кластере (DEPLOY-1, TRAEFIK-2, SEALED-2) шла через владельца: агент давал команду, владелец запускал.
- Владелец: в кластере пока ничего нет, это не продакшен. Пользователей и их данных в нём нет.
- В Claude Code правило `ask` сильнее `allow`: пока запись стоит в `ask`, разрешение в `settings.local.json` её не снимает. Значит, правится `.claude/settings.json` (запись манифеста `merge`).

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Что открыть | `kubectl`, `helm` (все подкоманды), `argocd`, `kubeseal`; из `doctl` только `kubernetes`/`k8s` и `registry` | весь `doctl`: это весь аккаунт DO - управляемая БД, биллинг, новые платные ресурсы; к кластеру не относится |
| Уровень | `allow` в общем `settings.json` | `allow` в `settings.local.json`: `ask` его перекрывает; режим без запросов: снимает и прочие защиты |
| Удалённая БД | остаётся как есть (хук `no-remote-db-writes.sh`, красный флаг 1) | открыть вместе с кластером: владелец говорил о кластере, не о БД; хук - вендорный `copy` |
| Срок | до признания кластера продакшеном | бессрочно: забудется, когда появятся данные |

## Decision

1. **Агент сам выполняет команды на кластере** - чтение, диагностика, `apply`, `delete`, `rollout`, `port-forward`, `exec`, `helm install|upgrade|uninstall`, `argocd app sync`, `kubeseal` - без подтверждения владельца.
2. **`.claude/settings.json`**: из `permissions.ask` убраны `kubectl`, `kubeseal`, `argocd` (с голыми формами), все записи `helm` и `doctl`; в `permissions.allow` добавлены `kubectl`, `helm`, `argocd`, `kubeseal` целиком и `doctl kubernetes`, `doctl k8s`, `doctl registry`. Остальной `doctl` остаётся в `ask`. `deny` и хуки не тронуты.
3. **GitOps остаётся источником желаемого состояния.** То, что должно пережить синхронизацию ArgoCD, идёт коммитом в `deploy/`; прямая правка - для диагностики, bootstrap и проверки. Правка, которую ArgoCD откатит, - не изменение.
4. **Не открыто:** запись в удалённую БД (красный флаг 1), новые платные ресурсы DO и удаление самого кластера (красный флаг 3, бюджет владельца), запись `gh api` (ADR-056 п. 3, 4), force-push.
5. **Заменяет** ADR-056 п. 1, 2, 7 и строку ADR-047 «Живой кластер агент не трогает»; остальное в обеих записях в силе. Скилл `backlog-burndown` и workflow `backlog-execute`, `backlog-prepare` приведены к этой записи.

## Consequences

- Positive: проверки DoD «на кластере» (DEPLOY-1, SEALED-2, TRAEFIK-2) агент делает сам, без круга через владельца.
- Negative: ошибочная команда агента ломает кластер без остановки; цена низкая, пока в нём ничего нет.
- Negative: `kubectl` ходит в тот контекст, что выбран в `~/.kube/config`; если там появится другой кластер, разрешение распространится и на него.

## Confirmation

`jq . .claude/settings.json` разбирает файл; `bash scripts/verifyAgentGuards.sh` зелёный; `git diff` строк `deny` пуст.

## Revisit when

- В кластере появляются данные реальных пользователей, или владелец называет его продакшеном: вернуть `ask` новой записью (до первого выката с реальными пользователями).
- В `~/.kube/config` появляется второй кластер.
