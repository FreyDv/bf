# ADR-060: Скрипт `seal-secret`: строгий разбор `.env`, секрет на файл, манифест для сторонних чартов, проверка шифртекста

## Context

- ADR-020 п. 3 поручает общему `scripts/seal-secret.ts` зашифровать весь `.env.production` и записать `deploy/apps/<app>/secrets.yaml`; формат файла, разбор и проверки в нём не заданы.
- Встроенный `util.parseEnv` (ADR-020 п. 4) мягкий: из повторных ключей берёт последний, обрезает `a#b` до `a`, принимает ключ `BAD KEY`, молча пропускает нечитаемую строку (проверено на Node 26.13). `kubeseal` запечатывает пустой stdin без ошибки. Для секретов это тихая порча.
- ADR-053 п. 4: два секрета БД (`migrator` и `app`) для одного приложения; ADR-020 п. 3 допускает отдельный секрет, способа его описать нет.
- Сторонним чартам (NATS-3, позже Loki, Grafana, Debezium) нужен готовый манифест `SealedSecret`, а не значения для чарта `app`.
- Строгая область (ADR-020, «Ключи» п. 4): шифртекст привязан к имени секрета и namespace, поэтому имя в скрипте и имя релиза чарта обязаны совпасть.

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Разбор `.env` | своя построчная проверка перед `util.parseEnv`; значения читает parseEnv | один parseEnv (молча портит); зависимость `dotenv` (нужен ADR, ADR-005) |
| Несколько секретов приложения | файл на секрет: `.env.production` -> `<app>-secrets`, `.env.<name>.production` -> `<app>-<name>-secrets` | ключ-префикс внутри одного файла (имя секрета не видно по имени файла); отдельный флаг на секрет |
| Сторонние чарты | второй режим: полный манифест `SealedSecret` из `--env`, `--name`, `--namespace`, `--out` | ручной `kubeseal` (против предпочтения TS-скриптов); значения в `values` стороннего чарта (чарт их не знает) |
| Защита от открытого текста в `secrets.yaml` | `--check` в `pnpm charts` (CI): значение похоже на шифртекст `kubeseal` | gitleaks (видит секрет по образцу, шифртекст-заглушку не отличает от открытого значения без образца); парсер YAML (новая зависимость) |
| Имя секрета | имя каталога приложения = имя релиза Helm; namespace `bf` | аргумент командной строки на приложение (расхождение с релизом, расшифровки не будет) |

## Decision

1. **Вход.** Строка `secrets:seal` в `package.json` приложения одна и та же: `node ../../scripts/seal-secret.ts`, без аргументов. Корневой `pnpm secrets:seal` = `turbo run secrets:seal` (задача без кеша). Сейчас скрипт только у `apps/backend`. Приложение со скриптом, но без `.env.production`, падает с понятной ошибкой, молча не пропускается.
2. **Ввод-вывод `kubeseal`.** `kubeseal --raw --cert deploy/sealed-secrets/pub-cert.pem --scope strict --name <секрет> --namespace <ns>`; значение идёт в stdin, запуск `spawnSync` без shell. Значение не попадает в argv, вывод, лог, сообщение об ошибке и временный файл; сообщения называют ключ и номер строки. Версию `kubeseal` и отпечаток сертификата не проверяем (отпечаток меняется при ротации, ADR-045); проверяем, что `kubeseal` в `PATH` и сертификат разбирается `node:crypto` (`X509Certificate`) и не просрочен.
3. **Строгость `.env`.** Сначала скрипт сам читает строки и отказывает (код 1, без значений) на: повторный ключ, пустое значение, ключ не по `^[A-Z_][A-Z0-9_]*$`, `#` без кавычек внутри значения, многострочное значение (включая `\n` в двойных кавычках), строку без `=`, файл без ключей. Затем значения читает `util.parseEnv`, и каждое должно совпасть со строкой файла. Пока весь файл не чист и каждый ключ не запечатан, ничего не пишется; запись атомарная (временный файл рядом, `rename`), во временном файле только шифртекст.
4. **Файл на секрет.** `apps/<app>/.env.production` -> секрет `<app>-secrets` (`secret.encryptedData`, контракт чарта `app`); каждый `apps/<app>/.env.<name>.production` -> `<app>-<name>-secrets` (`extraSecrets.<name>.encryptedData`, `<name>` по `^[a-z][a-z0-9-]*$`). Всё в `deploy/apps/<app>/secrets.yaml`, файл переписывается целиком, ключи в порядке файла `.env`. Какой процесс получает какой секрет и отрисовка `extraSecrets` - CHART-5, не эта запись.
5. **Сторонние чарты.** `--env <файл> --name <секрет> --namespace <ns> --out <путь>` пишет полный манифест `SealedSecret` (`bitnami.com/v1alpha1`, строгая область) тем же ядром разбора и шифрования.
6. **Источник не коммитится.** Файл `.env` (в обоих режимах) обязан быть проигнорирован git: `git check-ignore`; иначе отказ, файл не читается. Отслеживаемый файл и файл вне репозитория тоже отказ.
7. **Цель.** Имя приложения - `basename` каталога `apps/<app>`, из которого запущен скрипт; имя релиза Helm то же; namespace `bf` (ADR-038 п. 1); выход `deploy/apps/<app>/secrets.yaml` от корня репозитория. Имя длиннее 40 символов или с `-` на конце отказ: чарт режет `Release.Name | trunc 40 | trimSuffix "-"` (`deploy/charts/app/templates/_helpers.tpl`), и строгий секрет не расшифруется. Application ArgoCD (релиз Helm) каждого приложения называется точно как его каталог в `apps/` (условие в DEPLOY-1).
8. **`--check`.** Каждое значение под `secret.encryptedData` и `extraSecrets.*.encryptedData` в `deploy/apps/*/secrets.yaml` - base64, не короче 300 знаков, начинается с `Ag` или `AQ` (длина обёрнутого ключа RSA-4096 или RSA-2048 у `kubeseal`). Запускается из `pnpm charts` (`scripts/charts-check.ts`), значит в CI. Файл читается строго в той форме, в какой его пишет скрипт (парсера YAML в репозитории нет, ADR-005); другая форма - ошибка. Соответствие ключей `.env` в CI не проверяется (там нет `.env`): обычный запуск переписывает файл целиком. `.env.example` не заводим.

## Consequences

- Positive: тихая порча значения (повтор, `#`, пустое) не доходит до кластера; открытое значение в `secrets.yaml` ловит CI; секреты `migrator` и `app` (ADR-053 п. 4) запечатываются одним скриптом.
- Negative: строже `parseEnv`: значение с `#` придётся взять в кавычки, `export KEY=...` и `KEY: value` не принимаются, текст после закрывающей кавычки тоже; `--check` отличает шифртекст по виду, не расшифровывает (шифртекст не под тем именем в CI не виден, это видно только при синхронизации).
- Negative: переименование каталога приложения или Application ArgoCD ломает расшифровку без ошибки в CI; страхует условие в DEPLOY-1.
- Negative: интеграционный тест с настоящим `kubeseal` в CI пропускается (`kubeseal` на раннер не ставим); юнит-тесты с подставным запускающим идут в CI.
- Follow-ups: CHART-5 (отрисовка `extraSecrets`, привязка секретов к Job и Deployment), NATS-3 (первый потребитель режима манифеста).

## Confirmation

`pnpm secrets:seal:test` (CI): разбор и каждый отказ, аргументы `kubeseal`, отсутствие значений в argv, выводе и файлах, перезапись целиком, раздельные секреты, манифест, `--check`, отказ для не игнорируемого файла, нет частичного файла при сбое; тест с настоящим `kubeseal` и одноразовым сертификатом (пропускается без `kubeseal`). `pnpm charts` вызывает `--check`.

## Revisit when

- Появляется второй формат значений (многострочные: сертификат, ключ PEM) - тогда строгий разбор расширяется записью.
- `kubeseal` или контроллер меняют формат шифртекста так, что `--check` отвергает настоящий (длина или префикс).
- В репозиторий приходит парсер YAML - `--check` читает файл им, а не по форме.
