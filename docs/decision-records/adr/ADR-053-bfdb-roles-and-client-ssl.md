# ADR-053: Роли в `bfdb` и режим SSL клиента: `migrator` и `app` вместо `doadmin`

| **Decided by** | агент по поручению владельца (2026-11-12, 2026-11-13): владелец написал в чате «постарайся все делать сам без моих подтверждений» и «Продолжай, не жди меня»; варианты ниже выбрал агент, владелец их по отдельности не подтверждал; владелец вправе оспорить любой пункт новой записью |
| **Tags** | datastore, security, ssl, migrations |

## Context

- В `bfdb` одна роль `doadmin` (LOGIN, CREATEROLE, CREATEDB, REPLICATION, BYPASSRLS), одна база `defaultdb`, таблиц 0, кода работы с БД нет (`docs/runbooks/bfdb-postgres.md`). Менять модель сейчас дёшево: владения таблиц ещё нет.
- Приложение под `doadmin` при утечке его секрета даёт роли, репликацию и обход RLS; для работы ему нужен только DML (ADR-037, ось Data at rest, отдала выбор в DBSEC-3).
- ADR-013 про роль и SSL молчит: миграции вперёд, применяет механизм выката или человек. ADR-019 и ADR-047: миграции идут Job в кластере (хук `Sync`, волна 0), секреты БД не покидают кластер.
- ADR-033 п. 3 запускает приложение и Debezium локально под `doadmin` «как на DO»; ADR-040 отклонил RLS, среди прочего потому, что приложение работает под `doadmin` с `BYPASSRLS`.
- Не проверено живым кластером: `ssl_min_protocol_version`, права по умолчанию на схему `public`, покрывает ли сертификат DO приватный хост. Агент к кластеру не обращается (красный флаг 1); проверки делает владелец (DBSEC-7).

## Options considered

| Развилка | Выбрано | Отклонено |
|---|---|---|
| Роли | B. две: `migrator` (владелец объектов, DDL) и `app` (только DML); `doadmin` только у владельца вручную | A. `doadmin` для всего: секрет с CREATEROLE, REPLICATION, BYPASSRLS в кластере; C. `app` для приложения, миграции под `doadmin`: `doadmin` остаётся в кластере, владелец таблиц `doadmin`, гранты на каждую таблицу, второй секрет всё равно нужен |
| База | отдельная `bf`, владелец `migrator` | `defaultdb`: принадлежит `doadmin`, `DROP` и `ALTER DATABASE` остаются за ним |
| Права на объекты | C. записать инвариант; схему и точные `GRANT` отдать SCHEMA-1 | A. объекты в `public` и `ALTER DEFAULT PRIVILEGES` сейчас: зависит от непроверенной ACL `public`; B. отдельная схема сейчас: опережает SCHEMA-1 |
| Создание ролей | через DigitalOcean (`doctl databases user create`), права и владение - SQL для человека | `CREATE ROLE` под `doadmin`: DO API роли не знает, `doctl databases user list` и `pg_roles` расходятся после обслуживания или пересоздания узла |
| Режим SSL | B. `verify-full` в production по CA DO из ConfigMap, приватный хост VPC; локально и в CI без SSL | A. `require`: шифрует, сервер не проверяет (подмена внутри доверенных источников остаётся); C. страж при старте сразу: кода подключения ещё нет, страж идёт строкой |
| Debezium | A. роль и шаг CDC-1 остаются за CDC-3 | B. решить здесь три роли: нужны факты об `aiven_extras` и публикациях, которых нет |
| Локально и в CI | A. те же две роли; замещает п. 3 ADR-033 в части роли приложения | B. оставить `doadmin`, расхождение принять: тесты под владельцем с `BYPASSRLS` не заметят недостающий грант |

## Decision

1. **Роли.** `migrator` - владелец базы `bf` и всех объектов в ней, выполняет DDL (миграционный Job). `app` - только DML: без CREATEROLE, REPLICATION, BYPASSRLS, CREATEDB, без CREATE на любой схеме. `doadmin` используется только владельцем вручную и в кластере не живёт: ни в Secret, ни в ConfigMap, ни в values.
2. **База.** Приложение работает в отдельной базе `bf`, владелец `migrator`; `defaultdb` приложением не используется. Имя в кластере (`bf`) и локально (`bf_dev`, ADR-033) разные, как было с `defaultdb` (`docs/runbooks/bfdb-postgres.md`, находка 7): расхождение только в строке подключения.
3. **Объекты и права, инвариант.** Объекты создаёт и владеет ими `migrator`; `app` объекты создавать не может; DML (и USAGE на sequences) `app` получает по умолчанию через `ALTER DEFAULT PRIVILEGES` роли `migrator`, а не выдачей на каждую таблицу. Имя схемы и точные `GRANT`/`REVOKE` (включая право CREATE у `PUBLIC` на `public`) решает SCHEMA-1; SQL - файл `.sql`, который применяет человек после того, как владелец проверит ACL схемы `public`.
4. **Создание и пароли.** Роли создаются через DigitalOcean (`doctl databases user create`), чтобы DO API их знал; атрибуты, владение и гранты - SQL, который применяет человек (агент в живую БД не пишет). Пароли `migrator` и `app` - два отдельных SealedSecret (миграционный Job читает один, Deployment другой); ротация - по runbook секретов (SEALED-2, SEALED-3, ADR-020, ADR-045).
5. **SSL клиента.** В production клиент требует `verify-full` по сертификату CA кластера DO; CA лежит в ConfigMap чарта (сертификат публичный), подключение идёт по приватному хосту `private-bfdb-...` в VPC. Условная ветка: если сертификат не покрывает приватный хост (проверка владельца, DBSEC-7), режим `verify-ca` с тем же CA; это условие записи, правки записи не требует, результат проверки владелец пишет в runbook. Локально и в CI SSL нет. Запуск в production с режимом ниже `verify-full` (или `verify-ca` по ветке) запрещён; проверка при старте - отдельная строка DBSEC-8, приходит с первым подключением к БД.
6. **Минимальная версия протокола.** Ожидается `ssl_min_protocol_version` не ниже TLSv1.2. Условный пункт, результат проверки пишется в runbook без правки записи: если проверка владельца (DBSEC-7) покажет ниже, версия поднимается через `doctl databases configuration` (действие владельца); если параметр DO не меняет, принятый риск: клиент требует TLSv1.2, сервер остаётся при настройке DO, доступ ограничен доверенными источниками (ADR-037).
7. **Debezium и репликация.** `migrator` и `app` без REPLICATION. Роль Debezium и владелец шага CDC-1 (репликационный SQL) решает CDC-3; до неё CDC-1 здесь не решается, Debezium остаётся как в ADR-033.
8. **Локальная среда и CI.** Init SQL compose и CI e2e создают `migrator` и `app` так же, как на DO; `pnpm test:e2e` и `pnpm migrations:check` выполняют DDL под `migrator`, а тесты, которые проверяют поведение приложения, идут под `app`. **Заменяет п. 3 ADR-033 в части роли приложения** (там сказано «приложение и Debezium - `doadmin`»); часть про Debezium и остальные пункты ADR-033 действуют без изменений, ADR-033 остаётся Accepted и не правится (тот же приём, что ADR-030 с ADR-019). Правка init SQL, compose и CI - строка LOCAL-3.
9. **Пулы и соединения.** Вне этой записи: пулов DO нет, `max_connections=100` (`docs/runbooks/bfdb-postgres.md`); `CONNECTION LIMIT` по ролям решается вместе с DEPLOY-1.
10. **ADR-040.** Довод «приложение работает под `doadmin` с `BYPASSRLS`» в основании отказа от RLS (ADR-040, «Где проверять») больше не верен. RLS остаётся отклонённым по остальным доводам: авторизация в приложении, общий слой для tRPC и MCP, QRY-17. ADR-040 не правится.

## Consequences

- Positive: утечка секрета приложения не даёт ни DDL, ни ролей, ни репликации, ни обхода RLS; владение таблиц ясное с первой миграции; клиент проверяет сервер, а не только шифрует канал; локальные тесты ловят недостающий грант.
- Negative: второй SealedSecret и разделение секретов в чарте (сейчас Job и Deployment делят env, `deploy/charts/app/templates/migration-job.yaml`); два набора ролей в init SQL и CI; в первый выкат (ADR-047) добавляется шаг с `migrator`; сертификат CA нужно доставить и обновлять.
- Negative: условные ветки пп. 5 и 6 открыты до проверки владельца; строка в ADR-037 («отдельная роль и проверка SSL - DBSEC-3») и «под `doadmin`» в ADR-040 остаются в Accepted-записях и читаются по этой ссылке.
- Negative: вариант «база на воркер» ADR-039 опирался на CREATEDB у `doadmin`; у `app` и `migrator` его нет, и если вариант понадобится, его пересматривает новая запись.
- Pooling: `CONNECTION LIMIT` по ролям и DO-пулы не решены (п. 9).
- Follow-ups: DBSEC-7 (проверки и создание ролей и базы - владелец), CHART-5 (два секрета в чарте), LOCAL-3 (init SQL, compose, CI под двумя ролями), DBSEC-8 (страж SSL при старте); SCHEMA-1 решает схему и `GRANT`; CDC-3 решает роль Debezium.

## Revisit when

- Проверка владельца (DBSEC-7) показала, что DO не позволяет такую пару ролей или базу `bf`, что ACL `public` не даёт `migrator` и `app` работать по инварианту п. 3, или что CA не годится для `verify-ca`/`verify-full` по приватному хосту.
- Появилась третья роль (Debezium, CDC-3) или роль чтения (MCP, отчёты): состав ролей пересматривается.
- Решение об RLS в ADR-040 пересматривается: довод про `BYPASSRLS` уже снят этой записью.
