## Ubiquitous Language — Martin Fowler (martinfowler.com bliki, 31 Oct 2006) — https://martinfowler.com/bliki/UbiquitousLanguage.html
- Cited by README at line 325 in section "Domain Layer" to support: the domain layer should operate on domain objects described by a ubiquitous language.
- What it argues / defines:
  - Ubiquitous Language (term coined by Eric Evans in *Domain-Driven Design*) is the practice of building a common, rigorous language shared by developers and users/domain experts.
  - The language is based on the domain model used in the software; rigor is needed because software copes badly with ambiguity.
- Recommendations and rules:
  - Build the shared language from the domain model, and use the model-based language pervasively, not stopping until it "flows" (Evans's phrasing).
  - Use the language in conversations with domain experts: this is a key test of the model, and therefore of the domain model itself.
  - Let the language and the model change as the team's understanding of the domain deepens.
  - Domain experts should challenge terms or structures that are awkward or inadequate for expressing domain understanding.
  - Developers should watch for ambiguity or inconsistency in the language, because it will undermine the design.
- Definitions / vocabulary introduced: Ubiquitous Language → the common rigorous language above; Domain Model → the model the language is built on (linked to Fowler's EAA catalog).
- Examples, code idioms or patterns shown: none (short bliki entry).
- Trade-offs, caveats, anti-patterns: none stated beyond the ambiguity warning.

## Developing the ubiquitous language — Felipe De Freitas Batista (Medium, 27 Apr 2019; read via browser pane, WebFetch returned 403) — https://medium.com/@felipefreitasbatista/developing-the-ubiquitous-language-1382b720bb8c
- Cited by README at line 327 in section "Domain Layer" to support: a follow-up read on how to build the ubiquitous language the domain layer speaks.
- What it argues / defines:
  - Ubiquitous Language is modelled inside a bounded ("limited/delimited") context where the business terms and concepts are identified without ambiguity; whatever the software design, it must reflect a clear, modelled UL, and producing one requires understanding more of the business.
  - Code is the enduring expression of the UL (attributed to Vaughn Vernon): drawings, glossaries and other documentation that are hard to keep current should be expected to be abandoned.
- Recommendations and rules:
  - Characteristics to aim for: the UL must be expressed in the domain model; it unites the project team; it eliminates inaccuracies and contradictions coming from domain experts; it is not a business language imposed by domain experts, nor an industry jargon; it evolves over time rather than being settled in one meeting; concepts that are not part of the UL should be rejected.
  - Avoid (Evans's list as restated by the author): a missing common language that forces "translations" and produces wrong domain models; team members using terms differently without noticing; communicating without the UL even though one exists; technical abstractions in the domain model that domain experts do not understand; excluding domain experts from the model because it is "too abstract" (they are the only ones who can validate it).
  - Process: expect domain experts to disagree with each other, and resolve it with open discussion plus existing documents, dictionaries and standards; draw the domain on a whiteboard (formal or not); create a glossary of all terms with definitions; use Event Storming so experts and developers learn the business process in fast cycles; review and update the result in an agile way.
  - Every building block (aggregates, value objects, domain services, repositories, commands, events) must express the UL in code.
- Definitions / vocabulary introduced: Ubiquitous Language (as above); Event Storming → a workshop format for learning business processes quickly with experts and developers.
- Examples, code idioms or patterns shown (C#): requirement "the system must allow changing a Customer's email". Anti-example: class `People : Entity` with public setters and a generic `Update(name, email, ...)` that assigns whichever arguments are non-empty. UL-expressing version: class `Client : Entity` with private setters and a `ChangeEmail(string email)` method, i.e. the method name is the business operation.
- Trade-offs, caveats, anti-patterns: generic CRUD-style `Update` methods and public setters hide the business language; documentation other than code tends to rot.
- How it applies to a TypeScript/NestJS backend: name entity methods after business operations (`changeEmail`, `commitToSprint`) and keep property setters private; let command/event class names carry the same vocabulary.

## Class invariant — Wikipedia — https://en.wikipedia.org/wiki/Class_invariant
- Cited by README at line 335 in section "Entities" to support: entities must always protect their invariant (be valid at all times).
- What it argues / defines:
  - A class invariant (type invariant, object/representation invariant) is a constraint on the state of a class's objects that all methods must preserve; it is established during construction and holds between calls to public methods, so a method may reference the object without inaccurate assumptions about its state.
  - It is described as an essential component of design by contract; defining invariants helps programmers and testers catch more bugs.
- Recommendations and rules:
  - The invariant must hold after the constructor finishes and at the entry and exit of every public method; code inside a method may break it temporarily as long as it is restored before the public method returns.
  - A common pattern is for the constructor to throw an exception when the invariant is not satisfied; for mutable classes, re-check the invariant after each modification.
  - Public methods should also state preconditions and postconditions to help ensure the invariant (Java/JML example).
  - Invariants are inherited: the effective invariant of a class is its own conjoined with all parents' invariants, because descendants can access parent implementation data and could otherwise produce invalid instances; this risk is one reason to favour composition over inheritance.
  - Under concurrency, maintaining invariants generally requires a critical section (locking the state with a mutex).
- Definitions / vocabulary introduced: class invariant; design by contract (DbC); precondition/postcondition.
- Examples, code idioms or patterns shown: Ada generic `Stack` with `Type_Invariant` (length ≤ max depth, elements valid) and `Default_Initial_Condition`; D class `Date` with an `invariant()` block asserting day 1..31 and hour 0..23; Eiffel `DATE` with `valid_day`/`valid_hour` in an `invariant` clause and `require`/`ensure` on setters; C++ with the Loki library `GeoPoint::isValid()` (latitude ±90, longitude ±180) checked at method entry/exit; Java `Date` with JML `invariant`, `requires`, `ensures` annotations. Language support: native DbC in Eiffel, Ada, Dafny, D; assertions in Python, PHP, JavaScript, C++, Java; Loki (C++) and JML (Java) as libraries.
- Trade-offs, caveats, anti-patterns: inheritance can break encapsulation and let subclasses invalidate parent state; non-native approaches depend on external tooling; the article is flagged as needing more citations.
- How it applies to a TypeScript/NestJS backend: TS has no DbC, so the README's `validate()` method on entities, called from the constructor/factory and after each state-changing method, is the practical equivalent.

## Anemic Domain Model — Martin Fowler (bliki, 25 Nov 2003) — https://martinfowler.com/bliki/AnemicDomainModel.html
- Cited by README at line 341 in section "Entities" to support: entities should contain the domain business logic; putting it in services leads to an anemic domain model (domain services being the exception for logic that cannot live in one entity).
- What it argues / defines:
  - An anemic domain model looks like a domain model (objects named after domain nouns, rich relationships) but its objects have hardly any behaviour, being bags of getters and setters; all domain logic sits in service objects that compute and then update the model objects.
  - This is an anti-pattern because it contradicts the basic OO idea of combining data and process, and is really a procedural design (Transaction Scripts) in disguise.
  - Cost-benefit argument: you pay the full cost of a domain model (notably an O/R mapping layer) without getting its benefit, which only comes from using OO techniques to organise complex logic.
- Recommendations and rules:
  - Put domain logic (validations, calculations, business rules) in the domain objects; this does not conflict with layering that separates domain logic from persistence and presentation (that question is orthogonal).
  - Keep the Service Layer (Evans's "application layer") thin: it defines the jobs the software does and directs expressive domain objects, contains no business rules or knowledge, coordinates and delegates, and holds no business state (only task-progress state); the domain layer represents concepts, business situation and rules and is "the heart of business software" (quoting Evans via Fowler).
  - A Service Layer never justifies an empty domain model; its advocates use it together with a behaviourally rich model.
  - Treat growing behaviour in services as a warning sign; Evans's common mistake is giving up too easily on fitting behaviour into an appropriate object, which drifts toward procedural programming.
  - Prefer POJO domain models over technologies that encourage anemia (J2EE Entity Beans were his example).
- Definitions / vocabulary introduced: Anemic Domain Model; Transaction Script; Service Layer/Application Layer vs Domain (Model) Layer.
- Examples, code idioms or patterns shown: none (prose).
- Trade-offs, caveats, anti-patterns: domain models are not always the best tool; the critique targets the hybrid (domain-model shape with procedural logic), not the choice of Transaction Script per se; a likely cause is developers from a data background who never worked with a real domain model.

## Fail-fast — Wikipedia (the cited URL is a disambiguation page; content taken from the linked "Fail-fast system" article) — https://en.wikipedia.org/wiki/Fail-fast
- Cited by README at line 350 in section "Entities" to support: validate entities and other domain objects on creation and throw on the first failure.
- What it argues / defines:
  - A fail-fast system immediately reports at its interface any condition likely to indicate failure and usually stops normal operation rather than continuing a possibly flawed process; it checks state at several points so faults surface early; its responsibility is detection, with handling delegated to the next-higher level.
  - Rationale: contrasted with fault tolerance (redundancy, rerouting), which cannot save you from shared faults (ten database servers with the same bad auth configuration all fail together); lazy initialisation hides latent faults (a wrong path only fails on the first client request); early failure with rich diagnostics makes root causes easier to find; halting avoids irreversible or costly operations on bad state; the article claims it reduces software entropy and debugging effort.
- Recommendations and rules:
  - Objects should initialise their state in the constructor and throw on bad input, avoiding partially initialised objects that break later through setters; they can then be made immutable.
  - Functions should validate inputs in preconditions before doing any work.
  - Client-server code should validate requests on arrival, before routing them internally, and return errors for bad parameters.
  - Verify I/O resources and immutable configuration at startup rather than on first use.
  - A fail-fast iterator raises an error if the underlying collection changes during iteration; a state machine checks the initial state and halts on forbidden transitions, including those caused by bad external input.
- Definitions / vocabulary introduced: fail-fast system; fault-tolerant design (the opposing policy); related terms listed without explanation: crash-only software, fail-safe, fail-stop, fail-silent, design by contract, "failing badly" vs failing well; business meaning: the startup mantra "fail fast, fail often" (early, bold experiments to test viability).
- Examples, code idioms or patterns shown: as in the rules above (constructor validation, precondition checks, request validation at the boundary, fail-fast iterators).
- Trade-offs, caveats, anti-patterns: the core trade-off is more visible, immediate outages in exchange for avoiding hidden corruption; the article does not analyse availability cost and lacks inline citations.

## Factory method pattern — Wikipedia — https://en.wikipedia.org/wiki/Factory_method_pattern
- Cited by README at line 351 in section "Entities" to support: avoid no-arg constructors; accept and validate all required properties in a constructor or in a factory method such as `create()`.
- What it argues / defines:
  - A creational Gang-of-Four pattern that creates objects without specifying their exact classes: a factory method is called instead of a constructor, letting subclasses decide which class to instantiate.
  - It solves two problems: how subclasses can redefine the object that gets created, and how instantiation can be deferred to subclasses. Motivation: creation can be complex, duplicated, need information the caller lacks, or lack abstraction, so it is isolated in a dedicated method.
- Recommendations and rules:
  - Use it when callers should not depend on concrete classes, when subclasses should control which class is instantiated, and when the design must stay open for extension (open/closed principle).
  - Replace direct `new` calls in client code with the factory method; custom logic after creation can live there (the C# example sets a price after creating a phone).
  - Abstract Factory is often implemented with factory methods; Template Method may call factory methods; Joshua Bloch's "static factory method" is noted as related but with no direct GoF equivalent.
- Definitions / vocabulary introduced: Product (interface/base class), ConcreteProduct, Creator (holds logic that needs a Product and calls an abstract or default `factoryMethod()`), ConcreteCreator (overrides it).
- Examples, code idioms or patterns shown: maze game with abstract `Room` (`MagicRoom`/`OrdinaryRoom`), `MazeGame.makeRoom()` overridden in `MagicMazeGame`/`OrdinaryMazeGame` (Java, Python; the Java `MazeGame` constructor is a template method calling `makeRoom()`); C++23 `Creator::create(Id)` switching on an enum and returning `unique_ptr`; C# simple factory `PersonFactory.GetPerson(PersonType)` and `ProductAbstractFactory.MakeProduct()` overridden by `PhoneConcreteFactory`; PHP `CarFactory` interface with `makeCar()`. Real uses: ADO.NET `IDbCommand.CreateParameter`, Qt `QMainWindow::createPopupMenu`, `javax.xml.parsers` factories, DOM `Document.createElement()`.
- Trade-offs, caveats, anti-patterns: the pattern relies on inheritance (creation delegated to subclasses); the page has no dedicated criticism section.
- How it applies to a TypeScript/NestJS backend: the README's `static create(props)` on entities is the static-factory flavour: it generates the id, validates, and records creation events in one place while the constructor stays available for rehydration from persistence.

## Fluent interface — Wikipedia — https://en.wikipedia.org/wiki/Fluent_interface
- Cited by README at line 352 in section "Entities" to support: optional properties that need complex set-up can use a fluent interface or the Builder pattern.
- What it argues / defines:
  - A fluent interface is an object-oriented API whose design relies heavily on method chaining so that code reads like a domain-specific language; the term was coined by Eric Evans and Martin Fowler in 2005 (Fowler's bliki entry 20 Dec 2005), though the style predates it (Smalltalk method cascading in the 1970s, C++ iostream `<<`/`>>`, Garnet 1988, Amulet 1994).
  - Method chaining is the mechanism (each method returns the object it was called on); fluent design is broader: shaping the API, nesting and scoping so chains read like a DSL. A chain's context can be the previous return value, kept self-referential, or ended by a void return.
- Recommendations and rules:
  - A copy-on-write (immutable) variant clones the object, changes the clone and returns it; a base configuration can then fork into branches that share state without interfering (TypeScript `Kitten` example whose setters return new instances).
  - In strongly typed languages, subclasses must otherwise override every chained method to change its return type; use F-bounded polymorphism (generic self type) in Java or `this.type` in Scala to avoid it.
  - Python: returning `self` is discouraged by Guido van Rossum as unpythonic for operations that do not return new values (acceptable for string processing).
- Definitions / vocabulary introduced: fluent interface; method chaining; method cascading; copy-on-write fluent interface.
- Examples, code idioms or patterns shown: C# LINQ (`Where`/`OrderBy`/`Select`), setters returning `this`, NUnit `Assert.That`; C++ iostreams, a `Computer.Builder` with private constructor and `build()`, C++20 ranges with `|`; Java jMock, jOOQ, EasyMock, Swing `Packer`; JavaScript/TypeScript jQuery and `this`-returning class methods; Scala `this.type` and trait mixins; PHP `return $this;`; Swift `@discardableResult` setters returning `Self`.
- Trade-offs, caveats, anti-patterns: a fluent approach can defer missing-parameter errors to runtime, losing compile-time checks and conflicting with fail-fast design; breakpoints cannot be set inside a one-line chain (split lines, though some debuggers still point to the first line); with repeated calls it is unclear which one threw; logging mid-chain forces breaking the chain (C# extension methods can wrap logging); subclassing problem above. The fluent style is a common way to implement Builder; related ideas: command-query separation, named parameters, Unix pipelines.
- How it applies to a TypeScript/NestJS backend: type chained setters as returning `this` (polymorphic this type) so subclasses stay chainable; prefer the copy-on-write variant for value objects to keep them immutable.

## Builder — Refactoring.Guru (Design Patterns > Creational) — https://refactoring.guru/design-patterns/builder
- Cited by README at line 352 in section "Entities" to support: use Builder (or a fluent interface) for optional properties requiring complex set-up.
- What it argues / defines:
  - Builder is a creational pattern that constructs complex objects step by step, so the same construction code can produce different types and representations.
  - Problem: objects needing many fields and nested objects end up with a monstrous "telescoping" constructor (most parameters unused in most calls, e.g. pool parameters useless nine times in ten) or a subclass per configuration (hierarchy explosion for houses with porches, pools, heating...); linked to the Long Parameter List smell.
- Recommendations and rules:
  - Extract construction code from the product into builder objects that expose steps (`buildWalls`, `buildDoor`); clients call only the steps they need; the builder must not expose the product while it is being built.
  - Several builders can implement the same steps differently (wood/glass house, stone/iron castle, gold/diamond palace), which requires a common builder interface.
  - Optionally add a Director that owns the order of step calls and reusable construction routines; the client associates a builder with the director, starts construction, and fetches the result from the builder (the director is not coupled to concrete products).
  - Applicability: eliminate telescoping constructors (overloads like `Pizza(size)`, `Pizza(size, cheese)`, `Pizza(size, cheese, pepperoni)`); build different representations with similar steps; build Composite trees or other recursive structures (steps can be deferred or recursive); prevent clients from fetching incomplete results.
  - Implementation steps: define the common steps for all representations; declare them in a base builder interface; one concrete builder per representation with its own result-fetching method (it cannot be in the interface unless all products share a hierarchy); consider a director; the client creates both and passes the builder to the director (constructor or per-method); fetch the result from the director only if products share an interface, otherwise from the builder.
- Definitions / vocabulary introduced: Builder interface; Concrete builder; Product (products need not share a class hierarchy); Director; Client.
- Examples, code idioms or patterns shown (pseudocode): `Car` and `Manual` products; `Builder` interface with `reset()`, `setSeats()`, `setEngine()`, `setTripComputer()`, `setGPS()`; `CarBuilder` whose constructor calls `reset()` and whose `getProduct()` returns the car and resets (common practice, not mandatory); `CarManualBuilder` implementing the same steps as documentation; `Director.constructSportsCar(builder)` calling reset, seats=2, SportEngine, trip computer, GPS; the application runs the director with each builder and retrieves `Car` or `Manual` from the builder.
- Trade-offs, caveats, anti-patterns: pros: step-by-step/deferred/recursive construction; reuse of construction code across representations; Single Responsibility (construction isolated from business logic). Con: several new classes increase overall complexity. Relations: designs often start with Factory Method and evolve to Abstract Factory/Prototype/Builder; Abstract Factory returns products immediately whereas Builder runs extra steps first; Builder suits Composite trees; can combine with Bridge (director as abstraction, builders as implementations); builders can be Singletons.

## DDD Aggregate — Martin Fowler (bliki, 23 Apr 2013) — https://martinfowler.com/bliki/DDD_Aggregate.html
- Cited by README at line 371 in section "Aggregates" to support: the definition of an aggregate as a cluster of domain objects treated as a single unit.
- What it argues / defines:
  - A DDD aggregate is a cluster of domain objects that can be treated as a single unit (example: an order and its line items, which are separate objects but useful to handle together).
  - One member is the aggregate root; references from outside the aggregate go only to the root, which lets the root protect the integrity of the whole.
- Recommendations and rules:
  - External references point only to the aggregate root, never to internal members.
  - Aggregates are the basic unit of data transfer and storage: load and save whole aggregates, not parts individually.
  - Transactions must not cross aggregate boundaries.
- Definitions / vocabulary introduced: Aggregate; Aggregate root. Aggregates are domain concepts (order, clinic visit, playlist) rather than generic collection classes, and often contain several collections plus simple fields; the word "aggregate" in UML and elsewhere means something different.
- Examples, code idioms or patterns shown: order + line items (prose only).
- Trade-offs, caveats, anti-patterns: the entry is brief and gives no sizing or consistency guidance beyond the transaction rule; it points readers to Evans's book; repositories are not mentioned.

## Database transaction — Wikipedia — https://en.wikipedia.org/wiki/Database_transaction
- Cited by README at line 378 in section "Aggregates" to support: any operation on an aggregate must be transactional (everything saved/updated/deleted, or nothing).
- What it argues / defines:
  - A transaction is a unit of work in a DBMS (or similar system) treated coherently and reliably, independent of other transactions; it may span one or many operations (example: a bank transfer that debits one account and credits another as one unit).
  - Two purposes: reliable recovery from failures that would otherwise leave operations half-finished and data inconsistent; isolation between concurrently running programs whose interleaved results could otherwise be wrong.
- Recommendations and rules:
  - ACID: atomicity (all-or-nothing), consistency (existing constraints respected), isolation (no disruption of concurrent transactions), durability (committed changes reach persistent storage).
  - A transactional database brackets a set of operations between begin and commit; all writes take effect together or not at all.
- Definitions / vocabulary introduced: nested transactions (sub-transactions started within a transaction); multi-level transactions (sub-transactions at different layers of the stack, e.g. database engine and OS); distributed transactions (ACID across multiple nodes/participants such as databases, storage managers, file systems and messaging systems, usually with a coordinator); transactional filesystems (Reiser4; NTFS since Windows Vista supports distributed transactions; Warp Transactional Filesystem as research).
- Examples, code idioms or patterns shown: the bank transfer; no SQL syntax is given.
- Trade-offs, caveats, anti-patterns: the article is flagged for citations and does not cover rollback mechanics or object databases.

## Understanding Aggregates in Domain-Driven Design — Alireza Rahmani Khalili (DZone, 8 Jul 2020; read via browser pane, WebFetch returned 403) — https://dzone.com/articles/domain-driven-design-aggregate
- Cited by README at line 396 in section "Aggregates" as further reading on aggregate design.
- What it argues / defines:
  - Associations between domain objects are the main source of complexity and confusion; without simplifying techniques an object model's association network grows out of control and loading one object can drag large clusters into memory. The domain model exists to support invariants and use cases, not UIs, and is not the data model, so its associations must be communicative, applicable and constrained.
  - Designing relationships is as important as designing the objects; the questions are where to draw the line on references, how to persist referenced entities, and whether updates cascade.
  - Aggregates are one or more entities and value objects, grouped by domain invariants that change together, treated as a unit for data changes and considered as a whole for consistency; every aggregate has a root (an aggregate can be a single object, which is then the root); the root is the entity chosen as the gateway that coordinates all changes, prevents inconsistent states, and upholds invariants by delegating to the other members; an aggregate is a conceptual whole that acts as consistency and concurrency boundary and is always in a valid state.
- Recommendations and rules:
  - Base aggregate boundaries on domain invariants (business rules that must always be consistent); the consistency of everything outside the boundary is irrelevant to the aggregate.
  - Modify an aggregate with its invariants completely consistent within a single transaction; aggregates are synonymous with transactional consistency; one transaction per aggregate instance is a strict-sounding rule of thumb that should be followed in most cases, because the more aggregates one transaction modifies the greater the chance of concurrency failure.
  - Root heuristics: if deleting the object should cascade to others, it is probably a root; ask whether the object makes sense detached from its parent; ask whether an aggregate makes sense without some other entity (if yes, that entity should probably be its own root, otherwise part of an existing aggregate).
  - Keep entities inside an aggregate highly cohesive and aggregates loosely coupled; prefer putting behaviour on value objects rather than entities, since identity is already a burden for entities.
  - Treat boundaries as iterative: change them as domain knowledge grows; do not expect to find them right away.
  - Do not let the data model shape aggregates: database has-a relationships exist for referential integrity and reporting; include an object in an aggregate only if it is required to define the aggregate's behaviour, not merely related.
  - Aim for small aggregates: in the author's projects most aggregates held one or two entities and never more than three (value objects not counted); single-entity aggregates are fine, so do not gather entities artificially.
  - Make associations unidirectional (ORMs make bidirectional associations too easy); qualify associations by adding constraints to reduce traversal work (e.g. a post's approved comments only); reporting requirements that need all comments or multidirectional relations are a separate concern outside the domain model.
- Definitions / vocabulary introduced: aggregate; aggregate root; transactional vs eventual consistency; qualified association.
- Examples, code idioms or patterns shown: online retailer where `Customer` is the root and `Address` is an entity inside the aggregate because shipment requires an address, versus an online-webinar system where the customer aggregate is a single entity and an address is optional (needed only for a physical invoice): same has-a relationship, different invariants, different boundaries.
- Trade-offs, caveats, anti-patterns: a single big aggregate looks simpler but is harder to keep consistent and causes conflicts when several transactions update parts of it concurrently; boundaries are a trade-off between model simplicity and performance; unnecessary associations kill performance and consistency.

## What Are Aggregates In Domain-Driven Design? (and the rest of the series) — James Hickey (jamesmichaelhickey.com, Apr–Jun 2020) — https://www.jamesmichaelhickey.com/domain-driven-design-aggregates/

Diagrams are images and not recoverable; the articles have no real code except where noted.
- What it argues / defines:
  - An aggregate is a self-contained "bubble" of business data and behaviour that can be worked on independently; it is not a graph of entities, not merely a behaviour-rich object, and not a set of entities to dump into tables. Quoted from Fowler: aggregates are "the basic element of transfer of data storage", and transactions should not cross aggregate boundaries.
  - Invariant (via Vernon): a business rule that must always be consistent; true invariants need transactional consistency, other rules can be eventually consistent. The aggregate is the gateway ("bouncer") for all operations on what is inside it, so invariant logic is not scattered.
  - Logical data corruption: data that is inconsistent at the business level (an approved timesheet whose approval-history rows were never written because the code crashed outside a transaction), as opposed to physical corruption.
  - Collaborative domains: domains where the same resource is changed by several users at once; a consistency boundary alone does not stop two concurrent operations from both succeeding when they conflict.
- Recommendations and rules:
  - Model from behaviour, not from the database schema; CRUD-flavoured language is a red flag; let domain rules drive aggregate discovery (the discovered aggregates often differ from the initial expectation).
  - Use aggregates to simplify unwieldy models, isolate complex rules, limit memory use (a team with ~500 members would otherwise load every member's data), and absorb unforeseen requirements.
  - Rule of thumb #1 (Vernon): model true invariants as consistency boundaries; invariants, not entities/fields/data, should drive boundaries; cross-aggregate rules are allowed but should be eventually consistent; revisit boundaries when invariants change.
  - Reference other aggregates by id (foreign-key-like `TeamMemberId`); keep per-context views of a concept (a `Member` view in the Team bubble, another in the Project bubble holding the role) and an authoritative model elsewhere; prefer separate id classes per context (team.MemberId, project.MemberId) and a shared kernel only for truly shared logic, because less sharing means more decoupling.
  - Never use write-side aggregates as read models: reads get separate queries and models.
  - Persistence: data duplication is a problem, conceptual duplication is not (a team-specific email address and a member's general email are distinct concepts even when equal); relational persistence suffers impedance mismatch (rows must be iterated to rebuild the object graph; separate tables plus a composite team/team-member table); a document store can hold one aggregate per document with near-zero mismatch, but cross-aggregate queries then need CQRS, a relational query model, or messages that let each part cache the values it needs; event-sourced persistence stores all events of the whole aggregate (including inner entities) in one stream per aggregate instance (EventStoreDB encourages this); do not force a relational design into a document database and do not assume document stores are inherently simpler, cheaper or more scalable.
  - Do not tie one aggregate to more than one database; consistency across databases or systems needs a saga/process manager (a long-running business transaction without ACID guarantees) or moving the data into one database.
  - Concurrency: pessimistic locking (lock the whole resource, like an Excel file on a network drive) performs poorly and is brute force; prefer optimistic concurrency: read the current version, check it on write, fail the operation if the version is stale, then retry if the work still makes sense against the newer data; works for relational, document and event stores.
  - Cross-aggregate checks (e.g. a `GroupCluster` that must verify a person and group share the same tenant) can use a domain service that fetches the other aggregates, a distributed process when the data is in another bounded context, or an asynchronous check after persisting with undo/notify on failure; the need may also signal that the aggregate stores the wrong values.
  - Unit testing with DDD: test domain behaviour and invariants directly on the objects, not through data access; when behaviour spans aggregates or bounded contexts, do not test the whole collaboration — use domain events and test that the aggregate emitted the right event; one unit test per step of a multi-step process; testing is slower up front but forces rigorous thinking about requirements, pushes toward modular design, and gives a refactoring safety net.
- Definitions / vocabulary introduced: bubble (aggregate), consistency boundary, true invariant, logical data corruption, collaborative domain, data vs conceptual duplication, impedance mismatch, optimistic vs pessimistic concurrency.
- Examples, code idioms or patterns shown: teams/members/projects model (members in many teams, projects orphaned for a period, roles differ per project) split into a Team bubble, a Project bubble and an authoritative TeamMember model; JSON documents `Team { teamId, name, teamMembers: [{ teamMemberId, memberId, role, emailAddress }] }` and `Member { memberId, fullName, emailAddress, phone }`; timesheet with a 40-hour cap where two managers each add 8 hours to different days starting from 32 and both succeed (48 hours) unless the whole timesheet is the boundary; video-game health reaching 0 must kill immediately (true invariant) vs an insurance application's credit-score check that can be done later (eventually consistent); library analogy (rent one giant volume → no contention problems but everyone else blocked; per-chapter rentals → low contention but costly cross-referencing); EventStoreDB C# `AppendToStreamAsync(stream, expectedVersion, events)`; SQL `UPDATE ... WHERE RowVersion = @expected` and treat zero affected rows as a failed transaction; C#-style tests `new Order(emptyCart).CanPlaceOrder == false` and `order.PlaceOrder(); DomainEvents.GetRaised<OrderPlaced>().OrderId == order.OrderId`.
- Trade-offs, caveats, anti-patterns: naive cascade deletes that do not match business reality; a composite table per new relationship; loading all members of a huge team; storing fields an aggregate does not need; large aggregates → contention, tiny aggregates → weak cross-object consistency; aggregates do not remove contention or locking issues by themselves; retries are safe only when the operation still satisfies the rules against the updated state; member deletion "depends" (deactivate rather than delete, soft-delete some records and hard-delete others; propagate with events handled by application-layer listeners that drive domain operations).
- How it applies to a TypeScript/NestJS backend: the README follows the same choices — ids as value objects referencing other aggregates, aggregate-root base class collecting domain events, repositories that persist one aggregate per transaction, and read models separate from write models (CQRS).

## Effective Aggregate Design Part I: Modeling a Single Aggregate — Vaughn Vernon (dddcommunity.org essay, 2011, CC BY-ND 3.0; PDF fetched and text extracted locally) — https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_1.pdf
- Cited by README at line 398 in section "Aggregates" as the foundational reading on aggregate design.
- What it argues / defines:
  - Among all DDD tactical guidance the aggregate pattern is one of the least understood; the questions people ask (is it just a cluster of related objects? is there a size limit? can associations be navigated and modified deeply?) are all answered by understanding invariants and the consistency boundary.
  - Two failure modes: designing for compositional convenience and making aggregates too large, or stripping them bare and failing to protect true invariants; the business rules must decide.
  - Worked example: ProjectOvation, a multi-tenant SaaS Scrum tool (products, product owners, teams, backlog items, releases, sprints; Scrum terms seed the ubiquitous language; each subscribing organisation is a tenant). The Java/Hibernate team with little DDD experience makes the mistakes the essay dissects (the material applies equally to C#/NHibernate).
- Recommendations and rules (the essay's explicit rules, with reasoning):
  - Rule: Model true invariants in consistency boundaries. An invariant is a business rule that must always be consistent; the relevant kind of consistency is transactional (immediate and atomic), as opposed to eventual. Example invariant `c = a + b`: if a = 2 and b = 3 then c must be 5, so a boundary is drawn around a, b, c (`AggregateType1 { int a; int b; int c; operations... }`); everything inside the boundary obeys the invariants no matter which operation runs, and the consistency of everything outside is irrelevant to the aggregate, so "aggregate" is synonymous with "transactional consistency boundary". With a typical persistence mechanism one transaction (possibly handled by a unit of work) manages consistency; when it commits everything inside one boundary must be consistent. A properly designed aggregate can be modified in any way the business requires with its invariants fully consistent in a single transaction, and a properly designed bounded context modifies only one aggregate instance per transaction in all cases; aggregate design cannot be reasoned about without transactional analysis. One-instance-per-transaction is a rule of thumb and the goal in most cases, because it addresses the very reason to use aggregates. Consequently the UI should concentrate each request on a single command on a single aggregate instance; requests that try to do too much force the application to modify multiple instances. Aggregates are about consistency boundaries, not about designing object graphs; real invariants are usually less demanding than feared, which makes small aggregates possible.
  - Rule: Design small aggregates. Even if every transaction succeeded, a large cluster limits performance and scalability: with many tenants, products accumulate thousands of backlog items, releases and sprints; adding one backlog item to a years-old product would load thousands of items into memory (even with Hibernate lazy loading, and worse without it), and scheduling an item for release or committing it to a sprint would load several large collections; the 0..* multiplicities will almost never be zero and keep growing; multiplied across hundreds or thousands of tenants this never performs or scales. "Small" does not mean an aggregate of only an id and one attribute (unless that is truly all it needs); it means the root entity plus the minimal number of attributes and value-typed properties, where the correct minimum is the ones that must be consistent with each other even if domain experts never state it as a rule (a Product's `name` and `description` change together, so they belong in one aggregate; changing only one is a spelling fix). A value-typed property holds a reference to a value object, as distinct from a simple String/number attribute (Ward Cunningham's Whole Value). Before modelling a contained part as an entity, ask whether it must change over time or can be completely replaced; replaceable parts should be value objects, and many entity parts can be refactored to values this way. Favouring values does not make the aggregate immutable, because the root mutates when a value-typed property is replaced. Advantages of value parts: they can be serialised with the root (entities usually need separately tracked storage, e.g. SQL joins in Hibernate; reading one table row is much faster), they are smaller and safer (fewer bugs), and immutability makes unit tests easier. Data point: on a financial-derivatives project using Qi4j, Niclas Hedhman's team designed about 70% of aggregates as a single root entity with value-typed properties and the remaining 30% with only two or three entities in total; not a universal split, but evidence that a high percentage of aggregates can be a single entity. The DDD book's purchase-order example (sum of line items must not exceed a maximum total, tricky when users add items concurrently) is a legitimate multi-entity case, but most invariants are simpler. Smaller aggregates also perform and scale better and are biased toward transactional success (commit conflicts are rare), which makes the system more usable; when a true consistency rule appears, add a few entities or a collection, but keep pushing the size down.
  - Don't trust every use case: detailed use-case specifications from business analysts lack the perspective of the close-knit modelling team and must be reconciled with the model; a use case that modifies multiple aggregate instances must be examined to see whether that spans several transactions (fine — a user goal is not synonymous with a transaction) or one (be skeptical; it may not reflect the true aggregates). Trying to keep multiple instances consistent in one transaction may reveal a missed invariant, leading to folding the aggregates (or parts of them) into a new concept with a new name; but if that produces a large cluster, the answer is instead eventual consistency between aggregates: rewrite (or re-imagine) the use case to specify eventual consistency and the acceptable update delay. With three users contending for the same two aggregate instances, some commit-order permutations fail two of the three requests.
- Definitions / vocabulary introduced: aggregate; invariant; consistency boundary; transactional vs eventual consistency; false invariants (artificial constraints imposed by developers rather than real business rules); value-typed property; large-cluster aggregate; user goal vs transaction; CQS command vs query contracts.
- Examples, code idioms or patterns shown (Java): first attempt — `Product extends ConcurrencySafeEntity` holding `Set<BacklogItem>`, `Set<Release>`, `Set<Sprint>` plus description, name, ProductId, TenantId, with consistency rules such as "a backlog item committed to a sprint must not be removable", driven by reading "Products have backlog items, releases, and sprints" as composition. It failed in multi-user use: aggregates use optimistic concurrency (a version number incremented on change and checked on save; a stale client version is rejected) to avoid database locks, so when Bill plans a backlog item (Product version 1 → 2) and Joe schedules a release based on version 1, Joe's commit fails although the two actions are logically unrelated; with more users (sprint planning meetings) failing all but one request is unacceptable. Disabling Hibernate's optimistic-lock on the collections would remove the domino failures (there is no invariant on the number of items), but the cluster would still grow out of control. Second attempt — four aggregates (Product, BacklogItem, Release, Sprint) associated by a common `ProductId`; the `planBacklogItem`, `scheduleRelease`, `scheduleSprint` methods change from void CQS commands that add to a collection into query-style factories returning the new aggregate instance; the transactional application service `ProductBacklogItemService.planProductBacklogItem(...)` loads the product via `productRepository.productOfId(new TenantId(..), new ProductId(..))`, calls `product.planBacklogItem(...)`, and `backlogItemRepository.add(plannedBacklogItem)`, so any number of items, releases and sprints can be created by simultaneous requests — the transaction failure is modelled away.
- Trade-offs, caveats, anti-patterns: multiple small aggregates are less convenient for client consumption than one big graph; the large cluster was driven by false invariants and compositional convenience to the detriment of transactional success, performance and scalability; persistence mechanisms' default concurrency behaviour is important to protecting invariants from concurrent change, so do not casually turn it off; "Products have" in the ubiquitous language does not imply object composition.
- How it applies to a TypeScript/NestJS backend: the README's rule set (small aggregates, root plus value objects, ids as references, one aggregate per transaction, UUID identity) is a direct restatement of these rules; command handlers in `application` play the role of the transactional application service that loads one aggregate, invokes one command, and saves it.

## Effective Aggregate Design Part II: Making Aggregates Work Together — Vaughn Vernon (dddcommunity.org essay, 2011; PDF fetched and text extracted locally) — https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf
- Cited by README at line 399 in section "Aggregates" for how aggregates reference each other and for eventual consistency.
- What it argues / defines:
  - Holding a reference from one aggregate to the root of another is allowed by the DDD book, but it does not place the referenced aggregate inside the referencing one's consistency boundary: there are still two (or more) aggregates. A direct object association (`BacklogItem` with a `private Product product` field) therefore implies: (1) the referencing and referenced aggregates must not be modified in the same transaction, only one of them; (2) modifying multiple instances in one transaction strongly indicates wrong consistency boundaries, i.e. an undiscovered concept of the ubiquitous language; (3) if fixing that would produce a large-cluster aggregate, use eventual consistency instead of atomic consistency. Holding no references at all would prevent the temptation but is overly limiting, since models always need associations.
- Recommendations and rules:
  - Rule: Reference other aggregates by identity. Prefer references to external aggregates by their globally unique identity rather than by object "pointer" (`private ProductId productId;`). Aggregates with inferred references are automatically smaller because nothing is eagerly loaded; instances load faster and take less memory, which also reduces allocation overhead and garbage collection.
  - Model navigation: identity references do not prevent navigation. Using a repository from inside an aggregate for look-up (the "disconnected domain model", a form of lazy loading) is possible, but the recommended approach is for a repository or domain service to look up dependent objects ahead of invoking the aggregate behaviour, with an application service controlling it and then dispatching to the aggregate; this frees the aggregate from depending on repositories or domain services. Referencing multiple aggregates in one request still gives no licence to modify more than one of them.
  - Serving UI views may require several repositories in one use case; if query overhead hurts, consider CQRS (Dahan, Fowler, Young) or a balance between inferred and direct references.
  - Scalability and distribution: because aggregates reference by identity, their persistent state can be repartitioned continuously for almost-infinite scalability (Pat Helland's "Life Beyond Distributed Transactions"; what Helland calls an entity is an aggregate by another name — a unit of composition with transactional consistency); NoSQL stores provide the scale-aware lower layer; identity references also let distributed bounded contexts form associations from afar: message-based domain events carrying aggregate identities are sent around the enterprise and subscribers in foreign contexts use the identities in their own models (Helland's two-party activities; multi-party in publish-subscribe terms); transactions across distributed systems are not atomic, so the systems reach consistency eventually.
  - Rule: Use eventual consistency outside the boundary. The DDD book (p. 128) states that any rule spanning aggregates is not expected to be up to date at all times and is resolved through event processing, batch processing or other mechanisms within some specific time. So if a command on one aggregate instance requires additional business rules to execute on other aggregates, use eventual consistency; accepting that all instances in a large, high-traffic enterprise are never completely consistent helps accept it at small scale too. Ask domain experts whether they can tolerate a delay between modifying one instance and the others; they are often more comfortable with delays (seconds, minutes, hours, even days) than developers, who are indoctrinated with an atomic-change mentality, because business delays were normal before automation.
  - Mechanism: an aggregate command method publishes a domain event that is delivered in time to one or more asynchronous subscribers; each subscriber retrieves a different corresponding aggregate instance and executes behaviour on it in its own transaction, obeying one-instance-per-transaction. If a subscriber's modification fails through concurrency contention, it withholds acknowledgement so the message is redelivered and retried in a new transaction until consistency is achieved or a retry limit is reached; on complete failure, compensate or at least report for intervention.
  - Ask whose job it is (a guideline from discussion with Eric Evans): when examining a use case, ask whether it is the job of the user executing it to make the data consistent. If so, try to make it transactionally consistent while still obeying the other aggregate rules; if it is another user's job or the system's job, let it be eventually consistent. Classic DDD users lean to transactional consistency and CQRS users to eventual consistency, but both are only technical leanings; this question exposes the real invariants and deepens domain understanding, though other forces may still weigh in.
  - Reasons to break the rules (modify multiple instances in one transaction only with good reason): (1) User-interface convenience — batch creation of several backlog items with shared properties in one gesture (`planBatchOfProductBacklogItems` loops over descriptions, calling `product.planBacklogItem(...)` and `backlogItemRepository.add(...)`); no invariant problem because the created objects are full aggregates maintaining their own invariants and batch creation is semantically identical to repeated single creation. Udi Dahan's alternative: avoid special batch application services and instead batch multiple logical messages in one physical message through a message bus, which processes them in one transaction, all succeeding or failing together. (2) Lack of technical mechanisms — eventual consistency needs out-of-band processing (messaging, timers, background threads); without any such mechanism, and with rigid specifications that forbid new domain concepts, project dynamics may force multi-aggregate transactions; do not decide hastily, and beware of sliding back to large clusters. User-aggregate affinity (workflows where only one user works on a set of instances at a time) makes the compromise sounder, since it prevents most invariant violations and collisions, with optimistic concurrency still protecting each aggregate and rare conflicts being straightforward to recover from. (3) Global transactions — legacy technology or enterprise policy may mandate two-phase-commit transactions; even then, avoid modifying multiple aggregate instances in the local bounded context to limit contention in the core domain; the downside is that such systems never scale as they could without 2PC and immediate consistency. (4) Query performance — sometimes direct object references ease repository query performance; weigh against size and performance trade-offs (an example is deferred to Part III).
  - Adhering to the rules: UI decisions, technical limits and stiff policies may force compromises, but do not search for excuses; in the long run following the rules gives consistency where necessary plus optimally performing, highly scalable systems. Summary resolution: small aggregates around true invariants, references by identity, eventual consistency for cross-aggregate dependencies.
- Definitions / vocabulary introduced: reference by identity; disconnected domain model; user-aggregate affinity; two-party vs multi-party activities; compensation; "whose job is it" tie-breaker.
- Examples, code idioms or patterns shown (Java): `BacklogItem extends ConcurrencySafeEntity { private ProductId productId; }`; application service `assignTeamMemberToTask(tenantId, backlogItemId, taskId, teamMemberId)` loading the backlog item from `backlogItemRepository.backlogItemOfId(...)`, the team from `teamRepository.teamOfId(backlogItem.tenantId(), backlogItem.teamId())`, then `backlogItem.assignTeamMemberToTask(new TeamMemberId(..), ofTeam, new TaskId(..))`; `BacklogItem.commitTo(Sprint)` publishing `new BacklogItemCommitted(tenantId, backlogItemId, sprintId)` through `DomainEventPublisher.instance().publish(...)`; the subscriber eventually creates a `CommittedBacklogItem` so the `Sprint` records the commitment with its own `ordering` attribute (distinct from Product's `ProductBacklogItem` and Release's `ScheduledBacklogItem` orderings and from the item's `BusinessPriority`), avoiding a meaningless bidirectional association; batch planning service as above.
- Trade-offs, caveats, anti-patterns: direct references invite multi-aggregate transactions and eager loading; identity-only references make view assembly less convenient; eventual consistency needs infrastructure and retry/compensation handling; global transactions cap scalability; the whole essay is a set of rules of thumb to be broken only deliberately.
- How it applies to a TypeScript/NestJS backend: the README's domain events (collected on the aggregate root, published by the repository on persist, handled by application-layer handlers) plus integration events over a broker implement exactly this mechanism; references between modules are by id value objects; the "whose job is it" question is the practical test for deciding between a single-transaction command handler and an event handler.

## Why soft deletes are evil and what to do instead — James Halsall (jameshalsall.co.uk) — https://jameshalsall.co.uk/posts/why-soft-deletes-are-evil-and-what-to-do-instead
- Cited by README at line 418 in section "Domain Events" to support: why an audit log (built from domain events) is a better tool than soft deletes.
- What it argues / defines:
  - Soft deletes (marking records deleted so the deletion is easily reversible) seemed like "the right way" to the author, but they bypass the database, which is the best tool for managing relationships between data, and move cascading-delete responsibility into the application layer, which is not designed for it; the database has no native soft-delete support, so the application must do all the work.
  - Soft deletes without cascading leave associated records (users of a soft-deleted group) undeleted as an unintended side effect rather than a deliberate outcome.
- Recommendations and rules:
  - Let the database hard-delete through foreign keys and cascading operations, because it is the best tool for the job.
  - Keep the two real benefits of soft deletes (accountability for actions, ease of data recovery) with an audit log: the delete operation fires a generic deletion event; an audit listener persists an `AuditEntry` containing a serialised copy of the removed data (objects via an ORM, or records), the original object's class name (so it can be restored), the user who performed the operation, and the time.
  - The domain layer then no longer cares whether deletes are hard or soft; producing an audit trail is good practice anyway.
- Definitions / vocabulary introduced: soft delete; audit entry.
- Examples, code idioms or patterns shown (PHP, code blocks not present in the fetched text): a naive `GroupManager::delete()` that also deletes the group's users (breaks the Single Responsibility Principle and loads all users into memory); an event-based variant with a dedicated "group deleted" listener; the audit-manager listener described above.
- Trade-offs, caveats, anti-patterns: event-based cascading still pollutes domain logic and adds code, and a removed or forgotten listener leaves data that should have been deleted; hard deletes alone make records unrecoverable; the author admits the example is not perfectly SOLID and that the question is "not always so black and white", without listing the exceptions.

## Unit of Work — java-design-patterns.com (iluwatar) — https://java-design-patterns.com/patterns/unit-of-work/
- Cited by README at line 420 in section "Domain Events" to support: wrapping a whole flow (including changes made by domain-event handlers) in one transaction, e.g. with a Unit of Work.
- What it argues / defines:
  - Intent: maintain a list of objects affected by a business transaction and coordinate writing out the changes and resolving concurrency problems (Fowler's definition, summarised). In plain words: track object changes during a transaction and commit them together as one unit.
  - Real-world analogy: a librarian records borrows and returns during the day and updates the inventory once at closing, keeping it consistent with fewer updates.
- Recommendations and rules:
  - Use when several database operations must run as one transaction and stay consistent, when business-object changes must be tracked and saved in a coordinated way, and when working with ORMs such as Hibernate (which implement it).
  - Benefits: data integrity through transaction management; fewer database calls by batching; transaction management decoupled from business logic.
- Definitions / vocabulary introduced: Unit of Work; related patterns Identity Map (load each object once per transaction), Repository (pairs well with it), Transaction Script.
- Examples, code idioms or patterns shown (Java "arms dealer"): `Weapon(id, name)`; interface `IUnitOfWork<T>` with constants INSERT/DELETE/MODIFY and methods `registerNew`, `registerModified`, `registerDeleted`, `commit`; `ArmsDealer` keeps a `Map<String, List<Weapon>>` context keyed by operation and a `WeaponDatabase`; `commit()` returns early on empty context, then runs inserts, modifications and deletes in that order against the database; client registers a new hammer, a modified trident and a deleted sword, then commits once.

- How it applies to a TypeScript/NestJS backend: the README does not implement a full UoW; instead the command handler opens one database transaction and passes the transaction connection to repositories (so domain-event handlers' writes join it), which achieves the same all-or-nothing effect.

## Eventual consistency — Wikipedia — https://en.wikipedia.org/wiki/Eventual_consistency
- Cited by README at lines 421 and 449 in sections "Domain Events" and "Integration Events" to support: when a single transaction is unaffordable (contention) or impossible (across services), accept eventual consistency.
- What it argues / defines:
  - A consistency model used in distributed computing to achieve high availability: if no new updates are made to an item, eventually all reads of it return the last updated value; also called optimistic replication; originated in early mobile-computing work (Bayou, Terry et al. 1995; Vogels 2008/2009); a system that reached this state has achieved replica convergence. It is a weak guarantee: stronger models such as linearizability are trivially eventually consistent.
  - BASE (contrasted with ACID; Pritchett 2008, Bailis & Ghodsi 2013): basically available (concurrent access at all times without waiting on others' transactions), soft state (values may change without input until convergence), eventually consistent.
- Recommendations and rules:
  - Convergence needs anti-entropy (exchanging versions/updates between servers) and reconciliation (choosing a final state after concurrent updates); strategies: last writer wins (widespread), a user-specified conflict handler, first writer wins where LWW is unacceptable; timestamps and vector clocks detect concurrent updates.
  - Reconciliation timing (before the next read): read repair (slows reads), write repair (slows writes), asynchronous repair (outside both); the choice depends on the application.
  - Strong eventual consistency adds a safety guarantee (any two nodes that received the same unordered set of updates are in the same state), commonly achieved with CRDTs (Shapiro et al. 2011).
- Definitions / vocabulary introduced: eventual consistency; optimistic replication; replica convergence; BASE; anti-entropy; reconciliation; read/write/asynchronous repair; strong eventual consistency; CRDT.
- Examples, code idioms or patterns shown: none beyond the strategies above.
- Trade-offs, caveats, anti-patterns: eventual consistency gives liveness without safety, so any intermediate value may be observed before convergence, unlike single-threaded programming; it adds complexity to distributed applications; wrong consistency assumptions cause subtle bugs that surface only under network failure or high concurrency; Pessach (2013): lower load and higher availability versus greater cognitive complexity for developers and users.

## Mediator — Refactoring.Guru (Design Patterns > Behavioral) — https://refactoring.guru/design-patterns/mediator
- Cited by README at line 423 in section "Domain Events" to support: an in-memory domain-event bus can borrow ideas from the Mediator (or Observer) pattern.
- What it argues / defines:
  - Mediator (also Intermediary, Controller) reduces chaotic dependencies between objects by forbidding direct communication and forcing collaboration through a mediator object.
  - Problem example: a profile-editing dialog whose controls affect each other (ticking "I have a dog" reveals a dog-name field; the submit button validates every field); logic embedded in controls couples them so they cannot be reused elsewhere and a change ripples through many others.
  - Air-traffic-control analogy: pilots coordinate through the tower, not with each other; the tower does not fly the planes, it only enforces constraints.
- Recommendations and rules:
  - Components hold a reference typed to the mediator interface (usually a single `notify(sender, event)` method) and never to concrete peers; on a significant event a component only notifies the mediator, which identifies the sender and decides what to trigger; each side treats the other as a black box.
  - The concrete mediator holds references to all components and may manage their lifecycle (resembling a Factory or Facade); in the dialog example the dialog class itself can serve as mediator since it already knows its elements.
  - Use when classes are tightly coupled to many others and hard to change, when you want all inter-class relations extracted into one place, when a component cannot be reused because of its dependencies, or when you keep subclassing components just to reuse behaviour in new contexts; new collaboration patterns are added as new mediators without touching components.
  - Implementation steps: identify the tightly coupled group; declare the mediator interface and protocol; implement the concrete mediator storing all component references; optionally let it create/destroy components; give each component a mediator reference (constructor); replace component-to-component calls with mediator notifications and move the coordination logic into the mediator.
- Definitions / vocabulary introduced: Component; Mediator (interface); Concrete Mediator; God Object (the risk).
- Examples, code idioms or patterns shown (pseudocode): `AuthenticationDialog` implementing `Mediator.notify(sender, event)`; it builds a login/register checkbox, login and registration text boxes, OK and Cancel buttons, passing itself into each; on the checkbox "check" event it sets the title to "Log in" or "Register" and shows/hides form sections; on OK "click" it either looks up the user and shows an error or creates the account and logs in; base `Component` stores the mediator and its `click`/`keypress` call `notify(this, "...")`; `Checkbox.check()` sends "check".
- Trade-offs, caveats, anti-patterns: pros — SRP (communication logic in one place), open/closed (new mediators), less coupling, easier component reuse; con — the mediator can grow into a God Object. Relations: Chain of Responsibility passes a request along a dynamic chain; Command creates unidirectional sender→receiver links; Mediator removes direct links; Observer lets receivers subscribe/unsubscribe dynamically. Facade simplifies a subsystem without adding logic and the subsystem objects still talk directly; Mediator centralises and adds coordination. Mediator and Observer are often interchangeable or combined: a mediator implemented as a publisher that components subscribe to looks like Observer; permanently linking components to one mediator is still Mediator; if every component becomes a publisher with dynamic links there is no central mediator, only distributed observers.
- How it applies to a TypeScript/NestJS backend: NestJS CQRS's `EventBus`/`CommandBus` are mediator-style dispatchers; the README's domain-event publisher is a mediator implemented with observer-style subscriptions keyed by event class.

## Observer — Refactoring.Guru (Design Patterns > Behavioral) — https://refactoring.guru/design-patterns/observer
- Cited by README at line 423 in section "Domain Events" to support: implementing a domain-event bus with Observer ideas.
- What it argues / defines:
  - Observer (Event-Subscriber, Listener) defines a subscription mechanism that notifies multiple objects about events happening to the object they observe.
  - Problem: a customer wanting a new phone either visits the store daily (wasted trips) or the store emails everyone on arrival (spam); either the customer wastes time or the store wastes resources.
  - Magazine analogy: subscribers receive each issue by mail and can unsubscribe at any time; the publisher keeps the list.
- Recommendations and rules:
  - The stateful object is the publisher (subject); interested objects are subscribers; the publisher holds a list of subscriber references plus public methods to add and remove them; on an event it iterates the list and calls the notification method on each.
  - Publishers must not couple to concrete subscriber classes: all subscribers implement one interface declaring the notification method (usually `update`) with parameters for context; with several publisher types, a publisher interface declaring only subscription methods lets subscribers observe any publisher.
  - Context can be passed as arguments or the publisher passes itself so subscribers fetch what they need; permanently linking a publisher through the subscriber's constructor is less flexible.
  - Use when a change in one object may require changes in others whose set is unknown in advance or changes dynamically (GUI buttons with attached handlers), or when some objects must observe others only for a limited time.
  - Implementation steps: split logic into the core publisher and the subscriber parts; declare the subscriber interface (`update`); declare the publisher interface (add/remove); put subscription code in an abstract publisher base class, or in a separate composed object for existing hierarchies; concrete publishers notify on important events; subscribers implement `update`; the client registers subscribers with publishers.
- Definitions / vocabulary introduced: Publisher; Subscriber interface; Concrete subscriber; Client; EventManager.
- Examples, code idioms or patterns shown (pseudocode, text editor): `EventManager` with a map of event type → listeners and `subscribe(eventType, listener)`, `unsubscribe`, `notify(eventType, data)` calling `listener.update(data)`; `Editor` owns an `EventManager` by composition, `openFile(path)` notifies "open", `saveFile()` notifies "save"; `EventListener.update(filename)`; `LoggingListener` writes to a log file, `EmailAlertsListener` sends an alert; `Application.config()` subscribes the logger to "open" and the mailer to "save"; the helper object could become a centralised dispatcher letting any object act as publisher; new subscribers need no publisher changes.
- Trade-offs, caveats, anti-patterns: pros — open/closed (new subscribers without changing publishers), relationships established at runtime; con — subscribers are notified in random order. Relations with Chain of Responsibility, Command and Mediator as in the Mediator entry; a popular Mediator implementation is built on Observer.
- How it applies to a TypeScript/NestJS backend: an event-type-keyed map of handler lists is exactly the shape of a minimal domain-event dispatcher; because notification order is undefined, handlers must not depend on each other's order.

## Domain events: design and implementation — Microsoft Learn (.NET Microservices Architecture e-book, ch. 7; the docs.microsoft.com link redirects here) — https://docs.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation
- Cited by README at line 435 in section "Domain Events" to support: the definition of domain events and the deferred-dispatch implementation; the README's own wording ("something happened in the domain that you want other parts of the same domain, in-process, to be aware of", and the "if executing a command related to one aggregate requires additional domain rules to be run on other aggregates..." sentence) is taken from this article.
- What it argues / defines:
  - An event is something that happened in the past; a domain event is something that happened in the domain that other parts of the same domain (in-process) should know about and usually react to. Its key benefit is making side effects explicit: with a `DomainEvent` and at least one `DomainEventHandler`, a rule such as "when an order is created the user becomes a buyer" (`OrderStartedDomainEvent` handled by `ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler`) is visible instead of being coupled implicitly to the code that triggers it; this expresses domain rules in the ubiquitous language and improves separation of concerns.
  - All operations related to a domain event should finish successfully or none should, like a database transaction.
  - Domain events differ from messaging events: real messaging (queues, brokers, AMQP service bus) is always asynchronous and crosses processes and machines (good for integrating bounded contexts/microservices); domain events are raised from the running domain operation with side effects inside the same domain, almost immediately and usually in-process, and may be synchronous or asynchronous. Integration events must always be asynchronous.
  - Domain vs integration events: semantically both are notifications about something that happened; implementations differ: domain events are messages pushed to an in-memory dispatcher (e.g. a mediator built on the IoC container); integration events propagate committed transactions to other subsystems (microservices, bounded contexts, external apps) and so must occur only if the entity was successfully persisted; they need an event-bus infrastructure for inter-process, distributed, ideally push-based communication (commercial service bus, queues, a shared database used as a mailbox).
- Recommendations and rules:
  - Use domain events as the preferred way to trigger side effects across multiple aggregates within the same domain: if a command on one aggregate requires rules on other aggregates, implement them as event handlers (Figure 7-14: `OrderStarted` from the Order aggregate handled by the Buyer aggregate to create the buyer from identity info passed in the `CreateOrder` command). Alternatively the root can subscribe to events raised by child entities (an `OrderItem` raising an event when its price or quantity is too high) to perform a global calculation.
  - Event-based communication is not implemented inside aggregates: handling events is an application concern; the domain layer focuses on domain logic and handlers live in the application layer because they use repositories and application APIs; handlers resemble command handlers, except a command is processed exactly once while a domain event may be processed zero or n times by multiple handlers with different purposes.
  - Keep the number of actions per event open: adding behaviour by `new`-ing specific objects in the orchestrating class breaks open/closed and bloats the class (SRP); with events, adding a rule such as "when a customer's purchases exceed $6,000, apply 10% off future orders and email them" is a matter of adding handlers.
  - Flow: send a command (`CreateOrder`) → a command handler executes a single aggregate's transaction and optionally raises domain events → handlers in the current process execute an open number of side effects (verify/create buyer and payment method, create and send an integration event to the event bus, etc.).
  - Implement events as immutable data-holding classes named with a past-tense verb (`OrderStartedDomainEvent`, `OrderShippedDomainEvent`), read-only properties set only in the constructor; if events were handled asynchronously through a queue requiring deserialisation, properties would need private setters instead (not needed with synchronous MediatR).
  - Raising: Udi Dahan's static `DomainEvents.Raise(event)` (also recommended by Jimmy Bogard in 2010) dispatches immediately, which makes testing and debugging harder because handlers for other aggregates run the moment the event is raised. Preferred deferred approach (Bogard, "A better domain events pattern", 2014): entities add events to a collection (`AddDomainEvent` on the `Entity` base class, with `DomainEvents` list and `RemoveDomainEvent`), and the events are dispatched right before or right after committing the transaction; raising (adding to a list) is thus decoupled from dispatching, and dispatch may be synchronous or asynchronous depending on the dispatcher.
  - Before vs after commit decides whether side effects join the same transaction: dispatching before `SaveChanges` with a scoped `DbContext` shared by all repositories in the request makes handler changes part of one transaction (a failing `SaveChanges` rolls back everything); dispatching after commit creates multiple transactions and requires eventual consistency and compensating actions. This only works if the unit of work can span aggregates (EF Core + relational database); if the store cannot, extra steps are needed, which is one reason persistence ignorance is not universal.
  - Single transaction vs eventual consistency is controversial: Evans (DDD p. 128) and Vernon (Effective Aggregate Design II) advocate one transaction = one aggregate and eventual consistency elsewhere, to avoid substantial database locks at scale; atomic changes are often not needed, domain experts decide whether an operation needs atomicity, and needing atomicity across aggregates may mean the aggregate should be larger or was designed wrongly. Bogard is fine with one transaction across several aggregates when they are side effects of the same original command (dispatching just before commit). Both can be right: it depends on business requirements, required scalability (finer transactions, fewer locks), and how much code you will invest, since eventual consistency needs code to detect inconsistencies and compensate; a way to enable compensation is to store the domain events in extra tables in the original transaction and run a batch that compares events with aggregate state. The deferred, before-commit, single-transaction approach is the simplest with EF Core and relational databases and is what eShop uses.
  - Dispatcher: a real message bus is overkill for in-process domain events; MediatR maps events to handlers through `INotificationHandler<TEvent>` implementations, which act as the subscription so all handlers of an event are discovered and invoked.
  - Handlers may generate integration events to publish across microservices from within a domain-event handler.
- Definitions / vocabulary introduced: domain event; integration event; domain event dispatcher; deferred dispatch; persistence ignorance.
- Examples, code idioms or patterns shown (C#): `OrderStartedDomainEvent : INotification` with read-only `UserId`, `UserName`, `CardTypeId`, `CardNumber`, `CardSecurityNumber`, `CardHolderName`, `CardExpiration`, `Order`; `Entity` base with `_domainEvents` list, `AddDomainEvent`, `RemoveDomainEvent`; the Order root doing `this.AddDomainEvent(new OrderStartedDomainEvent(this, cardTypeId, ...))`; `OrderingContext : DbContext, IUnitOfWork` whose `SaveEntitiesAsync` calls `_mediator.DispatchDomainEventsAsync(this)` then `base.SaveChangesAsync()` (comment lists option A before commit = single transaction, option B after commit = multiple transactions); handler `ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler : INotificationHandler<OrderStartedDomainEvent>` that defaults the card type to 1, finds or creates the `Buyer`, calls `VerifyOrAddPaymentMethod(...)`, adds/updates through `IBuyerRepository`, saves via `UnitOfWork.SaveEntitiesAsync`, then adds an `OrderStatusChangedToSubmittedIntegrationEvent` through `IOrderingIntegrationEventService.AddAndSaveEventAsync` and logs.
- Trade-offs, caveats, anti-patterns: immediate static dispatch hurts testability; after-commit dispatch creates inconsistencies when a handler cannot commit its side effects; eventual consistency costs more code; the reference app propagates domain events synchronously via MediatR within one transaction, but RabbitMQ or Azure Service Bus could propagate them asynchronously with eventual consistency and compensation.
- How it applies to a TypeScript/NestJS backend: the README mirrors this exactly — `addEvent` on the aggregate base, the repository publishing events on persist, handlers in `application/event-handlers`, and the command service wrapping everything in one transaction (option A).

## Event Sourcing pattern — Microsoft Learn, Azure Architecture Center (docs.microsoft.com redirects here; page dated 27 Mar 2026) — https://docs.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
- Cited by README at lines 441 and 459 in sections "Domain Events" and "Integration Events" to support: with event sourcing (one stream per aggregate) changes across aggregates cannot share a transaction and become eventually consistent; also listed among distributed-system patterns.
- What it argues / defines:
  - Instead of storing only current state, store the full series of actions on an object as immutable events in an append-only store that is the system of record; derive state by replaying the entity's eventstream (rehydration), usually served through materialized views because replay is costly. Improves auditability and write performance in complex systems.
  - Problem with CRUD under high load: write contention (read-modify-write with row locks) and lost history unless a separate audit log exists.
  - Workflow (with CQRS): presentation reads from a read-only store and sends commands to command handlers; the handler loads the entity's events, replays them, runs business logic and raises new events, typically to a queue/topic; event handlers persist events to the event store, update read stores, and integrate with external systems.
- Recommendations and rules:
  - Adopt it only where benefits such as auditability and historical reconstruction justify the complexity; it changes storage, concurrency, schema evolution and querying, is costly to migrate to or from, and constrains later design; for most systems traditional data management suffices; apply it selectively (a payment ledger, an order pipeline) and keep CRUD elsewhere (profiles, configuration).
  - Design events to capture business intent ("two seats were reserved") rather than resulting state ("remaining seats changed to 42"), so projections, audit trails and new read models remain possible.
  - Never update stored events; correct or undo only with compensating events (`ReservationCanceled` after `SeatsReserved`); bugs that produced bad events persist, so compensating events or upcasters may be needed.
  - Schema evolution strategies: tolerant deserialisation (ignore unknown fields, default missing ones), explicit event versioning (version in envelope or type name), upcasting (chained transforms to the current schema at read time), in-place migration only as a last resort because it breaks immutability.
  - Ordering: multiple threads/instances append concurrently; add timestamps and an incremental per-request identifier so the store can reject a duplicate entity-id/event-id pair; use optimistic concurrency (reject an append if the stream changed since it was read; the handler reloads, re-evaluates and retries).
  - Querying: only "the stream for an entity id" is available; current state only via replay; use snapshots every N events (load latest snapshot, replay the rest) balancing storage cost against rehydration time; snapshots are an optimisation, the stream stays the source of truth.
  - Store options: purpose-built event stores (per-entity stream reads, optimistic concurrency, snapshots built in) vs general relational/document databases with an append-only table (you build those behaviours); streams partition naturally by entity id; a message broker such as Kafka is not an event store (no per-entity stream queries or optimistic concurrency), though it works as a fan-out layer.
  - Delivery is at-least-once, so handlers must be idempotent (track the last processed sequence per consumer or make mutations safe to repeat), otherwise projections drift and payments or notifications fire twice.
  - Beware circular logic (handling an event creates events that re-trigger it); handle cross-entity conflicts (stock reduced while an order is placed) by reconciling (advise the customer, back-order); test with given-when-then (set up past events, issue a command, assert the produced events) plus integration tests for projections, idempotency and schema paths; for personal data, store it outside the store referenced by id or use crypto-shredding with per-subject keys.
- Definitions / vocabulary introduced: event store; eventstream; rehydration; materialized view/projection; snapshot; compensating event; upcaster; crypto-shredding.
- Examples, code idioms or patterns shown: conference seat reservations — storing a booking count as an entity creates contention on the last day; storing bookings/cancellations as events and replaying them is more scalable; `SeatAvailability` entity rebuilt from events, raises a "seats reserved (n)" event appended to the store; cancellations append a cancellation event; full audit trail for free.
- Trade-offs, caveats, anti-patterns: eventual consistency between store and projections; no SQL-style queries; unsuitable for simple CRUD, prototypes/MVPs, systems needing real-time consistent views, mostly static reference data, and teams without event-driven experience; events are low level, so separate integration events may be needed. Well-Architected pillars: reliability (state reconstruction) and performance (append-only, no locking).

## Pattern: Saga — Chris Richardson (microservices.io) — https://microservices.io/patterns/data/saga.html
- Cited by README at lines 441 and 449 in sections "Domain Events" and "Integration Events" to support: when changes across aggregates or services cannot share a transaction, use sagas with compensating events.
- What it argues / defines:
  - Context: with Database per Service, some business transactions span services (an order must not exceed a customer's credit limit, but orders and customers live in different databases), and two-phase commit is not an option.
  - A saga is a reliably coordinated sequence of local transactions, each inside one service; the coordination (often asynchronous messaging) guarantees the saga ends either with all steps done or with compensating transactions undoing the completed steps after a step fails on a business rule.
- Recommendations and rules:
  - Choreography: each local transaction publishes domain events that trigger local transactions in other services, no central controller (Order Service creates a PENDING order and emits Order Created; Customer Service tries to reserve credit and emits the outcome; Order Service approves or rejects).
  - Orchestration: an orchestrator object tells participants which local transaction to run (Order Service creates a Create Order saga orchestrator; it creates the PENDING order, sends Reserve Credit to Customer Service, receives the reply, approves or rejects).
  - A service must atomically update its database and publish messages/events: a distributed transaction across database and broker is not an option, so use Event Sourcing or Transactional Outbox.
  - Report the saga's outcome to the client that started it synchronously (`POST /orders`): reply only when the saga completes; reply immediately with an id and let the client poll (`GET /orders/{id}`); or reply with an id and push a notification (WebSocket, webhook) on completion.
- Definitions / vocabulary introduced: saga; local transaction; compensating transaction; choreography; orchestration; countermeasures (design techniques that provide isolation, detailed in *Microservices Patterns* ch. 4.3).
- Examples, code idioms or patterns shown: the two create-order flows above; Eventuate Tram example implementations (choreography; orchestration with Eventuate Tram Sagas; choreography plus event sourcing).
- Trade-offs, caveats, anti-patterns: benefit — data consistency across services without distributed transactions; drawbacks — no automatic rollback (compensations must be designed), and no isolation (the I in ACID), so concurrent sagas can cause anomalies and need countermeasures chosen through careful analysis. Related: Database per Service creates the need; choreography sagas publish events via Aggregates and Domain Events; Command-side replica can replace saga steps that only query data.

## Process Manager — Gregor Hohpe & Bobby Woolf, Enterprise Integration Patterns (web excerpt; full text in the book) — https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html
- Cited by README at lines 441 and 449 in sections "Domain Events" and "Integration Events" to support: an alternative to sagas for coordinating multi-step, eventually consistent workflows.
- What it argues / defines:
  - Problem: routing a message through several processing steps when the required steps are not known at design time or are not sequential; the Routing Slip assumes a fixed, linear sequence, which fails when routing depends on intermediate results or steps run in parallel.
  - Solution: a central processing unit, the Process Manager, maintains the state of the sequence and determines the next step based on intermediate results; the message that starts a process is the trigger message; the manager sends a message to a processing unit, receives its reply, decides the next step and sends the next message; because all traffic passes through the hub this is a hub-and-spoke architecture.
- Recommendations and rules:
  - Use it when the sequence is conditional or parallel; it can implement almost any integration problem (most routing patterns in the chapter could be built with it), which is also its main weakness.
  - Do not use it everywhere: the central hub can become a performance bottleneck, overuse distracts from the core design issue and adds significant overhead; the author disputes the EAI-vendor claim that every integration problem is a process problem.
  - Designing and configuring a Process Manager is extensive (could fill a book) and points toward workflow and business-process modelling.
- Definitions / vocabulary introduced: Process Manager; trigger message; hub-and-spoke.
- Examples, code idioms or patterns shown: serverless loan-broker implementations using AWS Step Functions (orchestrates tasks and keeps state in a JSON document, a good match for the pattern) and GCP Workflows as the Process Manager.
- Trade-offs, caveats, anti-patterns: versatility vs bottleneck and overhead; the web page is an excerpt and does not discuss correlation identifiers or per-message process instances (Correlation Identifier is listed as a related pattern, alongside Routing Slip, Pipes and Filters, Content-Based Router, Message Store, Aggregator, Claim Check, Publish-Subscribe Channel and others).

## Pattern: Transactional outbox — Chris Richardson (microservices.io) — https://microservices.io/patterns/data/transactional-outbox.html
- Cited by README at line 449 in section "Integration Events" to support: publishing integration events reliably after the database changes commit.
- What it argues / defines:
  - Context: a command often must update aggregates in the database and send messages/events (a saga participant, a domain-event publisher); both must happen atomically, but a 2PC distributed transaction across database and broker is not viable (unsupported by the database or broker, and coupling the service to both is undesirable); sending mid-transaction is unreliable because the transaction may not commit, and sending after commit is unreliable because the service may crash first; messages must also be sent in the order the service sent them (if T1 then T2 update an aggregate and publish E1, E2, E1 must go first, even across service instances).
  - Solution: the service stores each message in the database in the same transaction that updates the business entities (an outbox table for relational databases; for NoSQL an outbox property on each record), and a separate Message Relay process sends the stored messages to the broker; two relay implementations are named: Transaction log tailing and Polling publisher.
- Recommendations and rules:
  - Messages are guaranteed to be sent if and only if the transaction commits, in the order sent, without 2PC.
  - Consumers must be idempotent (e.g. track processed message ids) because the relay may publish a message more than once (crash after publishing but before recording it); this is normally fine since brokers can deliver duplicates anyway.
- Definitions / vocabulary introduced: Sender; Message outbox; Message relay; Transaction log tailing; Polling publisher; also known as Application events.
- Examples, code idioms or patterns shown: only the generic saga-participant and domain-event-publisher cases; Eventuate Tram implements the pattern.
- Trade-offs, caveats, anti-patterns: potentially error-prone — a developer may forget to write the message to the outbox; related: Saga and Domain event create the need, Event sourcing is an alternative solution.
- How it applies to a TypeScript/NestJS backend: an `outbox` table written in the same transaction as the aggregate, polled by a scheduled worker (or tailed via CDC) and published to RabbitMQ/Kafka, with consumers deduplicating by message id.

## Change data capture — Wikipedia — https://en.wikipedia.org/wiki/Change_data_capture
- Cited by README at line 449 in section "Integration Events" to support: CDC as one way (with the outbox) to propagate committed changes as integration events.
- What it argues / defines:
  - CDC is a set of software design patterns for determining and tracking the data that has changed (the deltas) so action can be taken on it; a data-integration approach covering identification, capture and delivery of changes; involves a source and a target (possibly the same system, and several CDC mechanisms may coexist); can be built at any layer from application logic to physical storage; common in data warehousing (incremental loading, preserving state over time) but usable anywhere.
- Recommendations and rules (methodologies and their trade-offs):
  - Timestamps on rows (a LAST_UPDATE column; rows newer than the last capture are changed; such columns often already exist for optimistic locking).
  - Version numbers on rows (a table-level current version in a reference table, incremented after capture; row-level versions used for optimistic locking cannot find all changes unless every row's starting version is known).
  - Status indicators (a flag marking changed rows; can hold back rows that still need validation before reaching the target even when their version/date is newer).
  - Combined time/version/status for precise filtering (one version, a date range, a ready-for-production status; the three elements are not redundant).
  - Triggers on tables that log events (Id, TableName, RowId, Timestamp, Operation, deltas or full data) into a queue table replayed to targets, supporting publish/subscribe to multiple targets.
  - Transaction-log based CDC: minimal database impact (less still with log shipping to another host), no application or schema changes, low latency, preserves transactional integrity and commit order across tables; challenges: no standard log format and mostly undocumented internals (some vendors — Oracle, DB2, SQL/MP, SQL/MX, SQL Server 2008 — offer programmatic interfaces), coordination with log archiving, translating physical records into logical formats, format changes across versions, filtering uncommitted/rolled-back changes, handling schema changes.
- Definitions / vocabulary introduced: delta; push vs pull CDC (source snapshots and delivers changes vs target requests them); slowly changing dimensions as the alternative (SCD type 1 overwrite, type 2 keep history, type 3 previous and current only; CDC resembles SCD1 and suits delta-only delivery).
- Examples, code idioms or patterns shown: the trigger log-table layout above.
- Trade-offs, caveats, anti-patterns: metadata-only changes (a "last viewed" column) make CDC noisier; non-database sources make CDC a programming challenge; log-based approaches are DBMS-specific; the article is brief, lacks citations and does not cover deletes or timestamp unreliability.

## Domain Events vs. Integration Events in Domain-Driven Design and microservices architectures — Cesar de la Torre (Microsoft DevBlogs, 2017) — https://devblogs.microsoft.com/cesardelatorre/domain-events-vs-integration-events-in-domain-driven-design-and-microservices-architectures/
- Cited by README at line 453 in section "Integration Events" to support: the distinction between in-process domain events and out-of-process integration events, and publishing integration events only after the domain events and the transaction complete.
- What it argues / defines:
  - "Domain event" is ambiguous: it can mean an event raised in memory inside an open transaction (not yet persisted), or an event already committed that must be propagated to other services; only the latter is safe to publish asynchronously to remote systems.
  - Domain events: raised from a business method of a domain entity (aggregate root or child) and handled in-process by subscribers within the same transaction/operation; scope is one microservice or bounded context; they keep a fully encapsulated domain model and keep aggregates of the same model consistent; publishing them fire-and-forget before commit risks propagating data that is later rolled back.
  - Integration events: asynchronous events propagating state changes from one bounded context/microservice to others or to external applications, published only after the change is durably persisted (so it is "100% sure" the event happened); comparable to propagating writes from a write database to a read database in CQRS; published from the infrastructure or application layer as the last step after saving (Greg Young's SimpleCQRS event store publishes each event after persisting it).
- Recommendations and rules:
  - Implement domain events with a static `DomainEvents` class (Udi Dahan 2008–2009, Jimmy Bogard 2010) or an IoC-wired dispatcher; better, use Bogard's 2014 two-phase approach: entities record events in a collection (`Events.Add`) and the EF `SaveChanges` override finds tracked entities with pending events, copies and clears their lists, dispatches each event, then calls `base.SaveChanges()`; this decouples raising from dispatching and makes the model easier to test. Dispatch must happen before `base.SaveChanges()` or the handlers fall outside the transaction; "two-phase" here has nothing to do with two-phase commit.
  - Out-of-process messaging from inside the transaction is only safe through a transactional artifact (a transactional queue) so the message can be withdrawn if the save fails.
  - Name the APIs differently: `EventBus.Publish(IntegrationEvent)` for cross-service events; `DomainEvents.Add` / `Dispatcher.Dispatch` for in-process events; convert a domain event into an integration event, or aggregate several domain events into one, and publish only after the original transaction commits.
  - Design for distributed failure: options are a transactional outbox table written in the same transaction and read by an event-creator component (preferred); transaction-log mining (rejected as too coupled to infrastructure and complicated); event sourcing (probably best, often not feasible in full). Preferred pattern: in the original transaction save the state plus a "ready to publish" marker and commit; try to publish to the bus; on success start a new transaction and mark the event "published"; on failure the record stays "ready to publish" and a background process republishes later — effectively a simplified event store holding only integration events and their state.
  - Safeguards: retry failed publishes with exponential backoff; make consumers idempotent or include enough data to detect duplicates and return the same response; handle races between the background republisher and an in-flight publish.
  - Alternative design: one event definition on two channels — a `DomainEventHandler` that runs immediately, and a `CommittedDomainEventHandler` that runs after commit (from a "committed events" queue) for handlers that must query stored data, behaving like an integration-event handler.
- Definitions / vocabulary introduced: domain event vs integration event; two-phase domain events; committed events.
- Examples, code idioms or patterns shown (C#, described): a `Customer` that raises a "became preferred" event after changing in-memory state; a `RecordPayment` method that adds a payment, recalculates the balance and raises a "fee paid off" event at zero; a handler that loads another aggregate through a repository and calls a method on it inside the same transaction; the `SaveChanges` override described above.
- Trade-offs, caveats, anti-patterns: domain events suit in-memory communication between disconnected aggregates of one model and are not always applicable; publishing inside a `SaveChanges` override is not the same as Young's after-persist publish; the post is a comparison of community approaches that may change; some attributions (Vernon) are from memory.
- How it applies to a TypeScript/NestJS backend: the README's rule "domain event handlers send integration events, published only after all domain events finished and the transaction committed" is this article's conclusion; implement the "ready to publish/published" marker as an outbox table.

## Saga distributed transactions pattern — Microsoft Learn, Azure Architecture Center (the cited reference-architecture URL redirects to /patterns/saga; page dated 25 Feb 2025) — https://docs.microsoft.com/en-us/azure/architecture/reference-architectures/saga/saga
- Cited by README at line 457 in section "Integration Events" as a useful pattern for integration events in distributed systems.
- What it argues / defines:
  - A transaction is a unit of work of multiple operations; an event is a state change affecting an entity; a command encapsulates everything needed to perform an action or trigger an event; transactions must be ACID (atomicity, consistency, isolation, durability). Within one service with one database this holds; across services with database-per-microservice (encapsulated data, best-fit technology per service, independent scaling, failure isolation) ACID is not directly applicable and 2PC-style models are poorly suited, hence the Saga pattern.
  - A saga breaks a distributed transaction into local transactions; each completes atomically in one service, updates its database and triggers the next step through an event or message; if a step fails, compensating transactions reverse the preceding steps.
- Recommendations and rules:
  - Key concepts: compensable transactions (can be undone by an opposite-effect transaction); the pivot transaction (point of no return: once it succeeds, all remaining steps must complete; it may be irreversible/non-compensable, or the last compensable/first retryable step); retryable transactions (idempotent steps after the pivot that guarantee eventual completion).
  - Choreography (services exchange events, no controller): good for simple workflows with few services, no extra coordination service, no single point of failure; but confusing as steps are added, hard to track which commands each participant responds to, risk of cyclic dependencies, and integration testing needs all services running.
  - Orchestration (a central orchestrator issues commands, stores and interprets task states, handles failure recovery with compensations): suits complex workflows and adding services, avoids cyclic dependencies, clear separation of responsibilities; but adds coordination logic and a point of failure.
  - Considerations: a shift in design thinking toward coordination and consistency across services; debugging grows complex with more participants; local database changes are irreversible once committed; handle transient failures and ensure idempotence (Idempotent Consumer pattern); monitor and track sagas; compensating transactions may themselves fail and leave inconsistency.
  - Data anomalies from missing isolation: lost updates (a saga overwrites another's changes), dirty reads (reading another saga's incomplete modifications), fuzzy/non-repeatable reads (different steps read inconsistent data). Countermeasures: semantic lock (application-level lock/semaphore marking an update in progress during a compensable transaction); commutative updates (updates applicable in any order with the same result); pessimistic view (reorder the saga so updates happen in retryable transactions to eliminate dirty reads); reread value (verify data is unchanged before updating, else stop and restart); version file (log all operations on a record and apply them in order); risk-based concurrency by value (sagas for low-risk updates, distributed transactions for high-risk ones).
  - Use when you need consistency across services without tight coupling and must roll back/compensate on failure; not suitable for tightly coupled transactions, when compensations would have to occur in earlier participants, or when there are cyclic dependencies.
- Definitions / vocabulary introduction: saga; local transaction; compensating, pivot, retryable transactions; choreography; orchestration; semantic lock; commutative updates; pessimistic view; reread value; version file.
- Examples, code idioms or patterns shown: diagrams only (overview, choreography, orchestration); no code.
- Trade-offs, caveats, anti-patterns: as in the two benefit/drawback tables above; compensations not guaranteed to succeed.

## Saga vs. Process Manager — devarchive.net (blog, Nov 2015) — https://blog.devarchive.net/2015/11/saga-vs-process-manager.html
- Cited by README at line 458 in section "Integration Events" as reading on the difference between sagas and process managers.
- What it argues / defines (the author's own terminology, not reconciled with published definitions):
  - Saga: stateless; decides what to do only from the content of the incoming event; subscribes to events through lambdas that return a correlation id; handlers use try/catch and may issue commands, send emails, wait for results by subscribing to resulting events, and schedule themselves through a durable scheduler; on failure the catch block reschedules the event or an enriched copy (e.g. with a `retryNumber`); it inherits from a write-only Event Stream base.

  - Run each Process Manager as a single instance per system with cached state (e.g. an actor addressed by PM name plus correlation id; earlier he used Retlang fibers and channels per instance).
  - Split large Process Managers into smaller ones to parallelise work (easy for PMs, easier for sagas); use UML sequence diagrams to visualise processes spanning several sagas/PMs.
- Definitions / vocabulary introduced: correlation id; dead-event stream; durable scheduler; routing slip (in the comments: a `CarHotelFlightSaga` subscribed to `StartBookingEvent` and `SagaProgressEvent`, where the progress event carries a routing slip and the handler either compensates or moves to the next step; queue addresses can be the saga stream name = saga name plus correlation id).

## The Outbox Pattern — Kamil Grzybek (kamilgrzybek.com, 11 Mar 2019) — https://www.kamilgrzybek.com/design/the-outbox-pattern/
- Cited by README at line 459 in section "Integration Events" as a useful pattern for integration events in distributed systems.
- What it argues / defines:
  - Business operations often need fire-and-forget external communication (external services, message bus, mail server, another transaction in the same or a separate database): sending an email after an order, publishing a client-registration event, processing another aggregate in a separate transaction (decreasing stock after an order). Atomicity between the state change and the message cannot be guaranteed (dual write); 2PC is rejected even where available because it limits latency, throughput, scalability and availability.
  - Failure windows in a naive `RegisterCustomerCommandHandler`: the transaction commits and the system crashes before the event is sent (event lost); the transaction commits but the bus is unavailable (event cannot be sent).
  - Solution (based on the Guaranteed Delivery pattern): write messages to be processed later into an Outbox table in the same transaction as the business data (name borrowed from email clients); a separate process periodically reads unprocessed messages, processes them, and marks them processed; if sending succeeds but marking fails, the message is sent again next run, so delivery is at-least-once ("once-or-more") and receivers must be idempotent (same effect whether received once or many times).
- Recommendations and rules:
  - Keep `OutboxMessage` in Infrastructure, not the domain model (business people think of an Outlook outbox, not the messaging pattern).
  - Do not repeat outbox writes in every command handler (DRY): use Notification Objects — domain events that must run inside the transaction are dispatched normally, while events that must run outside it produce a notification that is serialised and written to the Outbox during the unit of work's commit.
  - Prevent concurrent outbox processing (`[DisallowConcurrentExecution]` on the Quartz job); choose the polling interval by message volume; the processor can be a separate process or a thread in the same process.
  - Design receivers to be idempotent because duplicates are expected.
- Definitions / vocabulary introduced: Outbox; at-least-once delivery; Notification Object; dual-write problem.
- Examples, code idioms or patterns shown (C#/.NET, EF Core, Dapper, Quartz.NET, MediatR, Json.NET): table `app.OutboxMessages(Id UNIQUEIDENTIFIER PK, OccurredOn DATETIME2, Type VARCHAR(255), Data VARCHAR(MAX), ProcessedDate DATETIME2 NULL)`; class `OutboxMessage { Id, OccurredOn, Type, Data }` with a private parameterless constructor for the ORM and an internal constructor generating the Guid; EF configuration `ValueGeneratedNever()`; `CommitAsync` in the unit of work: dispatch domain events via `_domainEventsDispatcher.DispatchEventsAsync(this)` which returns notifications, serialise each with `JsonConvert.SerializeObject`, create `OutboxMessage(occurredOn, typeFullName, json)`, add to the `OutboxMessages` set, then one `SaveChangesAsync` so domain changes and outbox rows commit atomically; `CustomerRegisteredEvent : DomainEventBase` holding the `Customer`, `CustomerRegisteredNotification : DomainNotificationBase<CustomerRegisteredEvent>` holding `CustomerId` with a `[JsonConstructor]` for deserialisation; `StartQuartz` builds a scheduler, an Autofac container (OutboxModule, MediatorModule, InfrastructureModule), a `JobFactory`, and a `ProcessOutboxJob` triggered by cron `0/15 * * ? * *` (every 15 seconds); the job queries `Id, Type, Data` where `ProcessedDate IS NULL`, resolves the CLR type by name from the assembly containing `IDomainEventNotification<>`, deserialises, `_mediator.Publish((INotification) notification)`, then `UPDATE ... SET ProcessedDate = @Date` (UtcNow); `CustomerRegisteredNotificationHandler : INotificationHandler<CustomerRegisteredNotification>` as the placeholder for sending a bus event or email. Source: the author's `sample-dotnet-core-cqrs-api` repository.
- Trade-offs, caveats, anti-patterns: at-least-once, never exactly-once; a crash between publishing and marking processed causes a duplicate; the sample query has no ordering or batch limit and builds SQL by concatenation.
- How it applies to a TypeScript/NestJS backend: same shape — an `outbox_messages` table written inside the command's transaction, a `@Cron`/scheduler job in a worker that publishes unprocessed rows to RabbitMQ/Kafka and marks them, serialising events to primitives (as the README's warning about not sending value objects across processes requires).

## Value Object — Martin Fowler (bliki, 14 Nov 2016) — https://martinfowler.com/bliki/ValueObject.html
- Cited by README at line 500 in section "Value objects" to support: the definition of value objects (no identity, structural equality, immutability).
- What it argues / defines:
  - Value objects are compounds whose equality depends on their property values (a 2D point, money as number plus currency, a date range); reference objects are distinguished by identity (memory reference or a unique key such as an order number); the distinction is how equality is tested, and it matters for all code. DDD's "entity" is a common kind of reference object; Fowler uses "entity" only inside domain models.
  - Two points at (2,3) must be equal, but default reference comparison breaks this (`{x:2,y:3} !== {x:2,y:3}` in JavaScript); Clojure's `=` compares values; Java's `Point` overrides `equals` (implemented in `Point2D`), so Java code must use `equals`, not `==`, as with `String`; Ruby's `==` can be overridden; JavaScript built-ins ignore a custom `equals` (`includes` fails; use `some(i => i.equals(p))`), whereas Java's `Object.equals` is honoured by libraries.
- Recommendations and rules:
  - Value objects should be immutable: to change a value, create a new object. Reason: aliasing bugs — two variables referencing one mutable object; Fowler's `Date` example where `partyDate = retirementDate; partyDate.setDate(5)` moves the retirement date too; fixed by assigning a new `Date`; Java 8's `java.time` avoids most of this. Immutability is usually enforced by offering no setters; an alternative is copy-on-assignment (C# structs).
  - Whether something is a value depends on context: a postal address is a value in simple systems but a hierarchy of references in a mapping system.
  - Replace primitives with value objects (a telephone-number type): explicit variables and parameters, type checking where supported, a focus for validation, and no inapplicable operations (no arithmetic on id numbers).
  - Small objects are the clearest cases, but larger structures qualify when they have no conceptual identity and need not be shared by reference; functional languages (immutable by default) suit this; value objects are often dismissed as trivial yet can carry rich behaviour (a `Range` class removes repeated start/end handling) and introducing them can be a refactoring focus that greatly simplifies a system.
  - Immutability also helps reference objects (an order that does not change during a GET can be immutable and safely copied), but that does not make them value objects since equality still rests on the identity key.
- Definitions / vocabulary introduced: Value Object; Reference Object; Entity (Evans classification); aliasing bug; whole value.
- Examples, code idioms or patterns shown (JavaScript): plain objects compared by reference; `class Point` with constructor `(x, y)` and `equals(other)` comparing `x` and `y` with `===`; immutable version storing `this._data = {x, y}` exposed via getters only (clients could still write `_data`, so immutability relies on discipline; `Object.freeze` is stricter; Fowler prefers a class with explicit accessors).
- Trade-offs, caveats, anti-patterns: no `hashCode` guidance; persistence of value objects deferred to Vaughn Vernon's DDD book (recommended as the best in-depth treatment); terminology confusion — around 2000 J2EE literature used "value object" for Data Transfer Object, a usage that has mostly disappeared; the term gained traction with *P of EAA* and Evans's DDD book.
- How it applies to a TypeScript/NestJS backend: implement `equals` structurally on a `ValueObject` base, keep props `readonly` (or `Object.freeze` them), and never rely on `===` or array `includes` for value comparison.

## Value Objects to the rescue! — Paul Milian (The Startup on Medium, 8 Sep 2019; read via browser pane, WebFetch returned 403) — https://medium.com/swlh/value-objects-to-the-rescue-28c563ad97c6
- Cited by README at line 501 in section "Value objects" as further reading.
- What it argues / defines:
  - Value objects (a DDD building block from Evans's "blue book") represent typed values with no conceptual identity; they are defined by their attributes and should be immutable; they are useful even outside DDD, which otherwise adds overhead only worth it for very complex domains. Evans's marker example: a child cares about colour and tip, not which identical marker he holds.
  - Three characteristics: value equality (60 seconds equals one minute as a `Duration`; Java needs `equals`/`hashCode` overrides, or Lombok `@Value`, or a Kotlin data class); immutability (change only by full replacement: a new instance; remove setters, return immutable objects or copies from getters; `final` in Java, `val` in Kotlin); self-validation (validate attributes at creation and refuse to create invalid instances, e.g. a negative `Age`, with `IllegalArgumentException` or a custom exception).
- Recommendations and rules:
  - Reduce primitive obsession (a string for an email, a number for a weight or duration, adopted because a class seems like too much effort).
  - Type safety: a `float distance` has an unknown unit; naming it `distanceInMeters` relies on developer attention, and the compiler accepts any float, so conversion code gets scattered or deleted; a `Distance` value object owns all conversions and exposes getters per unit. Parameter mix-ups: `sendEmail(String email, String subject, String body)` is easily called with arguments in the wrong order; `sendEmail(EmailAddress, Subject, Content)` makes inversion a compile error; going further to `sendEmail(Email email)` is simpler to read and more flexible.
  - Flexibility: an `Email` class can grow to multiple recipients or content types without changing the method signature; a `CustomerId` hides whether it is a string or number internally and lets the storage representation change with minimal impact.
  - Validation: the only way for a value object to exist is to be valid and it cannot change, so callers stop wondering whether to validate; otherwise validation is duplicated or missing because there is no sensible place for it; validation lives inside the object, which alone knows whether it is valid.
  - Reduce duplication by sharing value objects (an `Address` used by `Employee` and `Office`); readability (`List<PhoneNumber>` instead of `List<String>`); centralised domain logic easier to find and change.
  - Performance: immutable objects are safe in parallel code and can be shared as flyweights; stable hash codes make them safe keys in caches and hash maps.
- Definitions / vocabulary introduced: value object; primitive obsession; flyweight.
- Examples, code idioms or patterns shown (Java/Kotlin, images not captured): `Distance`, `EmailAddress`/`Subject`/`Content`/`Email`, `CustomerId`, `Address`, `Age`, `Duration`, `PhoneNumber`.
- Trade-offs, caveats, anti-patterns: do not wrap every single primitive — too many classes bloat the codebase and frequent re-instantiation can cost performance; immutable objects interface poorly with Java databases/ORMs (relax immutability or add DTOs, which adds classes). The author's rule: use a value object when a field or group of fields has validation or domain logic, when primitives would be ambiguous, or when the concept exists in the domain.

## Designing validations in the domain model layer — Microsoft Learn (.NET Microservices Architecture e-book, ch. 7; the docs.microsoft.com link redirects here) — https://docs.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-model-layer-validations

- What it argues / defines:
  - In DDD, validation rules are invariants; the aggregate's main responsibility is to enforce invariants across state changes for all its entities; domain entities should always be valid and must not be able to exist invalid; invariants are expressed as contracts, with exceptions or notifications raised on violation.   - Deferred validation in the domain: see Vaughn Vernon, *Implementing Domain-Driven Design*, section on validation.
  - Two-step validation: field-level validation on command DTOs and domain-level validation inside entities; return a result object instead of exceptions to make errors easier to handle; field validation with annotations is defined once and can run server- and client-side for DTOs.

## Why Domain Invariants are critical to build good software? — Sebastian Gebski (No Kill Switch, 20 Nov 2017) — https://no-kill-switch.ghost.io/why-domain-invariants-are-critical-to-build-good-software/
- Cited by README at line 528 in section "Domain Invariants" as further reading; the README's definition of invariants as "policies and conditions that are always met for the Domain in particular context" paraphrases this post.
- What it argues / defines:
  - Every system (software, board game, biotope, physical object) rests on underlying rules of the game; the specific scenarios derive from these invariants; modelling without learning the invariants gives wrong understanding and shaky foundations, and reverse-engineering invariants from scenarios is costly with no guaranteed success.
  - Trigger: a claim that User-Story-style functional specs are suboptimal because they cover only positive scenarios, the less important part of the problem.
  - Domain invariants are policies and conditions that always hold for a domain within a particular context: constraints, axioms and key characteristics forming the context's paradigm. They specify (1) what is impossible or prohibited (a non-validated user cannot purchase), (2) formulas or definitions that always apply (a portfolio = one's clients plus the team's clients and prospects in the area), (3) fundamental laws of the business (requested application content is ineffective until the request concludes; at most one contract annex in progress at a time). Those examples are not yet proper invariants because they lack the reasoning: what the invariant is for and why the constraint applies.
- Recommendations and rules:
  - Distinguish invariants from business validation rules: validation runs over an already-modified object whose state is then verified; an invariant guards the object so it cannot be modified in a contradicting way (minor difference); invariants do not map to business-logic containers such as methods, procedures or smart constructors — they can be expressed through the type system, aspects, declarative attributes, access modifiers, object/record relations or any other language feature (major difference).
  - Distinguish requirements from invariants: a user-story requirement is a single snapshot built on several interwoven invariants whose governing rules are unstated, so you must reconstruct them to implement it correctly; an invariant describes how the business operates in general, affects many scenarios (sometimes non-obviously when several combine), and business change usually hits invariants first and ripples into scenarios.
  - For each candidate invariant ask what it is for and why it holds.
- Definitions / vocabulary introduced: domain invariant; validation rule vs invariant; requirement vs invariant.
- Examples, code idioms or patterns shown: analogies only — physics (describing a sliding soap bar, a falling feather, a bouncing ball and a cannonball separately discards the knowledge of gravity and friction and cannot predict a wet feather fired at an angle); board games (learning Star Trader, Pandemic, Galaxy Trucker or Samurai Spirit by watching moves is slow, misreads conditional rules, cannot decompose composite interactions, and collapses when a wrong assumption is overturned).
- Trade-offs, caveats, anti-patterns: modelling from isolated scenarios; building on unverified assumptions; treating invariants as mere validation; listing constraints without their reasoning; missing conditional rules. The post gives no code, no enforcement location and no aggregate guidance.

## Value Classes and Universal Traits — docs.scala-lang.org (Scala 2 overview) — https://docs.scala-lang.org/overviews/core/value-classes.html
- Cited by README at line 587 in section "Replacing primitives with Value Objects" to support: Scala value classes represent wrapper types as primitives at runtime (an `Email` is a `String` at runtime), avoiding the boilerplate and allocation cost that TypeScript value objects incur.
- What it argues / defines:
  - A value class extends `AnyVal` (Scala 2.10, SIP-15) to avoid allocating runtime objects: `class Wrapper(val underlying: Int) extends AnyVal` has type `Wrapper` at compile time and is an `Int` at runtime; it may define `def`s but not `val`s, `var`s or nested traits/classes/objects.
  - Universal traits extend `Any`, have only `def` members and no initialisation; a value class may extend only universal traits and cannot be extended; calling an inherited universal-trait method forces instantiation.
  - Scala 3 keeps value classes for compatibility but recommends opaque types instead.
- Recommendations and rules:
  - Use value classes for extension methods without allocation (`implicit class RichInt(val self: Int) extends AnyVal` lets `3.toHexString` compile to a static call `RichInt$.MODULE$.toHexString$extension(3)`) and for type safety without overhead (`class Meter(val value: Double) extends AnyVal` with a `+` method operating on primitive doubles); in practice case classes and extension methods give cleaner syntax.
  - Allocation still happens when the value class is treated as another type (including a universal trait: `add(a: Distance, b: Distance)` with `Meter` arguments allocates; `add(a: Meter, b: Meter): Meter` does not), used as a type argument (`identity(Meter(5.0))`), assigned to an array (`Array[Meter]`), or subject to runtime type tests/pattern matching (`case P(3)`).
  - Limitations: exactly one primary-constructor parameter that is a public `val` (non-public allowed since 2.11.0) and not itself a value class; no `@specialized` type parameters; no nested or local classes, traits or objects; no concrete `equals` or `hashCode`; must be top-level or a member of a statically accessible object (a nested value class would need an outer reference, i.e. a second parameter); only `def` members (no `val`, `var`, `lazy val`); cannot be extended (implicitly final); no by-name or lazy constructor parameters; no secondary constructors; cannot appear as a result type in a structural refinement; cannot extend a non-universal trait ("illegal inheritance").
- Definitions / vocabulary introduced: value class; universal trait; opaque type (Scala 3 replacement); extension method via implicit class.
- Examples, code idioms or patterns shown (Scala): `Wrapper`, `RichInt`, `Meter`/`Distance`, `case class P(i: Int) extends AnyVal` pattern-matching example, and the compiler error messages for each illegal form ("value class needs to have exactly one public val parameter", "value class may not have secondary constructors", "value class may not be a member of another class").
- Trade-offs, caveats, anti-patterns: allocation returns whenever the value is used polymorphically, generically, in arrays or in runtime type tests; Scala 3 prefers opaque types.
- How it applies to a TypeScript/NestJS backend: TypeScript has no runtime-erased wrappers; the closest analogues are branded type aliases (zero runtime cost, no behaviour) or full value-object classes (behaviour, but allocation and `.value` unwrapping), which is the trade-off the README's note describes.

## Primitive Obsession — A Code Smell that Hurts People the Most — Arpit Jain (Sixt Research & Development India on Medium, 30 Jan 2019; read via browser pane, WebFetch returned 403) — https://medium.com/the-sixt-india-blog/primitive-obsession-code-smell-that-hurt-people-the-most-5cbdd70496e9
- Cited by README at line 595 in section "Replacing primitives with Value Objects" as recommended reading.
- What it argues / defines:
  - Primitive fields are a language's built-in building blocks (int, string, constants); primitive obsession is relying on them too much — a primitive value controls the logic of a class without being type-safe, i.e. using primitive types to represent a domain object. Example: a URL stored as a string loses access to its scheme, query parameters and protocol without extra code.
  - Unlike long methods or large classes, most developers cannot detect this smell intuitively.
- Recommendations and rules:
  - Recognise the pain points in the worked example (a user service with `authenticate(String userName, String password)` and `create(UserDTO)`): password rules (non-empty, length and character combinations) end up in `PasswordUtil`, `StringUtil` and `HashUtil` and are re-run before both methods; data duplicated in several places; hard to guess where the logic lives (password logic sprayed everywhere); no guarantee the value is not modified later; a new developer may not know which utility to call.
  - Fix with a value object (`Password`) with three fundamental characteristics: immutability (a `final class Password { private String value; ... }` with no setters; otherwise sharing a `Weight` value object between Jim and Jack means changing Jim's weight to 80 changes Jack's; immutable values can be shared by reference safely, important in multi-threaded code); value equality (two value objects with equal internal values are equal); self-validation (only accepts values that make sense in its context, e.g. throw `InvalidLength` when shorter than 6 characters; the constructor must not do all validations, only the basic sanity checks shared by all contexts).
  - Consequences: the `Password` class can answer whether another password matches, hiding hashing and rehashing; the three util classes can be deleted and their logic moved where it belongs; related logic that grows later has one dedicated home; signatures become `findUser(UserId id, Password password)` and `create(User newUser)`.
  - How to spot value objects: special validation logic applied wherever a kind of information is used (phone numbers, emails); special formatting for humans (IPv4/IPv6 addresses); sets of functions relating to one type (start/end date, first/last name); special comparison rules for similar value types. These are heuristics that vary per application; with practice you see more of them.
  - Closing rule: a method depending on a string feels lighter than one depending on a custom class, but the dependency on the primitive's rules is still there, hidden and implicit; with a string or int the compiler cannot tell whether the value is valid, so think about the domain of allowed values; if a bunch of rules for a value must be applied consistently throughout the project, create a class; if simple values suffice because the value is not critical, use a primitive.
- Definitions / vocabulary introduced: primitive field; primitive obsession; value object (immutability, value equality, self-validation).
- Examples, code idioms or patterns shown (Java): the `Password` class with and without the length check; the Jim/Jack `Weight` aliasing example; the before/after user-service signatures.
- Trade-offs, caveats, anti-patterns: utility-class sprawl; constructors that try to do every validation; wrapping values that are not critical to functionality.
