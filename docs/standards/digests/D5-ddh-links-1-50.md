## Backend best practices — Sairyss (GitHub README) — https://github.com/Sairyss/backend-best-practices
- Cited by README at line 5 in section "Domain-Driven Hexagon" (intro, "Check out my other repositories") to support: pointer to the author's companion collection of backend tools/guidelines.
- What it argues / defines:
  - A curated, mostly language-agnostic (examples in TypeScript/Node) catalogue of backend practices; architecture and testing are framed as investments to spend only where they pay back.
  - Companion to Domain-Driven Hexagon, System Design Patterns and the Full Stack starter template; MIT.
- Recommendations and rules (by section):
  - Architecture: choose it deliberately (fundamental, hard to change; it manages complexity and coordination); enforce architecture rules with tooling, not convention.
  - API security: validate all input; keep sensitive info out of auth tokens; TLS everywhere; encrypt sensitive data at rest; modern algorithms only (no MD5/SHA1; RSA 2048+, SHA2 256+, AES 128+); monitor user activity for privilege abuse; never commit secrets (env vars, gitignored `.env`); update dependencies and monitor their vulnerabilities; follow security advisories; no sensitive data in query strings or logs; harden servers (close unused ports, firewall, fail2ban, patching); baseline only — security is wider than the README.
  - Data validation order (cheap first, expensive last): origin (authorised user / whitelisted IP) → existence (null/empty) → size (before anything else; oversized input may be DoS) → lexical content (characters/encoding) → syntax (regex, JSON parse) → semantics (e.g., referenced id exists in DB); defer DB checks to the end. Example: class-validator decorators on DTOs.
  - Least privilege: expose only needed ports (443, admin SSH); DB users get only needed rights (read-only APIs / read replicas / CQRS query side have no write/delete); staff access limited by role and logged; reasoning: smaller attack surface.
  - Rate limiting: limit requests per window (default unlimited enables DoS, brute force, perf issues); also limit login attempts and lock accounts temporarily; tools: express-rate-limit, NGINX, Kong plugin.
  - Testing: prefer black-box (behavioural, public-API) tests; white-box tests couple to internals and break on refactor, so use them only as a supplement (to cut combinatorial cases e.g. per strategy, for libraries consumed by others, or to document complex code because a stale test fails unlike a comment). Split black-box tests into fast use-case tests with all I/O mocked (run on every change / pre-commit) and slow e2e tests with real infrastructure (run before push/deploy); e2e ideally independent of app code (QA-owned in big orgs); avoid in-memory/embedded DBs (sqlite) for e2e — faster but less reliable; BDD via Cucumber/Gherkin (jest-cucumber) lets non-devs define steps.
  - Load testing: find bottlenecks under concurrency before production; measure response times and error rates; k6, Artillery (configs double as seeders).
  - Fuzz testing: feed invalid/unexpected/random input (stored JS injection, SQL injection, odd Unicode/emoji); complements, never replaces, validation; Big List of Naughty Strings, Artillery fuzzer plugin, sqlmap.
  - Documentation: OpenAPI/Swagger or GraphQL specs for every endpoint (request, response, properties, examples, exceptions; NestJS Swagger decorators); keep a wiki (Notion/Obsidian/Confluence/Outline) for tools, procedures and the "why" (bus factor, onboarding); every repo gets a README (functionality, CLI, setup); self-documenting code (small single-purpose functions, descriptive names, named variables instead of inline primitives/conditionals); prefer statically typed languages (intent, compile-time errors, IDE help; "easy to use correctly, hard to use incorrectly"; optional for small scripts); avoid useless comments (they rot) except for counter-intuitive hacks/perf tricks; JSDoc on public APIs for intellisense.
  - Database: back up frequently, store remotely/separately, encrypt, define retention, monitor backup and restore, consider point-in-time recovery; manage schema with versioned, reversible migrations (hand-written or generated, e.g. TypeORM; can run on deploy); beware dropping columns/tables with data; run data migrations before schema migrations and back up first; raw SQL migrations are fine; seed dev/test data (typeorm-seeding, faker).
  - Configuration: no inline literals; never plain-text secrets in config/source; env vars (dotenv) or Docker/K8s secrets for secrets and env-specific values; group config hierarchically, one file per concern; fail fast at startup when required env vars are missing (env-var); plain objects suffice (alternatives: NestJS ConfigModule, rc, nconf); `.env.example` with dummy values, `.env` gitignored.
  - Logging: log all meaningful events; use levels correctly (info for production-meaningful, debug for dev, warn/error for unwanted behaviour); meaningful messages with metadata; never log sensitive data and scrub keys like "secret"/"password" as a safety net; mature structured (JSON) logger (Winston/Pino), not console.log; include user id; correlation id generated at gateway/client and propagated, causation id to order events; one event per line with timestamp, context, ids, metadata; ship to log management (Sentry, Loggly, Logstash, Splunk) and alert important events to Slack/SMS; write to stdout and let infrastructure route (Docker logging drivers) — the app does no log routing; offload transformations to a separate process/sidecar (Pino transports) because logging costs performance; visualise with Kibana/cloud tools.
  - Monitoring: design for monitoring from the start (production incidents are rare and hard to reproduce, so capture data when they happen); monitor connectivity (health-check endpoint), performance (response times), error rate, CPU/memory (spikes = bad code/leaks/cost), storage, dependencies; tools: Sematext, AppSignal, Prometheus, Checkly, ClinicJS.
  - Telemetry: collect metrics/logs/traces; wrap multi-step operations in spans with named events to find slow steps; instrument endpoints, event handlers, external calls, DB queries, big functions, periodic jobs; OpenTelemetry.
  - Standardisation: agree and write down one way to do each common thing (stack, tools, architecture, style, naming, API response shape, pagination, protocols/schemas, error handling, versioning, docs, health/error/metrics reporting, logging) and enforce it; otherwise teams diverge.
  - Static analysis: ESLint + typescript-eslint (airbnb / airbnb-typescript), reasonably strict rules incl. eslint-plugin-security; forbid explicit `any` (`@typescript-eslint/no-explicit-any: error`) and implicit `any` (`strict: true`); Code Spell Checker; trade-off: strictness vs convenience.
  - Formatting: Prettier for consistency.
  - Graceful shutdown: on termination stop accepting requests, finish in-flight ones, close DB/external connections, then exit (avoid data loss).
  - Profiling and benchmarking: Node built-in profiler; verify optimisations with benchmarks (hyperfine for CLIs).
  - Easy setup: one or a few commands after clone (package.json scripts, docker-compose, Makefile, seeds, migrations).
  - Deployment: CI/CD on push; run e2e, load/fuzz, static analysis, dependency vulnerability checks and halt on failure; blue-green deployment for zero-downtime rollouts and instant rollback.
  - Code generation: templates (Hygen) for boilerplate that encode the architecture (Clean/Hexagonal/DDD/SOLID); understand what is generated; adopt only after the architecture stabilises because templates churn.
  - Version control: git; pre-commit/pre-push hooks (Husky) running tests/lint/format; conventional commits (commitlint, semantic-release) for automated versioning and release notes.
  - API versioning: new DTO/route versions (`/v2/users`), keep old versions until clients migrate, prefer adding versions over modifying endpoints; unnecessary when the only consumer is your own frontend; GraphQL `@deprecated`; semver for packages.
- Definitions / vocabulary: bus factor; black-box vs white-box testing; correlation id vs causation id; least privilege; blue-green deployment; conventional commits; graceful shutdown; telemetry/spans.
- Examples / idioms: `handleUserCreatedEvent` wrapped in OpenTelemetry spans with attributes and events (TS); ESLint `no-explicit-any` rule; tsconfig `strict: true`; `.env.example` pattern; repo files for DTO validation, e2e `.feature` files, Artillery config, docker-compose.
- Trade-offs / anti-patterns: implementation-coupled white-box tests; in-memory DBs for e2e; secrets in source/URLs/logs; backups on the same disk; console.log logging; drifting comments; editing endpoints in place instead of versioning; manual setup; insecure hashes; careless column drops; premature code generation; logging transformations in-process.
- Recommended external repos: goldbergyoni/nodebestpractices, mkosir TypeScript style guide.

## System Design Patterns — Sairyss (GitHub README) — https://github.com/Sairyss/system-design-patterns
- Cited by README at line 6 in section "Domain-Driven Hexagon" (intro) to support: pointer to the author's companion list on distributed systems, scalability and performance.
- What it argues / defines:
  - Work-in-progress catalogue of distributed-system topics; recurring theme: distributed systems are hard mainly because of coupling and consistency, so add complexity only when needed.
- Recommendations and rules:
  - Synchronous calls (HTTP/RPC) fit client→backend, shared internal services and third parties; avoid sync calls between microservices (coupling, fragility, slowness, "distributed monolith"); prefer async messaging between services (autonomy, tolerate outages), reconciled by eventual consistency and events.
  - Serialization: describe models in a language-agnostic IDL; JSON is fine for most; move to Protobuf/Avro/Thrift as systems grow (compact, interoperable, forward/backward-compatible schemas).
  - API gateway: single entry point for routing, translation, load balancing, rate limiting, auth, circuit breaking, aggregation, monitoring (Kong, nginx; related: gateway offloading, BFF).
  - Redundancy and autoscaling for availability/cost; load balancing (L4 faster, no content inspection; L7 content-aware, smarter but slower; round-robin, least-connection, hashing).
  - Indexing first for read performance: B-Tree default; GIN/trigram for full-text/`%text%`; partial indexes; column order matters; indexes slow writes so create only used ones and drop unused.
  - Replication (fault tolerance/perf, can be async); partitioning (horizontal/vertical/range) when data outgrows one DB; hot/warm/cold storage tiers; database federation (scale and single source of truth vs no cross-DB joins, lost ACID, more complexity); denormalisation (faster reads vs costly writes, redundancy, inconsistency risk); materialized views for periodic data (stale, not real-time); multitenancy models (shared federated DB, DB per tenant, sharded) chosen by scale.
  - SQL vs NoSQL: SQL is the right default main DB for most projects (ACID, structure, vertical scaling, up to millions of users); NoSQL for unstructured, self-contained data and horizontal sharding at very large scale; never assume NoSQL is faster (query patterns decide; cited PostgreSQL vs MongoDB benchmark).
  - Identifiers: consider UUIDv7, Snowflake, ULID or composite keys instead of serial ints / UUIDv4; time-encoded ids help sorting and index locality.
  - Connection pooling (PgBouncer, PgCat) because per-client connections are expensive; poolers add cost/complexity.
  - Caching strategies (cache-aside, write-through, write-behind, refresh-ahead); distributed caches via DHT; CDNs for static assets and latency.
  - Coupling: break location coupling with DNS, load balancers, client-side sharding, brokers (broker pattern); break temporal coupling with message queues (RabbitMQ, Kafka), each message processed once by an idempotent consumer; each component owns its data and logic — never share business data across services (share ids, duplicate small data like email only with guaranteed update propagation); components independently deployable; shared-nothing architecture; selective data replication (local copies updated by events or polling; lower latency and dependency vs staleness); event-driven architecture (events are broadcasts of what happened); designing around dataflow (subscribe to change streams and keep derived data updated, spreadsheet analogy; from Designing Data-Intensive Applications).
  - Consistency: weak/strong/eventual models; study the fallacies of distributed computing before adding complexity; use different stores for OLTP/OLAP/cache/search/graph but never dual-write naively.
  - Distributed transactions: 2PC (strong but blocking, slow, coupled, rarely used); sagas (local transactions + compensations, eventually consistent) — orchestration (central coordinator, explicit, trackable) vs choreography (decentralised, flexible but implicit and hard to troubleshoot; consider a workflow engine); mixing is fine; process manager = stateful state machine (sagas usually stateless; terms often conflated); workflow engines (Temporal, Airflow, Google Cloud Workflows, Camunda, Prefect, Conductor; bpmn.io).
  - Dual-writes problem: never `save` then `publish` as two steps; use the outbox pattern (event stored in the same transaction, relayed by Debezium/polling; unnecessary with event sourcing) or retry jobs with idempotent consumers; idempotent consumer stores an idempotency token (event id or client UUID) atomically under a unique constraint; some actions naturally idempotent (set username), others not (charge card); extend idempotency end-to-end so double-submitted forms execute once; CDC (Debezium → Kafka) as a safer alternative to multi-store writes.
  - Time: wall clocks unreliable for ordering (drift, NTP jumps); Lamport timestamps (max+1), vector clocks (per-node counters, detect causality violations); CRDTs (Automerge) merge concurrent updates; consensus (Byzantine generals, Raft leader election, Paxos).
  - Event sourcing (immutable append-only events, replay for state); CQRS (separate read/write models; pairs with event sourcing but does not require it); projections as left-fold/reduce — batch events, compute in memory with pure functions, batch DB writes; actor model (Erlang, Akka) for concurrent real-time systems.
  - API federation (one unified API/GraphQL over many services); chaos engineering (controlled failures, usually in production, with observability in place; Chaos Monkey, Gremlin, Chaos Mesh); distributed tracing is a must-have for complex systems (OpenTelemetry); bulkhead isolation (ship compartments); local-first software; consistent hashing / hash ring (minimal key movement on node change); P2P, gossip, DHT (Kademlia, Chord); OSI 7 layers (helps reason about L4 vs L7 balancing).
- Definitions / vocabulary: performance, availability (uptime %), scalability (vertical vs horizontal), location/temporal/data coupling, dual write, distributed monolith, compensating transaction, orchestration vs choreography, process manager, OLTP vs OLAP, CQS vs CQRS, Lamport timestamp, vector clock, CRDT, hash ring.
- Examples / idioms: dual-write anti-pattern `await db.save(user); await bus.publish(event)`; `CREATE MATERIALIZED VIEW`; projections as `events.reduce(...)` (JS); `ProductPriceUpdatedEvent`/`ORDER_CREATED` events.
- Trade-offs / anti-patterns: sync microservice chains; shared business data; naive dual writes; choreography for complex stateful flows; unused indexes; assuming NoSQL is faster; multi-store writes without idempotency; 2PC blocking; sagas need compensation logic; denormalisation/materialized views/replication trade freshness for speed.
- Resources listed: Kleppmann's Designing Data-Intensive Applications (must-read), System Design Interview (Xu), Microsoft Cloud Design Patterns, Fowler's Patterns of Distributed Systems, microservices.io, System Design Primer, awesome-distributed-systems, aphyr distsys-class, CodeOpinion/InfoQ channels.

## Slonik — gajus (GitHub README) — https://github.com/gajus/slonik
- Cited by README at line 13 in section "Domain-Driven Hexagon" (intro) to support: the PostgreSQL client used for database access in the examples.
- Fetch note: the repository page showed only metadata; content below is from the raw README (`raw.githubusercontent.com/gajus/slonik/main/README.md`).
- What it argues / defines:
  - A Node.js PostgreSQL client with runtime and build-time type safety and composable SQL, built on node-postgres via a driver factory (`@slonik/pg-driver`).
  - Philosophy: write raw SQL in tagged templates; discourage ad-hoc dynamic SQL generation and query builders (argues against Knex-style builders); not an ORM.
  - Problems it targets: repetitive result-shape checks, no type safety on results, unsafe connection/transaction release, SQL injection from string-built queries.
- Recommendations and rules:
  - Only `sql` tagged templates are accepted; plain strings are rejected; values go through `${}` placeholders → bound parameters; never concatenate input.
  - Do not hand-build query objects (Slonik queries are frozen); use `sql.identifier([...])` for identifiers; `sql.literalValue` only for utility statements (CREATE USER, ALTER…), never for data; `sql.unsafe` is for development — production uses `sql.type(zodSchema)`, `sql.typeAlias(name)` or `sql.fragment`; never put `$slonik_` literals in fragments; sanitise untrusted JSON before `sql.json`/`sql.jsonb` (null bytes and unpaired surrogates are rejected, not sanitised).
  - Prefer `one`/`many`/`maybeOne`/`oneFirst`/`manyFirst`/`maybeOneFirst`/`any`/`anyFirst`/`exists` over raw `query` so row-count assertions happen automatically (unchecked results corrupt data downstream); use `record` over `Object.fromEntries` (errors on duplicate keys); let `SchemaValidationError` propagate rather than handling per query; avoid Zod `.passthrough()`, use `.strict()`.
  - Never check out connections manually: `pool.connect(fn)` releases on resolve/reject; `transaction(fn)` commits/rolls back on settle; nested transactions become savepoints; `pool.query` inside a transaction callback throws `UnexpectedForeignConnectionError` (override `dangerouslyAllowForeignConnections` exists); `pool.query` may hit different backends — use `connect()` for same-session work; connection reset runs `DISCARD ALL` (heavy; disable only when appropriate); `pool.end()` does not kill active work; `pg-native` unsupported.
  - Performance/shape: prefer `sql.array(values, 'int4')` (`= ANY(...)`) over `sql.join` for value lists (stable query text for pg_stat_statements, shorter parse, empty arrays OK); prefer `sql.and`/`sql.or`/`sql.list` over `sql.join` (readable, parenthesised; `sql.join` for custom glue like UNION ALL / ORDER BY); bulk inserts via `jsonb_to_recordset` + `sql.jsonb` (supersedes `unnest`); hoist/compile Zod schemas (`zod-compiler` preferred); `sql.binary` for bytea, `sql.date`/`sql.timestamp`/`sql.interval` for temporal values, `sql.uuid` for UUIDs.
  - Prepared statements (`sql.prepared`) are connection-scoped — use only inside `pool.connect`/transaction and only for repeated, planning-expensive queries; `DISCARD ALL` deallocates them.
  - Timeouts are aggressive by default (connectionTimeout 5 s, idleTimeout 5 s, idleInTransactionSessionTimeout 60 s, statementTimeout 60 s); adjust per long statement rather than globally; `DISABLE_TIMEOUT` to disable; pool defaults maxPoolSize 10, minPoolSize 0, maximumConnectionAge 30 min (no sizing guidance).
  - Read-only routing via `beforePoolConnection` is risky; prefer separate pool instances (a `@volatile` comment as escape hatch); interceptors need a mandatory `name` and run in array order.
  - Errors: all extend `SlonikError`; branch on `instanceof` and on `columns`, not on `constraint` names (implementation detail) or `cause` (driver error, debugging only); `columns` is empty for expression/partial indexes (fall back to `constraint`/`detail`); `BackendTerminatedError` must be handled at connection level (outer scope around nested `pool.connect`); after `StatementCancelledError`/`StatementTimeoutError` the connection is still usable.
  - Migrations intentionally excluded (author prefers Flyway; community: node-pg-migrate, @slonik/migrator); logging via Roarr (`ROARR_LOG=true`; query logging and `captureStackTrace` need `slonik-interceptor-query-logging`, which adds overhead); type functions' parameters as `DatabaseConnection`.
- Definitions / vocabulary: pool/connection/transaction connection types (`DatabasePool`, `DatabasePoolConnection`, `DatabaseTransactionConnection`, `CommonQueryMethods`); interceptor hooks (`beforePoolConnection`, `afterPoolConnection`, `beforePoolConnectionRelease`, `transformQuery`, `beforeTransformQuery`, `beforeQueryExecution`, `afterQueryExecution`, `beforeQueryResult`, `transformRow(Async)`, `queryExecutionError`, `dataIntegrityError`); error classes (`NotFoundError`, `DataIntegrityError`, `ConnectionError`, `BackendTerminatedError`, `StatementTimeoutError`, `StatementCancelledError`, `UnexpectedForeignConnectionError`, `SchemaValidationError`, `InvalidInputError`, `IntegrityConstraintViolationError` + unique/foreign-key/not-null/check subclasses, `TupleMovedToAnotherPartitionError`); transaction events `commit` (top level only), `rollback`, `savepoint`, `rollbackToSavepoint` with `transactionId`/`transactionDepth`; query retry on Transaction Rollback class errors (`queryRetryLimit`/`transactionRetryLimit`, default 5); type parsers (date, int8, interval→seconds, numeric, timestamp(tz)→ms; `createTypeParserPreset`, per-tag overrides via `createSqlTag({typeAliases, typeParsers})`); `parseDsn`/`stringifyDsn`.
- Examples / idioms (TS): `await pool.connect(c => c.query(sql.unsafe\`SELECT 1\`))`; `await conn.one(sql.type(schema)\`SELECT ... WHERE id = ${id}\`)`; `sql.and([sql.fragment\`a = ${a}\`, b && sql.fragment\`b = ${b}\`])` drops falsy members; `sql.identifier(['schema','table'])`; `sql.join(cols, sql.fragment\`, \`)`.
- Trade-offs / caveats: runtime validation is an opt-in recipe needing a user-written result-parser interceptor (sub-0.1 ms per row, ~25 ms per 100k rows); dynamic SQL deliberately restricted; no configurable transaction options, custom type formatting, raw text queries; footguns: `pool.end()` leaves active work, `sql.join` does not parenthesise, `sql.literalValue` bypasses parameterisation, named prepared statements are session-scoped; README compares itself with pg (minimal), pg-promise (mature, more contributors, disputed claims removed) and postgres (bare-bones tagged templates).

## Domain-driven design — Wikipedia — https://en.wikipedia.org/wiki/Domain-driven_design
- Cited by README at line 84 in section "Architecture" to support: DDD as one of the combined architectural styles.
- What it argues / defines:
  - DDD models software around the business domain with input from domain experts; code vocabulary (classes, methods) should mirror the domain; coined by Eric Evans (2003 book).
  - Rejects one unified model: large systems split into bounded contexts, each with its own model; three pillars: ubiquitous language, strategic design, tactical design.
- Recommendations and rules: focus on the core domain and its logic; base complex designs on a model; iterate the model with domain experts; keep models consistent inside explicit bounded-context boundaries; draw a context map; keep shared kernels small; use an anticorruption layer to translate upstream models; outside objects reference only aggregate roots, and roots enforce consistency; use repositories for retrieval, factories for creation, services for behaviour that belongs to no object; keep domain events lightweight within a context and integration events richer (overcommunicate) across contexts; apply DDD only to complex domains (Microsoft guidance).
- Definitions / vocabulary: domain; domain model; ubiquitous language; entity (identity, e.g. seat number); value object (immutable, attribute-defined, no identity, e.g. business card); domain event (past fact experts care about); aggregate / aggregate root (car vs engine/brakes); repository; factory; service; bounded context; context map; subdomain; context-mapping patterns (partnership, shared kernel, customer/supplier, conformist, anticorruption layer, open-host service, published language, separate ways, big ball of mud boundary); command (state-changing call on an aggregate) vs query (read-only); event store; event storming; naked objects; DSL.
- Related approaches: not tied to OO but uses it (aggregate roots receive commands, state encapsulated in roots); POJO/POCO; AOP for cross-cutting concerns; MDE/MDA compatible but different intent (platform translation vs domain understanding); CQRS (from Meyer's CQS; not required by DDD; aggregate root enforces logic, command handler manages persistence/transactions); event sourcing (commands produce persisted events, often published on a broker; aids verification tools and optimistic concurrency); microservices mapping one-to-one (ideal), one-to-many (split for scale) or many-to-one (merged for simplicity); event storming as a precursor.
- Trade-offs / criticisms: substantial isolation/encapsulation effort needed to keep the model pure; benefits conditional on domain complexity; article flagged for lacking citations; many legacy systems have no clean boundaries (big ball of mud pattern).
- Tools named: Actifsource, Context Mapper, CubicWeb, OpenMDX, Restful Objects, DDD Crew canvases.

## Hexagonal architecture (software) — Wikipedia — https://en.wikipedia.org/wiki/Hexagonal_architecture_(software)
- Cited by README at line 85 in section "Architecture" to support: Ports and Adapters as one of the combined styles.
- What it argues / defines:
  - Invented by Alistair Cockburn (renamed "Ports and adapters" in 2005; book with Juan Manuel Garrido de Paz, April 2024); loosely coupled, interchangeable components connected through ports and adapters; eases substitution and test automation; an alternative to layered architecture.
  - Motivation: avoid undesired dependencies between layers and UI code contaminated with business logic.
- Recommendations and rules: components (core, DB, UI, tests, other systems) interact only through exposed ports; each port has a protocol forming an abstract API implementable by method calls, RPC or web services; port granularity is free (one port, or ports per event source / notifications / database / administration, or one per use case); adapters are the glue translating between the outside and the ports; several adapters per port (GUI, CLI, automated feed, test scripts).
- Definitions / vocabulary: port; adapter; application core; "hexagonal" refers to the drawing (room for many interfaces), not six ports.

## The Clean Architecture — Robert C. Martin (Clean Coder blog, 13 Aug 2012) — https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
- Cited by README at line 87 in section "Architecture" to support: Clean Architecture as one of the combined styles.
- What it argues / defines:
  - Hexagonal (Cockburn; used in Freeman & Pryce's GOOS), Onion (Palermo), Screaming (Martin), DCI (Coplien, Reenskaug) and BCE (Jacobson) all pursue separation of concerns by layering, with at least one layer for business rules and one for interfaces.
  - Shared result: systems independent of frameworks (used as tools, not constraints), testable without UI/DB/web server, UI-independent, database-independent, and independent of any external agency.
  - The integrating idea is The Dependency Rule: source-code dependencies point only inward.
- Recommendations and rules:
  - Nothing in an inner circle may know anything about an outer circle: no outer-circle name (function, class, variable, any named entity) may be mentioned inside; outer data formats (especially framework-generated ones) must not be used inward; nothing outer should impact inner circles.
  - Entities (innermost): enterprise-wide business rules as objects with methods or data structures plus functions; reusable by many applications (or the app's business objects in a single app); least likely to change when externals change — page navigation or security changes must not touch them.
  - Use cases: application-specific business rules; implement and encapsulate every use case; orchestrate data flow to/from entities and direct entities to apply their rules; isolated from DB/UI/framework changes; change only when application operation changes.
  - Interface adapters: convert between the form convenient for use cases/entities and the form convenient for DB/web; the whole MVC lives here (presenters, views, controllers; models are plain data structures passed controller → use case → presenter/view); all SQL confined here; adapters for external services convert external data into internal form.
  - Frameworks and drivers (outermost): DB, web framework, tools; mostly glue code; keep details outside where they do little harm.
  - Four circles are schematic — add layers if needed, but the Dependency Rule always holds and abstraction/policy level rises inward.
  - Crossing boundaries: control flow may go controller → use case → presenter while dependencies all point inward, via the Dependency Inversion Principle: the use case calls an inner "Use Case Output Port" interface that the outer presenter implements; use dynamic polymorphism at every boundary so source dependencies oppose control flow (in Java, arrange interfaces/inheritance accordingly).
  - Data crossing a boundary must be simple isolated structures (structs, DTOs, arguments, hashmaps, plain objects) in the form most convenient for the inner circle; never pass Entities or database rows / framework row structures inward.
  - Conclusion: separate into layers, obey the Dependency Rule, and the system is intrinsically testable; obsolete externals (DB, web framework) can be replaced with minimal fuss.
- Definitions / vocabulary: Dependency Rule; Entities; Use Cases (Interactors); Interface Adapters; Frameworks and Drivers; Use Case Output Port.
- Trade-offs / caveats: none stated beyond the warning that framework row structures and entities must not leak across boundaries.
- How it applies to TypeScript/NestJS: README's application services = use-case circle; controllers/DTO mapping/repositories = interface adapters; NestJS, Slonik and HTTP = frameworks/drivers; ports = output ports implemented by infrastructure.

## Onion Architecture — Herberto Graça (21 Sep 2017) — https://herbertograca.com/2017/09/21/onion-architecture/
- Cited by README at line 88 in section "Architecture" to support: Onion Architecture as one of the combined styles.
- What it argues / defines:
  - Onion Architecture was coined by Jeffrey Palermo in 2008; it builds on Ports & Adapters by putting the domain at the centre, externalising delivery mechanisms (UI) and infrastructure (ORM, search engines, third-party APIs), and adding DDD-inspired internal layers inside the business logic.
  - Traditional layering is four layers (presentation, application, domain, persistence); Ports & Adapters reduces it to two concentric ones (external, internal); enterprise apps need more than two, hence the internal rings.
- Recommendations and rules:
  - Outer layers depend on inner layers; inner layers know nothing of outer ones; coupling direction points toward the centre; outer layers can change without touching inner, more important ones.
  - Palermo's tenets: the application is built around an independent object model; inner layers define interfaces, outer layers implement them; coupling direction is toward the centre; all application-core code compiles and runs separately from infrastructure.
  - Any outer layer may call any inner layer directly (Palermo and Fowler agree): strict layer-by-layer calls only produce proxy methods/classes without business logic.
  - Adapter code keeps infrastructure from leaking into the core; mocks can replace delivery/infrastructure so the core runs alone — good for testing.
- Definitions / vocabulary: delivery mechanism (UI), infrastructure (ORM, search, third-party APIs), domain model at the core, DIP applied at architecture level.
- Trade-offs / caveats (from the author's replies in comments): disagrees with Palermo placing repository interfaces in the domain-services layer — the domain should know nothing about persistence, so repository interfaces belong in the application layer; alternative is ports for the ORM instead of repository interfaces (repository ports simpler but changes spread across all repositories; ORM ports more correct but more complex and error-prone); choice usually left to the team with little practical difference; post reads best with the earlier series entries (EBI, DDD, Ports & Adapters).
- How it applies to TypeScript/NestJS: the README follows the author's position — repository ports live in the application/module layer and are implemented in infrastructure.

## SOLID — Wikipedia — https://en.wikipedia.org/wiki/SOLID
- Cited by README at line 89 in section "Architecture" to support: SOLID principles as one of the combined foundations.
- What it argues / defines: mnemonic for five OO design principles making code more understandable, flexible and maintainable; principles introduced by Robert C. Martin (2000 paper on design principles / software rot, later "the first five principles"); acronym coined by Michael Feathers around 2004; also a core philosophy of agile/adaptive development.
- Recommendations and rules:
  - SRP: a class should have only one reason to change → maintainability, testability, flexibility, changes to one responsibility do not ripple.
  - OCP: open for extension, closed for modification → add features without editing existing code, fewer regressions, adaptability.
  - LSP: code using base-class references must work with derived classes without knowing → polymorphism, reliability, predictability; linked to design by contract.
  - ISP: clients must not depend on methods they do not use → decoupling, targeted implementations, no needless dependencies.
  - DIP: depend on abstractions, not concretions → loose coupling, swappable implementations, testability, maintainability.
- Trade-offs / criticisms: the article names none; see-also: code reuse, GRASP, inheritance, design by contract.

## BoundedContext — Martin Fowler (bliki, 15 Jan 2014) — https://martinfowler.com/bliki/BoundedContext.html
- Cited by README at line 103 in section "Pros" to support: splitting along bounded-context lines makes later extraction of microservices easy.
- What it argues / defines:
  - Bounded Context is the central pattern of DDD strategic design (large models, large teams): divide a big model into contexts and make their interrelationships explicit.
  - A model is both the ubiquitous language with domain experts and the design basis; it must be internally consistent (unified).
  - A single unified model of a large domain is not feasible or cost-effective (Evans): different groups use subtly different vocabularies — polysemes like "customer", "product", or "meter" (grid-to-location connection vs grid-to-customer connection vs physical device at an electricity utility) — which conversation smooths over but software cannot.
- Recommendations and rules: give each context its own unified model (multiple canonical models); be explicit about boundaries and relationships; a context map is usually worthwhile; provide mapping mechanisms for concepts that differ across contexts; human culture/language is the dominant boundary factor (a vocabulary change signals a different model); representation differences (in-memory vs relational model) also draw boundaries; Evans's "bubble context" lets new functionality be grafted onto legacy systems via a mapped, distinct model.
- Examples: support tickets exist only in the customer-support context while products and customers are shared concepts; Kent's "oil wells" polyseme (Data and Reality).
- Trade-offs / caveats: boundaries are subtle and may reflect history and human relationships as much as domain concepts (Verraes, Wirfs-Brock); integration requires mapping between models; the page does not detail duplication costs.
- References: Evans DDD Part IV; Vernon IDDD ch. 2-3.

## Loose coupling — Wikipedia — https://en.wikipedia.org/wiki/Loose_coupling
- Cited by README at line 147 in section "Modules" to support: public interfaces/messaging between modules ensure loose coupling so internals can be refactored and modules extracted.
- What it argues / defines: components weakly associated so that changes in one least affect another; little or no knowledge of other components' definitions (classes, interfaces, data, services); opposite of tight coupling; in programming, loose coupling = depending on an interface rather than a concrete class (dependency inversion), tight coupling = pointing directly at a concrete class.
- Dimensions (Josuttis, SOA in Practice; each with a tight counterpart): physical connection via mediator; asynchronous communication; simple common data types; weak type system; data-centric self-contained messages; distributed control of process logic; dynamic binding; platform independence; business-level compensation instead of system transactions; deployment at different times; implicit upgrades in versioning; four autonomies: reference, time, format, platform; ESBs and event-driven architecture pursue it.
- Recommendations (ways to decrease coupling): publish data in standard formats (XML/JSON); use standard data types in parameters; pass only key data (e.g., customer id) so services can be called in any order; depend on interfaces; use function objects/callbacks so receivers need not know callers.
- Benefits: replaceable implementations; independence from platform/language/OS/build; replication gives availability; swappable classes enable extensibility.
- Trade-offs: decoupling in time makes transactional integrity hard and needs coordination protocols; replication causes consistency/synchronisation problems; over-engineered or misplaced ESBs recreate tight coupling and a central hotspot; data-element coupling measured by how many message changes (add, reorder, rename, restructure, omit) break communication.
- Related: cohesion, connascence, Law of Demeter, separation of concerns, cascading failure.

## Modular programming: Beyond the spaghetti mess — Millie Macdonald, Tiny blog (28 Jun 2023) — https://www.tiny.cloud/blog/modular-programming-principle/
- Cited by README at line 158 in section "Modules" to support: further reading on modules.
- What it argues / defines:
  - Modular programming (1960s idea) remains relevant: split programs into independent building blocks each holding everything for one aspect of functionality; modules nest; Tiny builds TinyMCE and its libraries (Katamari, Sugar, Bedrock) this way; package managers and frameworks now favour small single-purpose packages.
  - Levels of modularity: functions within files, files within libraries/repos, libraries within projects; module types: program-control modules (coordinate others) and specific-task modules; an interface/API is a contract stating what a module does, returns and how outside code may use it; monolith = everything in one place → spaghetti.

- Trade-offs / anti-patterns: over-modularisation (too many tiny functions, data passed across too many files); bundle size and performance if dependencies cannot be tree-shaken; unnecessary complexity for small/personal projects; monoliths claimed harder to tamper with; organic decay when code is bolted on without understanding the architecture; structural overhauls hard to schedule against features.

## What are Modules in Domain Driven Design? — Philip Brown, Culttt (10 Dec 2014) — https://www.culttt.com/2014/12/10/modules-domain-driven-design/
- Cited by README at line 159 in section "Modules" to support: further reading on modules.

## Command–query separation — Wikipedia — https://en.wikipedia.org/wiki/Command%E2%80%93query_separation
- Cited by README at line 229 in section "Commands and Queries" to support: separating methods into state-changing commands and data-returning queries.
- What it argues / defines: Bertrand Meyer's principle (Eiffel): every method is either a command (performs an action, returns nothing) or a query (returns data, no side effects); "asking a question should not change the answer"; a method may return a value only if referentially transparent and side-effect free.
- Reasoning / benefits: suits design by contract — assertions are annotations, so running them must not change state, and side-effect-free queries can be called from any assertion; enables reasoning about state without changing it; assertion checks can be disabled for performance without behavioural change; may prevent some heisenbugs; simplifies programs by separating states from state changes (flagged citation needed).

## Universally unique identifier — Wikipedia — https://en.wikipedia.org/wiki/Universally_unique_identifier
- Cited by README at line 239 in section "Commands" to support: letting clients generate a UUID so commands need not return a server-generated id.
- What it argues / defines: 128-bit identifier (Microsoft: GUID) generated without a central registry; canonical 8-4-4-4-12 hex form, lowercase preferred, `urn:uuid:` form; origins in Apollo NCS (1987) → OSF DCE → RFC 4122 (2005, now obsoleted) → RFC 9562 (May 2024, adds v6-v8); ITU-T X.667 equivalent.
- Versions: v1 time (100 ns ticks since 1582) + clock sequence + node (MAC or random with multicast bit); v2 DCE security (local ids; mostly unsupported); v3 MD5 name-based; v4 random (122 bits); v5 SHA-1 name-based (preferred over v3); v6 time-ordered reordering of v1; v7 48-bit Unix-ms timestamp + counter/random bits, no MAC; v8 implementation-defined (uniqueness not guaranteed); nil (all zeros) and max (all ones) UUIDs; variants 0/1/2/3 (variant 1 is the standard layout, variant 2 Microsoft COM byte order).
- Collision figures: ~2.71×10^18 random v4 values for a 50% collision chance; ~103 trillion for one-in-a-billion; bit flips are a likelier source of duplicates than generation; weak randomness and reused EUI-64 addresses raise risk.
- Recommendations / trade-offs for developers: decentralised generation and a fixed-size key space make UUIDs good client-generated ids; random keys (v3/v4/v5) scatter inserts and fragment indexes, and v1/v2 field order hurts primary keys — prefer time-ordered v6/v7 (new rows at the index end; ordering holds best when all ids come from one generator); database support: PostgreSQL native type (modules generate most versions), SQL Server `NEWID()`/`NEWSEQUENTIALID()`, MySQL `UUID()` is v1, Oracle `SYS_GUID()` non-standard.
- Security / privacy caveats: v1/v2/v6 can leak the generating machine's MAC (Melissa virus author traced this way); timestamp-bearing versions (v1/v2/v6/v7) reveal creation times and business volumes; name-based inputs recoverable only by brute force; RFC warns never to use any UUID as a security capability without analysis; v7 bit allocation and guessability are implementation-dependent.

## CQS versus server generated IDs — Mark Seemann (ploeh blog, 11 Aug 2014) — https://blog.ploeh.dk/2014/08/11/cqs-versus-server-generated-ids/
- Cited by README at line 239 in section "Commands" to support: client-generated UUIDs let a Create command return nothing yet give the caller an id.
- What it argues / defines: CQS can be kept even when a Create seems to need a server-generated id; breaking CQS here is a conscious trade-off, never a necessity; the common `int Create(T item)` design makes a side-effecting method look like a query, is a leaky abstraction (assumes the store assigns ids) and risks LSP violations for stores that cannot generate ids; the "CQS is impossible here" comment is an apology for not seeing alternatives.
- Options and verdicts:
  - `void Create(Guid id, T item)` with a client-generated GUID — the easiest proper command; costs: some databases (SQL Server) perform worse with GUID keys, GUIDs are long and error-prone when humans read them aloud (support-case numbers).
  - GUID command plus a separate query `int GetHumanReadableId(Guid id)` backed by a secondary index — for cases needing integers; possibly two round trips, mitigated because the integer is rarely needed at creation time.
  - `T CreateEntity()` + `void AttachEntity(T)` (reader proposal) — acceptable only if `CreateEntity` has no side effects; the author objects to writable ids because an entity without an id is an invalid state — make the id a mandatory constructor argument (`new Foo(Guid id)` throwing on `Guid.Empty`).
  - Repository events are fine for commands (events are side effects) but not for queries; Hi/Lo batch allocation (reader comment, not endorsed); natural keys and out parameters not discussed.
  - Meyer's stack: strict CQS needs `Pop` + `Top`, which is not thread-safe or convenient — CQS is not mandatory everywhere.
  - REST boundary: `POST /api/users` → `202 Accepted` + status URL (robust, harder for UI devs) or `201 Created` + `Location` + representation (easier); orthogonal to CQS because applications are not object-oriented at their boundaries.
  - Child entities of an aggregate have no identity of their own — integer keys as an implementation detail are fine; tables may combine `INT IDENTITY` clustered primary key with a `UNIQUEIDENTIFIER PublicId` used by application code.
  - Commands returning `Either<Success, Failure>` with data still violate CQS: commands may expose only an error channel (`Task` as async void); errors belong on the left of Either.
  - The author avoids the Repository pattern (widely misunderstood) and lets clients own single-member interfaces per the DIP.
- Final recommendation: default to commands taking a client-supplied GUID and returning void; add a separate query when an integer/human-readable id is required; weigh the extra round trip; CQS ≠ CQRS.
- References: Meyer OOSC (stack example, side-effecting functions vs mathematical functions), Fowler's CQS bliki and PoEAA, Greg Young's CQRS writings, Evans DDD (entities/aggregate roots), REST in Practice, APPP (DIP ch. 11), Knuth on premature optimisation, Martin on apologies in code.

- Rules and caveats: register handlers, sagas and events as providers; models do not know the `EventBus` — connect them with `EventPublisher`; events dispatch on `commit()` (or immediately with `autoCommit = true`); `commit()` clears events so a second call republishes nothing; if an awaited `commit()` fails, roll back and rerun the command with a freshly loaded model; the default in-memory publisher does not await handlers while async publishers do; event handlers run outside the HTTP request context — exception filters do not catch their errors (use try/catch or a saga issuing a compensating command) and they cannot send HTTP responses (use WebSockets/SSE); exception filters do catch command-handler errors; sagas return an Observable of commands dispatched asynchronously, run in memory (a command is lost if the process stops between event and command — use durable workflows), and must be singletons; unhandled event-handler/saga exceptions are logged and pushed to `UnhandledExceptionBus` as `UnhandledExceptionInfo{exception, cause}` unless `rethrowUnhandled`; subscribe with `takeUntil` and clean up in `onModuleDestroy`; request-scoped handlers need an `AsyncContext` payload passed as the second `execute()` argument (and to `publish`/`mergeObjectContext`; sagas forward it via `AsyncContext.merge`).
- Examples (TS, compressed): `class KillDragonCommand extends Command<{actionId: string}>`; handler loads hero via repository, `publisher.mergeObjectContext(hero)`, `hero.killEnemy(id)`, `hero.commit()`; `class Hero extends AggregateRoot { killEnemy(id) { this.apply(new HeroKilledDragonEvent(...)) } }`; `@Saga() dragonKilled = events$ => events$.pipe(ofType(HeroKilledDragonEvent), map(e => new DropAncientItemCommand(...)))`; `@Workflow('order-fulfilment') @StartOn(OrderPlacedEvent, {...})` with `ctx.step('charge-payment', ...)` and `ctx.waitForSignal(...)`.

## Command Query Separation — Khalil Stemmler — https://khalilstemmler.com/articles/oop-design-principles/command-query-segregation/
- Cited by README at line 282 in section "Queries" to support: further reading on CQS/CQRS.
- What it argues / defines: CQS is a general (not strictly OO) design principle: a method is either a command (changes state) or a query (returns data), never both; "asking a question shouldn't change the answer"; hidden side effects produce heisenbugs; CQRS is CQS at architecture level with separate read and write models; use cases sit in between (each strictly a command or a query).
- Recommendations and rules: callers must be able to tell from a signature whether state changes; never hide side effects inside queries (a `GET` job endpoint silently logging a view only for job-seekers gives inconsistent, untestable behaviour) — extract them into an explicit command (`POST /jobs/:jobId/view`) and let the UI make two calls; commands generally return only success/failure; avoid returning a created entity's id by generating ids in the domain layer rather than in persistence (not via Sequelize); names must reveal the kind (`approveComment` command, `getX` query) — a `postComment` that returns the saved comment is misleading, so split it into a void command plus a `getComment` query; each use case is strictly a command (`CreatePost`, `UpdatePost`, `DeletePost`, `PostComment`) or a query (`GetPostById`, `GetAllPosts`, `GetCommentById`); separate read and write models in DDD because writes must load full aggregates to enforce invariants (slower) and one model for both is expensive; keeping paths separate means query changes cannot break commands.
- Examples (TypeScript, compressed): violation `postComment(...): Promise<Comment>` creating via `CommentModel.create` and returning the mapped domain object; fix `postComment(comment: Comment): Promise<void>` + `getComment(id): Promise<Comment>`; service `Comment.create(...)` generates the id, then `commentRepo.postComment(comment)`, then Slack message using `comment.id`; quiz: only `approveComment(): Promise<void>` is a valid command; `getAllVinyl(): Promise<void>` is not a query; `getVinylById` returning an array is confusing; mappings: CRUD C/U/D commands and R query; HTTP POST/PUT/DELETE/PATCH commands and GET query; SQL mostly commands except SELECT.
- Trade-offs / caveats: returning created data can be justified when a downstream step needs the id, but the preferred fix is domain-generated ids; CQS is rarely considered in simple CRUD apps and shines in complex DDD domains; CQRS adds architectural complexity; stack `pop()` and Result types not covered.

## Exposing CQRS Through a RESTful API — Ali Kheyrollahi, InfoQ (Dec 2013) — https://www.infoq.com/articles/rest-api-on-cqrs/
- Cited by README at line 283 in section "Queries" to support: further reading on CQRS over REST.
- What it argues / defines: a CQRS system (Greg Young's m-r / SimplestPossibleThing, ASP.NET Web API, AngularJS) can be exposed RESTfully; HTTP semantics absorb distributed concerns such as eventual consistency and concurrency; CQRS splits asynchronous, transactionally stored commands from eventually consistent reads served from denormalised views; m-r uses event sourcing (state rebuilt by replaying versioned events); domain events are granular and unsuited to cross-context integration; "public domain" = externally visible resources and messages, distinct from the internal domain; output model preferred over "view model".
- Recommendations and rules:
  - Expose and document the public domain, never the internal domain (internal `Version` becomes an opaque string ETag); schemas/message names are part of the contract (WADL, Swagger, RAML, RestDown).
  - Model the root entity as resources `/api/InventoryItem` and `/api/InventoryItem/{id}` with GUID ids; a `/{id}/Stock` sub-resource was considered and rejected as a mere nicety.
  - Queries: collection GET returns ids and names, detail GET full fields; content negotiation via Accept; ETags from content hashes or concatenated ids/names, `If-None-Match` → 304; `max-age=0` so clients revalidate; encrypt numeric versions (AES) so ETags are opaque and unguessable; invalidate list caches on add/remove/rename; reusable `IConcurrencyAware` + global `ConcurrencyAwareFilter`.
  - Commands: avoid RPC-style URIs (`/{id}/rename`); do not route on the body (bodies stream, buffering is not always possible); identify the command type in a `domain-model` parameter of Content-Type (level 4 of the Five Levels of Media Type, 5LMT); choose verbs by idempotency since no command verb is safe — PUT/PATCH/DELETE idempotent, POST not: Create = POST to collection; Deactivate = DELETE (logical, idempotent); Rename = PUT with concurrency check; CheckIn/Remove stock = POST (repeating changes the count again, even though PUT/PATCH "look" natural).
  - Responses: commands return 202 Accepted; only Create adds a `Location` of the future item; Rename uses `If-Match` with the opaque ETag — mismatch → 412 Precondition Failed via `ConcurrencyExceptionFilterAttribute`; concurrency checks are optional and client-driven, separate from internal event versions; do not apply version checks to commutative operations (concurrent stock additions would falsely conflict under load); perform the check synchronously so 202 means no conflict.
  - Support HEAD (routed to GET, body stripped, ETag kept), OPTIONS (Allow header + verb list; could later serve docs), 405 with Allow for unsupported verbs.
  - Media types: use 5LMT parameters (format, schema, domain model, version) on standard types instead of minting vendor types (registration burden, dictionary-based clients break); precedents `application/rss+xml`, `application/atom+xml`; version carried as `version=1.0.0.0` parameter.
- Examples (HTTP, compressed): `POST /api/InventoryItem` with `Content-Type: application/json;domain-model=CreateInventoryItemCommand` body `{"name":"CQRS Book"}` → 202 + Location; `DELETE /api/InventoryItem/{id}` (DeactivateInventoryItemCommand) → 202; `PUT /api/InventoryItem/{id}` (RenameInventoryItemCommand) with `If-Match` → 202 or 412; `POST /api/InventoryItem/{id}` (CheckInItemsToInventoryCommand) `{"count":"230"}`; AngularJS `$http` decorator adds the domain-model parameter from the payload constructor name (names must stay stable); source aliostad/m-r.
- Trade-offs / caveats: CRUD-verb mindset rarely matches real domain operations; leaking internals; guessable ETags; false conflicts on commutative ops; asynchronous checks undermine 202; client coupling to constructor names; prototype has an in-memory event store and in-process synchronous bus; eventual-consistency handling for clients and hypermedia are not developed.

## CQRS pattern — Microsoft Azure Architecture Center — https://docs.microsoft.com/en-us/azure/architecture/patterns/cqrs
- Cited by README at line 284 in section "Queries" to support: further reading on CQRS (fetched via its redirect to learn.microsoft.com).
- What it argues / defines: segregate reads and writes into separate data models to optimise each independently; a single CRUD model becomes hard to optimise as apps grow because read/write shapes differ (fields needed on update but not on read), parallel operations cause lock contention, data-store/DAL load and complex queries hurt performance, and overlapping read/write entities complicate security; commands update data and should express business tasks ("Book hotel room", not "set ReservationStatus"); queries never alter data and return DTOs without domain logic.
- Recommendations and rules: refine the command flow — client-side validation to avoid obvious failures (disable "Book" when no rooms), server-side handling of edge cases/races (waiting lists, alternatives), asynchronous command processing via queues; two levels of separation: distinct read/write models over one store (write model with validation and domain logic for transactional integrity; read model producing DTOs/projections) or separate stores (scale each, different technologies, e.g. document DB for reads and relational for writes); keep stores synchronised by publishing events from the write side; because brokers and databases rarely share a transaction, use the Transactional Outbox pattern and make read-model consumers idempotent; read store may be a materialized view or read-only replicas (multiple replicas cut latency and raise availability); scaffolding/ORM tools cannot generate CQRS code from a schema, so custom bridging logic is needed.
- Benefits: independent scaling (less lock contention), optimised schemas per side, security (only appropriate operations may write), separation of concerns (complex logic on the write side, simple read side), simpler queries via materialized views.
- Issues / considerations: significant complexity, especially with event sourcing; messaging brings failures, duplicates, retries (priority queues for mixed priorities); eventual consistency — stale reads, keeping the read store current, detecting users acting on stale data.
- When to use: collaborative environments with concurrent edits (granular commands reduce merge conflicts); task-based UIs and complex domain models (write model = full command stack with aggregates kept consistent; read model = no business logic, returns DTOs, eventually consistent); performance tuning where reads far outnumber writes (scale read model horizontally, few write instances); separate development concerns (teams per side); evolving systems; integration with other subsystems, especially event-sourced ones (failure isolation). Not suitable when the domain/rules are simple or CRUD UI and data access suffice.
- Workload design: supports the Performance Efficiency pillar (PE:05 scaling/partitioning, PE:08 data performance); weigh trade-offs against other pillars.
- Event sourcing combination: event store is the write model and single source of truth; read model builds denormalised materialized views from the same events, rebuildable by replay; reduces update conflicts on aggregates; considerations: eventual consistency, added complexity (code to generate/process events and assemble views, though history and intent are preserved), view-generation cost — use periodic snapshots of entity state or aggregated totals.
- Example (C#, compressed): read model `ProductsDao { FindById, FindByName, FindOutOfStockProducts, FindRelatedProducts }` returning `ProductDisplay`/`ProductInventory` DTOs; `ICommand { Guid Id }`, `RateProduct : ICommand { ProductId, Rating, UserId }`; `ProductsCommandHandler` implementing `ICommandHandler<AddNewProduct|RateProduct|AddToInventory|ConfirmItemShipped|UpdateStockFromInventoryRecount>` over `IRepository<Product>`: find product, `product.RateProduct(userId, rating)`, `repository.Save(product)`; commands typically arrive via a queue and are granular to reduce conflicts.
- Related patterns: Event Sourcing, Transactional Outbox, Idempotent consumer, Materialized View, Priority Queue, Event-driven architecture style.

## Dependency inversion principle — Wikipedia — https://en.wikipedia.org/wiki/Dependency_inversion_principle
- Cited by README at line 293 in section "Ports" to support: the core depends on ports (interfaces) with infrastructure implementations injected, so dependencies point inward.
- What it argues / defines: high-level (policy) modules should not import from low-level modules — both depend on abstractions; abstractions should not depend on details — details depend on abstractions; reverses the conventional top-down dependency so high-level modules are independent of implementation details; Robert C. Martin (1994 metrics paper, 1996 C++ Report article, 2003 book).
- Traditional vs inverted layering: direct policy→utility coupling limits reuse of policy; in the inverted pattern an abstract layer owned by the higher/policy layer (same package) is implemented by lower layers; upper layers can then use other implementations; adapters mediate when lower components are closed or reused; abstractions as abstract classes or interfaces; "direct" implementation keeps policy and abstractions in one library (low-level packages depend on high-level ones, choose direction to maximise reuse and kill cycles); "flexible" implementation extracts abstractions into their own packages per layer (reuse, robustness, portability); run-time wiring via plugin, service locator or dependency injection; DIP can be viewed as the adapter pattern (high-level class owns the adapter interface).
- Generalisation caveats: many projects apply DIP to every interface because an interface looks like a finished pattern and mocking tools push for it; full generalisation implies all member variables are interfaces/abstract types, concrete packages connect only via abstract packages, no inheritance from concrete classes, no overriding implemented methods, every instantiation via a factory or DI framework, static members rely on DI, every testable method implements an interface — more plumbing, restricted language features; generic interfaces everywhere make code harder to read when the only other implementation is a mock; implementing an interface is not enough — only abstracting the interaction reduces coupling; direct implementation makes low-level reuse harder.
- Benefits: loose coupling, policy reuse, swappable implementations (replace `CustomerHandler` without touching the UI), robustness/portability from separate packages, control over dependency direction (no cycles), testability by mocking, simpler interfaces, transparent local vs remote storage, supports SRP.
- Examples (compressed): Java `Car` constructing `GasEngine` → `Engine` interface with `GasEngine`/`ElectricEngine` injected via constructor; genealogy module hiding a relation graph behind derived-relation properties; file-server client interfaces (connection, folders/tags, file ops, search, conflict resolution, history) with local and remote implementations; MVC where `Page` (UI) depends on `ICustomerHandler` created by a factory and passes an `IPageViewer` so handlers talk back without a concrete dependency.
- Related: inversion of control and DI listed (DI is one provisioning mechanism; sources argue injecting is not the same as following DIP); Hollywood principle not mentioned.
- How it applies to TypeScript/NestJS: port interfaces live beside the application services that own them; implementations in infrastructure are bound via NestJS providers with injection tokens.

## Mock object — Wikipedia — https://en.wikipedia.org/wiki/Mock_object
- Cited by README at line 297 in section "Ports" to support: ports let application logic be tested in isolation by mocking implementations.
- What it argues / defines: a mock imitates a production object in limited ways (a test double, also usable in generic programming), substituted when the real object is impractical: non-deterministic results (time, temperature), hard-to-reproduce states (network error), slow (prepared database), not yet existing or changing, or would need test-only members; crash-test-dummy analogy.
- Terminology: inconsistent across literature; stub = pre-arranged responses; fake = anything not real (Osherove) — a stub or a mock; mock = a fake that decides pass/fail by verifying an interaction occurred; complexity ranges from canned answers to full logic imitation; Fowler's "Mocks Aren't Stubs" (classical vs mockist schools) cited only as an external link.
- Usage: same interface as the real object; frameworks let tests specify expected calls, order, parameters and return values and verify them; mock-only settings force exceptions, hangs or nulls to test failure handling; logging mocks count calls (exposing redundant saves); in TDD, test an area in isolation without databases/web services/networks so tests stay fast; integration tests remain necessary after mocks are replaced by real objects.
- Limitations: over-specifying order/counts couples tests to implementation and breaks refactoring; heavy mocking inflates maintenance; mocks drift from real behaviour (especially for other teams' or not-yet-written objects) and can let tests pass while production fails; mocking one method may need less setup than building a real object; unit tests should check external behaviour, not internals.
- Examples: mock time service for an alarm clock; authorisation mock with `isUserAllowed` controlled by an `isAllowed` setting; database mock logging `save(person)` calls; sources: Osherove, Beck, Feathers.
- How it applies to TypeScript/NestJS: `jest.fn()` / `jest.mock` implementations passed to ports in the README's fast use-case tests.

## Unit testing — Wikipedia — https://en.wikipedia.org/wiki/Unit_testing
- Cited by README at line 297 in section "Ports" to support: mocking ports is useful for unit testing.
- What it argues / defines: unit (component/module) testing validates isolated source code against expected behaviour; a unit is a single behaviour tied to a requirement — entry points to externally visible behaviour, not necessarily one function/class; manual or automated (automation gives frequent, cheap, repeatable runs); history: SAGE "parameter testing" (1956), Mercury (1964), MIL-STD-483/490, Beck's SUnit (1989), JUnit (1997, Beck & Gamma), xUnit family, Google's automated-testing adoption (~2005-06).

- Tools / examples: xUnit, JUnit, TestNG, NUnit, SUnit; built-in support in Rust, D, Cobra; standard libraries (Python unittest, Go testing, Julia Test, Ruby Minitest, …); community frameworks for C++, C#, Java, JavaScript, PHP, Perl, PowerShell Pester, R testthat, …; JUnit `Adder` example (0+0, 1+2, −1+−2, 1234+988); tests can be rendered into diagrams as specifications.

## Interface segregation principle — Wikipedia — https://en.wikipedia.org/wiki/Interface_segregation_principle
- Cited by README at line 301 in section "Ports" to support: split large port interfaces into smaller ones when it makes sense, without overdoing it.
- What it argues / defines: no code should be forced to depend on methods it does not use; split fat ("polluted") interfaces into client-specific role interfaces so clients know only relevant methods; one of the five SOLID principles; akin to GRASP high cohesion; also a key principle of distributed-system design and one of the IDEALS microservice principles.
- Origin / example: Robert C. Martin consulting at Xerox — a new printer system (staple, fax, print) grew around one fat `Job` class used by every task, and small changes needed hour-long redeploy cycles; the fix inserted an interface layer per job type (Staple Job, Print Job) between `Job` and its clients, applying the Dependency Inversion Principle, with `Job` implementing all of them.
- Reasoning / benefits: keeps the system decoupled, easier to refactor, change and redeploy; interfaces act as barriers against coupling to dependencies so a change in one place does not cascade.
- Violation example: an ATM UI handling both deposit and withdrawal requests should be split into more specific interfaces.
- Caveats: the article does not discuss over-segregation or dynamic-language considerations; its origin section lacks citations.

## The false abstraction antipattern — edA-qa mort-ora-y (mortoray.com, 1 Aug 2014) — https://mortoray.com/2014/08/01/the-false-abstraction-antipattern/
- Cited by README at line 306 in section "Ports" to support: abusing ports/interfaces leads to unnecessary abstractions; often depending on a concrete implementation is fine.
- What it argues / defines: a false abstraction is any interface, base class or adaptor that should not exist — typically created speculatively, with a single implementation; premature generalisation violates YAGNI and leaves code harder to maintain; such abstractions obstruct other changes (the author removed one from the Leaf project for that reason).
- Arguments against: duplicate maintenance (every interface change repeated in the implementation); artificial feature freeze (people hesitate to change abstract types); obstructed refactoring (the abstraction imposes artificial constraints and working around it becomes most of the effort); misleading readers (poor names reveal nothing or suggest alternative implementations that cannot exist); bloated interfaces become concrete and inflexible; partial implementations that raise errors for unsupported methods; interface-plus-implementation is not inherently clean; building for hypothetical futures wastes effort and does not buy flexibility.
- Recommendations and rules: treat a single implementation as a warning sign; be wary of `Fluff`/`FluffImpl` pairs (the `Impl` suffix usually signals a false abstraction) and `FluffInterface` implemented by `Fluff` (suggests the interface cannot be described on its own); an abstraction must be explainable without reference to its implementations; keep interfaces minimal and focused; remove abstractions that obstruct work; do not create abstractions speculatively — add them when a real need arrives (the author reports never struggling to add one later).
- Exceptions admitted: interfaces exported from shared libraries (then an implementation detail, not a real abstraction) and other strong system-level reasons; testing/mocking and plugin boundaries are not discussed.
- Examples: naming pairs only; no code, no language named.
- How it applies to TypeScript/NestJS: the README echoes this — add a port only when there is a real reason (multiple adapters, test isolation, delaying a technology decision), otherwise inject the concrete class.

## A Color Coded Guide to Ports and Adapters — Damon Kelley, 8th Light (18 May 2021) — https://8thlight.com/blog/damon-kelley/2021/05/18/a-color-coded-guide-to-ports-and-adapters.html
- Cited by README at line 317 in section "Ports" to support: further reading on ports and adapters.
- What it argues / defines: Ports and Adapters (= Hexagonal) decouples the application from details — web framework, database, ORM, third-party APIs, even the client-server protocol; the team gained the ability to defer integrations and decouple domain models from the DB schema at the cost of a learning curve; the guide draws the pattern beside Layered Architecture with colours: incoming ports (red) and outgoing ports (yellow); incoming adapters (blue), outgoing adapters (purple).
- Definitions: a port is simply an interface (a duck type would do); incoming/driving port = interface the application implements; outgoing/driven port = interface the application depends on; incoming adapter depends on an incoming port and drives the application (HTTP controller, CLI); outgoing adapter implements an outgoing port and is driven by the application (database, HTTP client, in-code provider); application = the use-case core holding business logic, free of framework/ORM details; the hexagon is only the customary drawing.
- Recommendations and rules: insert ports between controller and application and between application and database/ORM; the essence is inverting dependencies by depending on abstractions; application implements incoming ports and depends on outgoing ports; adapters are injected (incoming adapter receives the incoming port via constructor); any number of ports and adapters on either side, mixing CLI/HTTP/etc.; keep the core free of framework details; add new outgoing adapters (file, database rate sources) without modifying the core; wire everything in `main` (application ← outgoing adapter; HTTP adapter ← application; start server); "incoming/outgoing" = "driving/driven" in other literature; Layered Architecture is simpler and faster to start but may cost nimbleness and is not always the best fit; recommended deeper reading: Getting Your Hands Dirty on Clean Architecture.
- Worked example (Kotlin/Ktor, compressed; inspired by Cockburn's SmallerWebHexagon): `RatingUseCase` (incoming port) implemented by `RatingApplication`, which depends on `RatingProvider` (outgoing port) implemented by `InCodeRater`; `KtorHttpAdapter` (incoming adapter) takes the use case in its constructor; `main` composes them; runnable repo damonkelley/ports-and-adapters-examples.
- Trade-offs / caveats: learning curve for newcomers; simplicity vs flexibility; terminology confusion (two names for one pattern, two label pairs for the sides); hexagon shape carries no meaning; ports need not be formal interfaces; concrete examples were scarce (motivation for the post).
- How it applies to TypeScript/NestJS: interfaces are erased, so ports need injection tokens; NestJS modules play the `main` composition role.
