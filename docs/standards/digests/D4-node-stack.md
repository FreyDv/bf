## WHAT-THIS-IS.md — What this is

- Purpose: positioning page: what the stack layer is, why a separate repo, what you get, how verified, what it refuses to decide.
- Definition: stack layer = Node/TS picks + reasoning + "a reference implementation that a CI run boots end to end on every change." "It is decisions and files. Not a framework, not a dependency - nothing here has a version your project resolves."
- Why a separate repository: "The method moves slowly and technology does not. Splitting them lets the picks change at technology speed while the way of working stays still, and it keeps the standard itself free of any technology's vocabulary."
- Rule: one stack per technology; variation is a profile or adoption mode inside this repo, never a sibling - "two repositories claiming the same technology is how a standard forks in public."
- Rule: link back to core is "a **pointer, not a version range**" - living standard, latest is the only target, "so there is no compatibility matrix to maintain and no core release that has to wait for this one."
- What you get (table): **The decisions** - "Eighteen picks, grouped by area, each naming what it was chosen against and what would make you right to deviate. The escape hatch is part of the pick, not an afterthought - a paved road nobody may leave is a cage." (Note: this "Eighteen" is the SELF-6 count discrepancy vs 17 numbered sections; see backlog.) **A running application** - Next.js and Fastify behind one proxy, sign-up to dashboard, three test tiers, real dependencies in Docker rather than mocks; "The weekly boot is what makes 'it works' a result instead of a claim." **A path for a repository that exists** - per entry, build kept green; "Most standards describe the destination and leave the journey to you."
- How verified: "The same engine that verifies the standard verifies this layer, reading the same manifest schema, and reports **one drift number across both**." No separate compliance story; "it counts what you took rather than what exists."
- Deliberately not decided: "Your datastore, your query layer, your deploy target" - least portable decisions; "a stack that picked them for you would be wrong for most readers while sounding authoritative." The shape ships: "container-ready, env-only config, stdout logging - and the choice is a record you write."

## DECISIONS.md — Layer 2 - Node/TypeScript paved road: the decisions

- Purpose: THE decision document - every technology pick with rationale, what it was chosen against, and its escape hatch; summary tables first, then one numbered section per axis (17 sections), then provisional open questions.
- Method statement: "Evidence-based, not blog-based. Every pick below was distilled from two production monorepos (call them repo A and repo B) and cross-checked against 2026 community consensus. Where the repos disagreed, the pick went to the side the community backs."
- "This file is the *why*; the runnable truth is `starter/`."
- Deviation rule: "Deviating from a pick? Record a superseding ADR in your repo (ADR-004) - the paved road is a default, not a cage."
- Reading guidance: "Read the area you are arguing about. Each row names what the pick was chosen against; the sections below carry the reasoning, one per axis."

### #1 Package manager - pnpm
- Pick: pnpm, pinned via `packageManager` + `engines`; Node 24 pinned via `.nvmrc`.
- Reasons: content-addressed store; strict resolution (no phantom deps); first-class workspaces; "the strongest supply-chain story of the three managers (see #8)". Both reference repos agree; so does "the 2026 default recommendation for new monorepos".
- Caveat: "Stricter resolution occasionally trips a hoisting-reliant package - the fix is an explicit dependency, which is the point."

### #2 Task runner - Turborepo
- Pick: Turborepo - content-hash caching, `dependsOn` task graph, near-zero config, pnpm-native.
- Rule: "start with Turbo, graduate to Nx when coordination is the bottleneck (10+ packages, multiple teams, enforced project boundaries). Nx is the documented escape hatch, not the default."

### #3 Lint + format - Biome
- Pick: Biome as the one linter+formatter; Prettier scoped to `*.scss` only ("Biome does not format SCSS").
- Reasons: one tool, one config, "10-50x faster than ESLint in CI", a11y preset included.
- Gap: "no type-aware rules needing the TS language service, and some framework plugins have no Biome equivalent." Rule: "If you truly need one of those, add a minimal ESLint alongside - never as the primary."

### #4 TypeScript - strict, target stratified by layer
- Pick: `strict: true` plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`; base `target: ES2022`.
- Reasons: "Strict-from-day-one is the settled consensus, and `noUncheckedIndexedAccess` catches the real index bugs."
- Rule: leaf `tsconfig` per app sets `module`/`jsx`/`moduleResolution`.
- Rejected: `verbatimModuleSyntax` is skipped because "Biome's `useImportType`/`useExportType` already enforce type-only imports."

### #5 Fastify - native plugin DI, no container
- Pick: Fastify-native DI - plugins + `decorate`/hooks + `setErrorHandler`, no IoC container.
- Reasons: "Blogs lean toward `@fastify/awilix`; both production repos independently shipped without a container, and encapsulation via plugin scope plus request-scoped `decorateRequest` covers the need with one fewer framework."
- Escape hatch: "Reach for awilix only when a service's graph genuinely outgrows native wiring, and record it as an ADR."
- Layering: `src/{lib,middleware,routes}` = external clients; the hook chain + error handler; route files.
- Twelve-Factor applies: config from the environment (validated once, at boot), stateless processes, logs to stdout.

### #6 Env config - Zod-validated schema at boot
- Pick: a Zod schema validates every env var at boot - defaults, transforms, "fail fast with a readable error".
- Anti-pattern: "Raw `process.env` reads scattered through a service are the weakest spot in otherwise strong repos; one schema is the fix and the Twelve-Factor config story in practice."

### #7 Next.js - App Router, standalone, typed config
- Pick: App Router, `output: "standalone"`, typed `next.config.ts` carrying the security headers plus a **report-only CSP baseline** - "it observes without ever breaking the app, and its report is the enforcement worklist."
- Enforcing CSP is a per-app step: per-request nonces plumbed through `proxy.ts` ("it runs per request on the Node runtime; Next picks the nonce up for its own inline scripts") - "the config comment carries the recipe."
- React 19 for greenfield.
- Rule: "Never `typescript.ignoreBuildErrors` - it is an anti-pattern observed in the wild, not a config option."

### #8 Supply-chain cooldown - 7 days
- Pick: `minimumReleaseAge: 10080` (7 days) in `pnpm-workspace.yaml`, plus an explicit `allowBuilds` allow-list and `enablePrePostScripts: false`.
- Reasons: "pnpm 11 ships a 1-day cooldown by default; real incidents (Shai-Hulud ~12h, the chalk/debug compromise ~2.5h) sat inside that window, so the paved road is more conservative."
- Rule: "Critical security bumps use a scoped exclude, never a global lower."

### #9 Testing - Vitest + Playwright, tiered; Lighthouse as a local perf budget
- Pick: Vitest (unit + integration) + Playwright (e2e) + Lighthouse (advisory perf budgets), "orchestrated from the repo root so the commands are discoverable and Turbo-cacheable."
- Tier definitions:
  - unit "proves one module's logic (no I/O, milliseconds)";
  - integration "proves the contract with a real backing service via an ephemeral Docker test-stack (`docker-compose.test.yml`, non-default ports, tmpfs, healthchecks - never a shared dev DB)";
  - e2e "proves a user journey through the booted app."
- Layout rules: unit and integration co-located (`*.test.ts` / `*.integration.test.ts`, split by Vitest project); journeys in a top-level `e2e/` workspace package "because they cross app boundaries."
- Rule: "Money / security / external-contract paths are non-negotiable at the integration tier and above" (mirrors the core testing-strategy checklist entry, `docs/method/checklist.md`).
- Maintenance rules: "coverage is a floor on paths that matter, not a vanity percentage; flaky tests are quarantined with an owner, never retried-forever; a test changes in the same PR as its spec; if the unit suite needs Docker, it is mis-tiered."
- **Pick (perf):** Lighthouse driven by a small in-repo runner (`perf/`, the `lighthouse` package on headless Chrome), "**not** Lighthouse CI and **not** `temporary-public-storage`."
  - Rationale: "LHCI's easy upload target is a public bucket that auto-expires after a few days - the opposite of what a perf record is for."
  - Nature: "a **local, report-only pre-push tool** (never a CI gate, never fails a push)": diffs the run against a committed baseline, prints per-route deltas; "moving the baseline is a deliberate, reviewed commit."
  - Retention: rolling `baseline*.json` and append-only dated `history/` are **committed** ("kept, especially for deployed targets"); live `.results/` is gitignored; "nothing is uploaded anywhere and nothing expires."
  - Measurement is standard/generic (points Lighthouse at an origin); preparing a measurable environment - build, start, seed only if needed - is the per-repo **adapt** seam (`scripts/perf-budget.sh`, overridable command hooks). Seeding off by default; if numbers depend on data, "pin a **defined state** (seed a containerised DB via `docker-compose.test.yml` / `bootstrap:test-stack`, or a fixed dataset) so a run is repeatable."
  - Targets: `local` is "the only one built and served for you"; **any other name** (`dev`, `qa`, `perf`, `staging`, `prod`, ...) is a **deployed** target measured at its real URL with no seed/build/start, each with its own `baseline.<target>.json` + history. "Routes stay read-only so measuring a deployed target never creates real traffic or data."
  - Methodology: "**Local numbers are machine-specific**" - a "relative pre-push check ('did my work regress against my own pre-work baseline?'), not a cross-team trend." The "comparable, trackable signal is a fixed deployed environment (dev/qa/perf/prod) - stable hardware, so its committed history is a real trend." Both baseline and history committed for every target; whether a team commits *local* history "is their call, made with the machine-variance caveat in mind." For continuous prod health prefer RUM over synthetic runs against the live site.
- **Pick (RUM):** synthetic answers "did my change slow things down?"; RUM answers "how slow is it for real users?" - complements. "The **method is fixed, the vendor is not**":
  - measure with the **`web-vitals` library** ("the primitive everyone - Sentry, Grafana Faro, Vercel, GA - wraps, because only it matches how Chrome reports to CrUX");
  - report **p75/p95** segmented by device and route ("the mean buries the tail that is the real experience");
  - validate the SEO-facing number against **CrUX** ("the 28-day field dataset that actually feeds ranking").
  - "Sentry is **not** a Web-Vitals platform - it is an error tool with an APM bolted on - so we do not anoint it; we standardise the primitive and treat the reporting **sink as a thin, swappable adapter** (one `sink(metric)` function)."
  - Starter ships the neutral half: `web-vitals` (attribution build) in `instrumentation-client.ts` -> one-function `reportWebVital` sink -> `/api/vitals` beacon stub; "runs with no vendor account."
  - Recommended sink when you have it: **Sentry** (team already running it for errors adds RUM with the browser SDK at near-zero new ops; browserTracing auto-captures the same vitals). Env-gate by `NEXT_PUBLIC_SENTRY_DSN` (no-op locally and in CI), keep `sendDefaultPii: false`, **Session Replay off by default** (DOM/PII).
  - Cost caveat deciding when to swap: in Sentry Web Vitals ride on **spans**, "billed per-span since Aug 2025 (the free span quota was halved to 5M) with no metrics-only path - so hold `tracesSampleRate` ~0.1"; when cost/scale bites swap to **Grafana Faro self-hosted** or keep the **DIY beacon -> Prometheus/Loki** ("both ~$0 into an existing Grafana stack, more ops") or **Vercel Speed Insights** (if on Vercel).
  - Rule: "Close the loop with an **alert on a Web-Vitals budget** (e.g. p75 LCP over target on a key route) so a regression pages someone instead of living on an unwatched dashboard."
  - Fixing what RUM finds is "**not** a checklist we freeze here - it would go stale and never fit every app." Use the attribution build (`web-vitals/attribution`) to locate the cause (LCP element, INP interaction/handler, shifting node), then apply the current canonical technique from **web.dev** (Optimize LCP / INP / CLS). "Diagnose, then fix against living guidance; don't ship a static optimisation plan."
  - Division of labour: "synthetic catches regressions **before merge**, RUM measures what real devices and networks **actually experience** - run both."

### #10 App shell - auth, proxy, styling
- **Pick (auth):** Better Auth for product auth - "sessions in your Postgres, MFA and rate-limiting built in; it is the 2026 default for new TS apps and now maintains Auth.js/NextAuth, which is no longer the pick for new projects." Enterprise OIDC SSO uses `openid-client` "in one framework-agnostic shared module, so the same code serves Next's auth routes today and a standalone Fastify tomorrow."
  - Sessions rule: "DB-backed and revocable, short-lived with silent server-side refresh and an absolute cap."
- **Pick (proxy):** Next `proxy.ts` on the Node runtime ("it may query the DB, so the session gate is revocable, not JWT-blind"); Next `rewrites` route app-to-API traffic to the Fastify service in dev and single-origin deploys.
  - Rule: "Auth gates live in both the proxy and the service (default-deny) - the proxy is UX, the service is the boundary."
- **Pick (styling):** CSS Modules + SCSS - co-located `*.module.scss`, no CSS-in-JS runtime; design values from DTCG three-tier tokens "so the visual language has one source." Tailwind is "the recorded escape hatch for teams already living in it."
- All three assembled and boot-verified in `starter/`: "`pnpm i && pnpm dev` boots web + api wired through the proxy with Better Auth in place."

### #11 CI - least-privilege, cached, frozen, pinned
- Pick: GitHub Actions with explicit least-privilege `permissions:` per workflow ("`contents: read` unless a job proves it needs more"), pnpm + Turbo caches, installs with `--frozen-lockfile`, "every action pinned by full commit SHA with a version comment (the core standard's exact-pinning rule, ADR-017 there)."
- Shape: "Two workflows, two speeds: a fast quality gate on every push (`check:all` + unit), the full e2e tier gating release."
- Why: "the workflow file is the most-copied file in any repo - whatever it does becomes the org's habit. Least-privilege and SHA pins cost nothing on day one and are expensive to retrofit after the fleet copies the loose version."
- Escape hatch: another CI vendor or self-hosted runners when mandated - "keep the same shape (least-privilege, frozen installs, pinned steps); the shape is the decision, the vendor is not."

### #12 Dependency updates - Renovate, riding the cooldown
- Pick: Renovate - `config:recommended` base, pin-everything range strategy, `minimumReleaseAge: "7 days"` mirroring the pnpm cooldown (#8), minor/patch updates grouped, labels on. `starter/renovate.json` is the reference copy.
- Why: "exact-pin-everything without update automation is how repos age in place - the pinning axis (#8 and the core standard's exact-pin rule) makes an update *chore* mandatory, Renovate makes it happen as reviewed diffs."
- Escape hatch: Dependabot when the org already lives in it - "keep the cooldown and the pin strategy either way."

### #13 Logging - pino, one JSON line per event, redacted at the edge
- Pick: pino as the one log shape ("it is already Fastify's engine"); logs to stdout as JSON lines ("the platform aggregates; the app never writes files"); secrets and session material redacted at the logger config (authorization/cookie headers); request-id correlation on.
- Rule: the web app does not log to the browser console ("Biome's `noConsole` flags it, allowing only console.error/warn") - "user-facing failures surface in the UI, server truth lives in the API's log."
- Why: "one shape means one query language in any aggregator; redaction at the edge means a leaked log is not a leaked session."
- Escape hatch: "a different transport/aggregator is config, not a new logger; structured console in edge/serverless contexts where pino's stream model does not fit."

### #14 Request validation - Zod at the boundary
- Pick: Zod schemas validate every request body/query at the Fastify boundary via `fastify-type-provider-zod` - same library/pattern as the env schema (#6); "handlers receive typed, validated input or the request 400s before any logic runs."
- Status: "The starter currently ships no body-carrying route - this axis pre-decides the tool so the first POST does not improvise; the env schema is the worked example of the pattern."
- Why: "validation duplicated per-handler drifts; a type provider makes the schema the single source of both runtime check and static type."
- Escape hatch: `@fastify/type-provider-typebox` "when JSON-schema output matters more than Zod ergonomics (OpenAPI generation)."

### #15 Datastore, query layer and migrations - decided per repo, by ADR
- Pick: "deliberately NOT decided here - this is the fork the core standard's decision checklist makes every repo record for itself (datastore, schema evolution)."
- Paved-road guidance the ADR starts from: Postgres is the default datastore ("the test-stack ships it; the auth package documents the swap and the integration test proves it"); the query layer is the real fork - Drizzle (SQL-first, migrations from schema diffs), Kysely (query builder, bring your own migrations), Prisma (schema DSL, "heaviest but most guided") - "one ADR, three options, pick by the team's SQL fluency"; the migration tool follows the query-layer choice; "Better Auth's tables ride its own migrator regardless."
- Why deferred: "any pick here would be taste dressed as evidence - the axes above are distilled from production repos, this one genuinely varies by product shape (read/write mix, multi-tenancy, reporting). A recorded per-repo ADR beats a hollow default."

### #16 Containers and deploy - the shape is decided, the target is a per-repo ADR
- Pick: container-ready shape ships (Next `output: "standalone"`, the api runs plain node, both log to stdout, config is env-only) - "but no Dockerfile and no deploy target: that is a per-repo ADR."
- What the ADR must cover: "base image pinned by digest (the exact-pin rule reaches images), a non-root user, healthcheck endpoints (the api already has `/api/health` and `/api/ready`), env injection per environment, and where the two processes run relative to each other (one origin via the proxy vs split)."
- Why deferred: "the deploy target is the least portable decision a repo makes - the starter refusing to fake one keeps the boot honest."
- Escape hatch: "none needed - this axis IS the escape hatch, recorded."

### #17 Monorepo layout - `apps/` for everything deployed, `packages/` for everything else
- Pick: two top-level workspace roots. `apps/*` holds every deployable ("the Next application and the Fastify service sit side by side, UI or not"); `packages/*` holds code never deployed on its own. Plus two single-purpose roots that are neither libraries nor deployables: `e2e/` (journeys crossing applications), `perf/` (local budget runner).
- Why not `services/` beside `apps/`: "the split reads as 'has a UI' versus 'does not', and that line breaks the first time somebody adds a backend-for-frontend, an admin panel or a worker with a status page. It also implies the two are deployed differently, which the starter does not do - both are plain node processes, both log to stdout, both take env-only config." A third top-level concept "earns its place when a team genuinely treats backends differently: separate on-call, separate release train, separate ownership. Until that is true, it is a folder that has to be explained."
- Why not `libs/`: it pairs neatly with `apps/` and "in a pnpm workspace every member is a package, apps included, so `packages/` names a subset using the word for the whole" - but "That is a naming purity worth less than meeting the expectation of everyone arriving from this ecosystem, where `packages/` is what Turborepo and pnpm examples use. `libs/` is the Nx convention; a repo already living in Nx should keep it and record the deviation."
- Escape hatch: "rename either root. Nothing in the tooling depends on the names - the globs are two lines in `pnpm-workspace.yaml` - so the cost of deviating is a decision record, not a migration."

### Open questions - decided, provisionally
- Genre (core's open-questions catalog): "a standing 'I chose X, convince me of Y'".
- **Better Auth as the product-auth default.** Decided in #10 (2026 community default; maintains Auth.js; `openid-client` for SSO is field-proven). Doubt: "Better Auth here is proven by one boot, not by fleets." Better: "field evidence beyond the starter - evidence over consensus."
- **CSS Modules + SCSS over Tailwind.** Decided in #10 (matches the evidence repos; Tailwind recorded escape hatch). Doubt: "a large slice of the 2026 ecosystem defaults to Tailwind; this is the closest pick to taste in the whole stack." Better: "a criterion that makes the choice situational (team, design-system maturity) instead of one paved road."

## ADAPTING.md — Adapting a brownfield repo to this stack

- Purpose: the per-entry "how" for a repository that already has its own picks; what the adoption agent reads; `pnpm import` routes per source package manager; the app-shell picks as architecture moves.
- Start it: `> take this repo onto repositorystandards.com with the node stack` - "It measures the repository first - what is here, what technology, how much you want done - and comes back with a plan naming who has to act on each item. Nothing is touched before you have seen it."
- Plan without the work: `> score this repo against repositorystandards.com with the node stack - count the work, do not do it`
- What the agent reads: the table below; "Each note answers one question: the repository already has something in this spot - how do we get from theirs to ours without breaking the build?" Reasoning stays in DECISIONS; "a plan you cannot check is a plan you have to take on trust."
- Rule: "**Nothing here is all-or-nothing**: an entry that does not fit gets an exception recorded rather than forced, and the drift number counts what you took, not what you skipped."
- Rule: "the order matters more than the speed - every note is written as a move that leaves the build green, because a migration that goes red in the middle is a migration that gets reverted."
- **Where to record the exception:** in this stack's own `stack.manifest.json`, in its `exceptions` array. `self-verify.mjs` (core) merges this stack's `files`/`sections`/`guards` and `exceptions` into its check, "so an entry recorded here is honoured exactly like a core-manifest one". Example:
  `{ "kind": "file", "match": "pnpm-workspace.yaml", "reason": "npm workspace kept - no cooldown equivalent, see ADAPTING.md" }`
  - `kind` is `"file"`, `"section"`, `"content"`, or `"key"`; `match` is the path exactly as the entry spells it (`file#heading` for a section, `file#key.path` for a declared key).
  - "A guard script itself cannot be excepted by presence - that would delete the check rather than waive it; a `kind: "content"` exception on a guard is allowed, since the guard still runs and must pass."
  - (Note the tension with CHANGELOG/SELF-1: the publisher repo itself records its exceptions in `standard.manifest.json`, not `stack.manifest.json`, because the latter is copied verbatim into adopters - see those sections.)
- **Where your copy came from:** when the run finishes, write this repository's commit SHA into your `stack.manifest.json` as `provenanceCommit`. "`version` says which release you took; the commit says which tree, and that is what the next update diffs against. Without it the stack half of an update has nothing to compare but a version string, and every `merge` entry - which is most of them - goes unenumerated." Core manifest carries the same field for its own layer; "the two move independently: updating one stack never implies the core or another stack."

### The app shell - picks, not table rows
- The app-shell picks (DECISIONS #10 - auth, proxy, styling) and the deferred forks (#15, #16) "are architecture moves, not config merges: an existing auth system, Express/Koa API or Tailwind setup is not 'drifted config', it is a standing decision." Record the repo's own superseding ADR (core's deviation mechanism) or plan a real migration with its own ADR.
- **Existing auth vs Better Auth.** "Migrating means a session-store migration, a password-hash migration and a cutover window - none of it incidental. The superseding ADR is usually the honest first move: record why the incumbent stays, revisit when the product forces it."
- **Existing Express/Koa vs Fastify.** "The shape transfers even when the framework stays - plugins/hooks and the default-deny session gate map onto their middleware chain. Adopt the boundary pattern (one error contract, default-deny, config validated at boot), defer the rewrite."
- **Existing styling vs CSS Modules + tokens.** "Tokens first - they are stack-agnostic and pay off regardless of the component layer; the component migration to CSS Modules follows the repo's own tempo."

## SPEC.md — The repository-standards spec (verbatim copy of the core's normative page, R1–R27)

- Purpose: the whole normative core of the standard (copied in as a `copy` manifest entry, sha256-checked); "Everything else in the standard explains, templates or enforces what is written here; where any other document appears to add a requirement, this page wins."
- Versioning: the number lives once in `VERSION`; "**The standard is living and the only target is latest** (ADR-025)"; a repo complies against the state it last aligned to, recorded in `.standards-version` - "a bookmark ... it never names a version to stay at. Tags mark the standard's own development; nothing downstream tracks them." RFC 2119 key words.
- Rule numbers R1-R27 are stable; `standard.manifest.json` is the machine-readable projection (each entry names the rule it enforces); `scripts/self-verify.mjs` reports unmet rules as a drift count; rules the manifest cannot check are verified at review or by shipped guards ("the clarify gate checks R12 by script, outside the manifest"). Rules marked *(scale)* bind only the scale profile - which a repo is on "by reach, not by headcount (ADR-040)"; everything else is core and binds every repo, solo included.
- (Observation: this copy defines R1-R27; `standard.manifest.json` additionally cites "R28" for the elicitation entries - not defined in this SPEC.md copy.)

### Entry and knowledge
- **R1.** MUST carry `AGENTS.md` at root as the single entry point (what the project is, where each kind of knowledge lives, how work flows). MUST state the altitude order `PRINCIPLES -> ADR/BDR -> specs + ARCHITECTURE -> conventions -> code` (wins on conflict). Whatever file the agent loads **first** MUST point here and carry the working rule: "check whether a shipped skill covers the request before acting on it, and again when the work closes." For Claude Code that file is `CLAUDE.md`. "A rule that only exists one hop away is a rule the agent reaches after it has already started."
- **R2.** MUST record the standard's state last aligned to in `.standards-version` and carry the matching copy of `standard.manifest.json`. A bookmark, not a constraint; nothing MAY read it as a held version or compatibility requirement (ADR-025). SHOULD carry `SPEC.md`.
- **R3.** Project knowledge MUST live in the repo, versioned with the code. "A rule that exists only in chat, a wiki or someone's personal agent config does not exist." **In a repo is not the same as in public**: work whose *publication* is the harm (unfixed vulnerability before fix ships, third-party material contractually unpublishable, unannounced commercial move with a set date) MAY be held in a private mirror (platform's private advisory fork is the paved road) and MUST rejoin mainline when the embargo lifts. Every rule binds inside the mirror (spec, coupled change R11, backlog intent R15, changelog entry written there while the work happens). An embargo MUST name its lifting condition and owner at the start; one with no stated end is knowledge kept out of the repo. "'Not written up yet', 'it is in the chat', and work someone would rather not publish are not embargoes." An already-private repo needs none of this (ADR-034).
- **R4.** Documents are living: MUST be updated in place; "The current version is the truth; git is the history." When a change reverses something a future reader needs, the doc SHOULD say so in one line. History MUST NOT accumulate inside a living document - no change-log section in a spec/doc; git and the changelog (R18) hold the past (ADR-018). **A fact has one home**: a count/version/path/command restated elsewhere MUST link to its home or be a **declared** restatement listed in `docs/facts.json` with its source, so `scripts/facts-check.mjs` fails when they disagree; "a surface reworded past its own declaration fails the same way: silence there is indistinguishable from agreement."

### Decisions
- **R5.** A contestable, re-litigable choice MUST be recorded as a decision record in `docs/decision-records/` - ADR technical, BDR business, MADR form. A settled way of doing a recurring thing MUST be written as a rule where the next person will look; the taxonomy (by reference, always latest) maps where each kind lands.
- **R6.** An accepted record MUST NOT be edited into a different decision; superseded by a new record (status flip + link). An accepted record **binds work in its scope** until superseded: a contradicting spec/plan/change MUST stop, then come into line or supersede. "Writing around it is not a third option."
- **R7.** Every fork in the decision checklist that applies MUST be consciously decided and recorded; an area that does not apply MUST say so once, in one line. "Silence is not an answer - an undecided area gets decided anyway, by whoever writes the first file that depends on it." Names no subset, asserts no count; the checklist owns the areas and carries a paved-road default; "accepting a default is a decision."
- **R8.** Behavior MUST be specified by capability - never by ticket, page or feature number.
- **R9.** A capability spec MUST be buildable by default (an agent could rebuild and verify from the spec alone); behavioral tier is an escape hatch that MUST be justified in-spec and SHOULD be rare.
- **R10.** Every capability spec MUST name the persona it serves; "a spec that serves nobody fails the structure guard."
- **R11.** Every capability MUST have an entry in `specs/capability-map.json` binding it to code globs; a change to a capability's code MUST land in the same PR as its spec update. *(scale)* The coupling guard blocks any PR that breaks this. A capability implemented in a repo this one does not own MUST still have an entry naming that repository with a recorded reason in place of globs; no coupling enforced for that part, "and the audit names it on every run (ADR-039)."
- **R12.** A spec MUST pass the clarify gate before planning or implementation: zero open questions, explicit deferrals recorded as answers, never dropped.
- **R13.** Plan and task scaffolding is ephemeral and MUST be removed when work closes. Specs, records and docs are permanent.

### Ideas and backlog
- **R14.** A speculative idea MUST NOT mint records or specs before approval. Lives in `docs/ideas/` under a status - idea, exploring, approved, parked, dropped, graduated - and on approval hands off to the normal flow (backlog intent, spec, records), the idea doc flipping to `graduated` and pointing at what it became.
- **R15.** The repo backlog holds intents, each with a definition of done; an item leaves only when its DoD is met. Execution state and work history live in the tracker - GitHub Issues by default, or an adapter (Jira, Linear field-proven; GitLab Issues and others follow the same shape); "the tracker is wherever execution state actually lives, not a fixed set of product names."

### Verification and updates
- **R16.** Compliance MUST be enforced by tooling, not prose: `self-verify` (against the recorded manifest) and `spec-structure` MUST gate CI; *(scale)* `spec-guard` too. "Aligned means self-verify reports drift 0." These guards and `facts-check`/`schema-pair` are dependency-free Node scripts (`scripts/*.mjs`); the agent guards R19 relies on are shell scripts reading input with `jq`. Therefore "A Node runtime, a POSIX shell and `jq` MUST ... be present ... regardless of the repo's own language, stack or operating system" - complete list in `prerequisites.md` (by reference). "This is a real cost for a non-Node repo and for a team on a platform with no POSIX shell"; a repo that cannot meet it records the guards it does not run as a deviation.
- **R17.** Adoption and updates MUST adapt, never blind-copy: align reconciles to latest; the record names the state aligned to; an update applies the delta preserving the manifest's `exceptions`.
- **R26.** Adoption's Step 0 (intake, ADR-020) MUST leave a record: `docs/adoption-intake.md`, a required manifest entry filled before any greenfield/brownfield/stack work proceeds, never deferred (ADR-042). "An agent that skipped the question round and one that ran it in full produce the same tree without this file".
- **R27.** Assessment and count gates MUST leave artifacts carrying what the gate is for: `docs/adoption-assessment.md` (required; rates all eight assessment passes `absent`/`partial`/`solid`, names top risks, groups every finding by owner role) and a backlog whose alignment scope block states a total its categories sum to, every item naming its owner role (ADR-048). `adoption-gates` reads both for shape.

### Releases and hygiene
- **R18.** A PR MUST NOT add a version heading to the changelog and MUST NOT bump a version; the maintainer cuts every release; a PR writes under `## Unreleased` - at every profile, one mechanism. Multiple release lines (R23): one changelog per line, each with its own Unreleased heading, entry under the heading on the branch targeted. Multiple independently-versioned units from one tree (monorepo of packages/gems/crates): one changelog per unit instead of one at the root; a PR writes under every unit it touches. "release lines split a changelog across branches over time, units split it across the same tree at once ... never a second kind of mechanism (ADR-044)."
- **R19.** Secrets MUST NOT enter the repo - environment and a secret manager only. The shipped secret scan SHOULD gate CI; agent access to remote databases SHOULD be write-blocked by the shipped settings baseline. The security baseline R7 requires MUST state where each axis in `security-baseline.md` (by reference) lands - including "not applicable" ones, "because an axis nobody considered and an axis deliberately dropped are indistinguishable a year later." Technology-specific depth belongs to the stack layer.

### Layers and profiles
- **R20.** Two layers, adoptable independently: Layer 1 (methodology, any stack); Layer 2 (optional technology best practices in per-technology stack repos, "official only when listed in the core registry (`stacks.json`)"). One standard, two profiles: core keeps knowledge alive in every repo; scale "adds what carries it to people who are not in the room." Profile is a question about reach (asynchronous hand-off, outside contributors/readers, a release audience that is not the authors), never headcount (ADR-040). "Solo repos meet core alone and are compliant." A stack declares what adopting it means in `stack.manifest.json` (core schema); an adopting repo carries it; `self-verify` counts one drift across both. Permanently coexisting stacks: one manifest per stack (`stack.<technology>.manifest.json`); all read; drift stays one number (ADR-037).

### Supply chain
- **R21.** Everything consumed MUST be pinned exact and move only by explicit reviewed diff: manifests/overrides exact (no ranges), sealed by a committed lockfile; container images, CI runners and actions name an exact version or digest - "never `latest`, never a floating tag." A new version SHOULD clear a release-age cooldown ("the paved road is seven days"); a critical security fix MAY bypass via a recorded, temporary exclusion. Per-stack mechanics live in the stack repos (ADR-017).

### Agent executability
- **R22.** Lifecycle procedures (spec loop, backlog capture, pre-PR review, version updates) MUST ship in the repo in a form the coding agent can execute - shipped as Claude-format skills (`.claude/skills/`) with engine in `scripts/spec/`. A non-Claude repo MUST port them "strictly and completely" to its own mechanism (e.g. `.agents/skills`) before claiming compliance; `self-verify` accepts the ported location. "A partial port is drift, not a variant (ADR-019)."

### Integration and history
- **R23.** Mainline history MUST read as one finished unit of work per **reviewed change**. The PR is the paved road's unit; a repo reviewing elsewhere (mailing-list patch series, Gerrit, Phabricator) MUST name its unit in the branching decision (R7). A branch is brought up to date by **rebasing onto its base**; the base MUST NOT be merged back. Every reviewed change MUST be based on the branch it will merge into - mainline or a **maintained release line** (long-lived, protected, declared supported with R7, never rewritten) - never another open change's branch. A fix for more than one line MUST land on mainline first and reach each supported line as its own reviewed change, unless mainline no longer carries the code (ADR-035). MUST land by **rebase-merge** (paved road) or squash-merge - decided once with R7; platform linear-history protection SHOULD enforce it. Rebase-merge MUST NOT be chosen unless each commit is complete, buildable, reviewed; otherwise squash. A branch MAY be rewritten while the author's alone; once another person/branch builds on it, MUST NOT be (ADR-026).
- **R25.** (core repo's own workflow) A PR that changes what the standard ships describes it under `CHANGELOG.md`'s `## Unreleased` AND MUST move the version in the same PR - "deliberately tighter than the R18 default it ships, because here the maintainer reviews every PR"; the version MUST be one fact restated nowhere unchecked (R4). "**Patch is the default and covers nearly everything**"; "**Minor is a judgment, not a trigger**" - requester's explicit instruction, "never derived mechanically from 'a rule was added' or 'a path changed'". A PR MAY be told not to bump. Patch is not two-digit: 1.0.12 -> 1.0.13 -> ... 1.0.99 -> 1.0.100. Adopting repos still track latest, never a pin (ADR-025).

### Data and schema
- **R24.** A repo owning a database MUST carry the schema as executable DDL under `database/schema/` complete enough to rebuild from a checkout ("the disaster-recovery copy, and the artifact a schema change ships as (R19: an agent prepares the reviewed file, a human applies it)"). Migrations are the delta, never the readable current state. The same schema MUST also exist as a **typed, documented** definition in the stack's idiom (Zod in TypeScript, Pydantic in Python); every path reading/writing the DB MUST go through it. The two are **1:1** (every table, column, constraint, enum; each side names its counterpart in the file; a change to either lands in the same PR); `scripts/schema-pair.mjs` resolves it both ways and fails when a DDL-defined name is absent from the twin. Either side MAY be generated where the generator "does not silently drop what DDL can express"; type agreement/generation are per-stack mechanics (ADR-027). **Owning a database vs shipping the mechanism that changes one**: a migration library / ORM DDL layer / schema toolkit owns no database - `database/schema/` and the twin do not apply (say so once, R7); it owns the emitted DDL per supported backend as an interface contract that MUST be specified verbatim per backend (R9), including where backends differ.

### What this standard does not do
- Does not mandate a tracker, a CI vendor or a stack - "Layer 2 is a paved road, not a toll gate." No company-specific configuration (tokens, tenant ids stay variables). Rejects per-ticket/per-page specs (R8). "It is not an open-source community kit: codes of conduct, support and governance files are the adopter's own affair." Edge cases / "what about X" belong in the FAQ, never here as new rules.

## CONTRIBUTING.md — Contributing

- Purpose: what belongs in this layer vs the core; the bar for a change.
- Scope rule: "a change to how the standard works belongs there [the core], not here."
- What belongs here: (1) "**A pick that is wrong for a real repository.** The most valuable contribution: name the repository shape it fails on, not the preference. Every decision carries an escape hatch for exactly this reason, and an escape hatch that nobody has needed is a hypothesis." (2) "**A default that is unsafe once copied.**" (see SECURITY.md; report privately if exploitable). (3) "**An adapting note that does not survive contact with a brownfield repository.** ... a note that assumes a clean tree is worth less than no note."
- What does not: "A pick swapped for a preference" (reopening means engaging with what it was chosen against); "A dependency added without a decision" (every surviving pick is in DECISIONS.md with its escape hatch).
- The bar: "A change to what the tree ships **moves the version** and the boot pulse must stay green ... If your change cannot be proven by it, say what would prove it instead."
- Integration: "Pull requests sit on `main` and land by rebase, so each commit is published on its own and needs a message that stands alone."

## SECURITY.md — Security policy

- Purpose: reporting path and posture.
- "This repository ships a reference monorepo and the decisions behind it. It runs no service and collects nothing." Realistic surface = what an adopter copies: "the session gates, the redirect handling, the CI templates and the supply-chain policy - a weak default here becomes a weak default in every repository that adopts it."
- Reporting: unsafe-once-copied defaults ("a gate that can be walked past, a redirect that survives a round trip, a workflow with more permission than it needs") -> email **bodurkalukasz@gmail.com** with the file and scenario; answer within **7 days**; no public issue for anything exploitable before it is fixed.
- "The starter's own guards are the first place to look: the boot pulse asserts them on every push, so a report that makes the pulse red is the most useful shape a report can take."

## AGENTS.md — the agent entry point (not in the requested list but it is the R1 root file)

- Altitude: this is the **stack layer** - "decisions and files. Nothing here has a version another project resolves, and nothing here decides method: how work is specified, recorded and verified is Layer 1's business, adopted here by reference."
- Two audiences wanting opposite things: a reader comparing picks ("will adopt nothing if the reasoning is missing") and an adopting repository wanting the ordered path. "Writing for one at the other's expense is the failure mode."
- Map: `DECISIONS.md` (picks), `starter/` (boot-verified app), `ADAPTING.md`, `stack.manifest.json`, `specs/` ("what each capability of *this repository* is for"), `docs/decision-records/` ("decisions about this repository, as opposed to picks about Node"), `backlog.md`.
- The distinction that trips people: "`DECISIONS.md` holds **technology picks this stack publishes**; `docs/decision-records/` holds **decisions about how this repository itself works**. A change to Fastify's role goes in the first. A change to how this repository verifies itself goes in the second."
- "The loop runs itself (unprompted)" - when work changes something a document asserts, the document changes in the same change: a pick in DECISIONS and its embodiment in `starter/` move together ("or the argument stops being evidence"); a capability's files change -> spec updated in the same change ("The coupling guard enforces this and it is not a formality"); something learned gets written where it belongs before closing; a decision made in passing gets recorded with what it was chosen against. "A red weekly boot is a claim this repository can no longer make, not a flaky run to retry."
- "Volunteer, don't wait to be asked": finish the whole task; fix adjacent breakage in scope or write it into `backlog.md` with evidence. Two habits: "**Report the number you measured, not the number you expected.**" and "**Say when something did not reproduce.**"
- "Say where you are, every minute or two": during long work post one or two sentences every 60-120 seconds (what you are doing, what you are waiting on). "**Waiting is an update.**" "**Never invent progress, and never report a result that has not come back.**" "**A countable total earns a measured percentage** (`N/M`); an open-ended one earns a labelled estimate (`~Z% (estimate)`)". "Work that takes thirty seconds has nothing to report - do not pad it."
- Conventions adopted from core by reference (`docs/conventions.md` at main); the two that most often catch people: "a pull request writes under `## Unreleased` in `CHANGELOG.md` and never bumps a version, and every pull request is based on the mainline."

## specs/README.md — Capability specs

- Purpose: the policy for the specs folder (core text, adopted as copy): "The functional source of truth for **what this system does now**."
- `SPEC = the current truth of a CAPABILITY` not `SPEC = the description of a ticket`. "A spec is not written once and archived. It is edited in place forever, and `main` always says what production does."
- Structure (core ADR-002, by reference): organized by capability/domain, e.g. `specs/bookings/spec.md`, `specs/payments/spec.md`; a large capability may split within one domain (`specs/bookings/{overview,lifecycle,modifications,cancellation}.md`).
  - "**No ticket-numbered or timestamp-prefixed folders.**" Never `specs/001-booking/` or `specs/booking/017-change/`; `scripts/spec-structure.mjs` blocks the shape mechanically.
  - "**No per-page or per-route folders.**" (a concept like *packages* appearing on three pages would duplicate three times and drift).
  - "**No versioned specs.**" No `payments-v2/`; cross-domain changes edit every affected spec in the same PR.
  - "**An existing directory means the same capability.**" Update in place; no sibling because the work "feels different".
- Every spec names the persona(s) from `docs/personas.md` and states in one line how it advances that person's job; "A spec that serves nobody is a candidate for deletion, not for merge."
- Spec depth (core ADR-003): the bar - "An engineer or an agent could implement and verify this capability from the spec alone, without reverse-engineering the code." Buildable is the default: exact schemas and enums, every endpoint with inputs/outputs/errors, algorithms as implementable steps, state machine as a transition table, flags, acceptance criteria in Given/When/Then; "Contracts quote real identifiers verbatim ... A paraphrased contract is not a contract."
- "**A content product has contracts too.**" (translation catalogue, packaging recipe, narrative work, normative document) - buildable means the artefact's structure and its consumers, stated as exactly as an endpoint; reaching for `behavioral` because there are no endpoints "discards the part that was checkable."
- "**`behavioral` is the escape hatch, not a shortcut.**" Must declare itself in the header AND carry a one-line justification. "On a money, security, external-contract or data-integrity path it is not available at all".
- Coupling: every capability needs an entry in `capability-map.json` (shape in `capability-map.example.json`); "a capability with no map entry is not merely unguarded, it rots silently". `/spec-specify` registers a new capability when minting the directory; `spec-guard --audit` re-checks the whole map in CI. Behaviour change + spec update land in **the same PR**; "The guard is per-PR and has no bypass".
- Make the loop self-triggering: loop = `/spec-specify -> /spec-clarify -> /spec-plan -> /spec-tasks -> /spec-implement -> /spec-reconcile`, **AI-led**. Three layers: (1) **Loaded context** - `AGENTS.md`'s "the loop runs itself" section imported into every session (`@AGENTS.md` from `CLAUDE.md`); (2) **The gate** - `scripts/spec/check-spec-clarified.sh`: a spec may not reach `ready-to-develop` without a `## Clarifications` section, zero open `[NEEDS ...]` markers, and an `## Open questions` section saying there are none; (3) **The bridge precondition** - `setup-plan.sh` and `setup-tasks.sh` call the gate first and refuse on non-zero (the skills' prompts also document it as "MANDATORY PRECHECK", but the scripts enforce it independently).
- "No skill may offer to skip clarification. A spike is a reason to *defer* an answer, and a recorded deferral is an answer".
- What does not go in: tickets/page names/version suffixes; **History** ("Do not keep obsolete behaviour 'for the record'"); **Ticket language** ("This feature adds...", "in TICKET-123 we...").
- How you use it: skills `/spec-specify` (one capability from what you said), `/spec-clarify` (questions until nothing open), `/spec-impact` (which other capabilities this ripples into), `/spec-update` (edit every affected spec to target state), `/spec-plan` `/spec-tasks` `/spec-implement`, `/spec-reconcile` (spec == code == tests, specs agreeing). The gate that matters is `/spec-clarify`: "a missing decision, a missing input and a missing asset block work exactly like an unanswered question, because all four mean somebody would have to guess." An open question the work answered gets closed in the same PR.

## specs/enforcement.md — Spec policy enforcement

- Purpose: what is mechanically enforced vs AI pass, and where the gates run. "Honest scope - only part of this is mechanical; the rest needs an AI pass."
- **Status check (shipped, in the structure lint):** a spec whose `**Status:**` claims `ready-to-develop` or `live` MUST pass the clarify gate - the structure lint re-runs the real gate script and fails the PR otherwise. "`spec-reconcile` owns writing it; this owns proving it. A gate that cannot be run is not a gate that passed, so that case fails too."
- **Structure lint (shipped, `spec-structure.mjs`, standalone, no capability-map):** no ticket-numbered paths (`specs/<capability>/`, never `specs/NNN-feature/` or `specs/<cap>/NNN-*` - "a common leak from upstream Spec Kit's native specify"). Also mechanical: a spec declaring `**Spec tier:** buildable` must carry `## Data contracts`, `## Interface contracts` and `## Acceptance criteria`, each with something under the heading ("the template marked them REQUIRED and nothing read the template, so a buildable spec shipped without its contracts and they were retrofitted by hand months later"). A section that does not apply keeps its heading and says so; a spec declaring no tier is warned, not blocked. Link resolution "stays a lighter follow-on, not yet mechanical."
- **Coupling guard (the key one):** PR changes code in a capability's domain without touching its spec -> block (or warn): "you changed `<capability>` code without touching `specs/<capability>/`; update it or state why not." Cannot prove the spec is correct; forces touching or acknowledging.
- **Map audit (same guard, `spec-guard.mjs --audit`, full-tree in CI, tracked and untracked alike, git ignore rules apply):** four silent rot modes: (1) a `specs/<capability>/` with no map entry; (2) a map entry naming a capability with no spec; (3) a glob matching no file ("the guard is watching an empty set"; a retired capability keeps its entry and is exempt - `--audit` reads `**Status:** retired`); (4) code belonging to no capability (survives a refactor: old glob matches nothing AND new path claimed by nobody) - bounded by `"$unclaimed": ["<glob>", ...]`; `specs/` always exempt; without `$unclaimed` the check is **off and says so**. Keys starting with `$` are metadata (`$about`, `$unclaimed`); any other `$` key is refused.
- **Clarify gate (ADR-010; "field-proven in production, 2026-07"):** all four must hold - `## Clarifications` section; **zero** open `[NEEDS ...` markers (CLARIFICATION, DECISION, INPUT, ASSET); **nothing merely shaped like a marker** (translated family name, invented type -> fail); `## Open questions` section that **says there are none** ("prose, a statement, a table of gaps and an item answered above but still listed below were all found passing"). Wired twice: skills' "MANDATORY PRECHECK" and the scripts' own call (even a `--json` dry run cannot skip it). Not a Claude Code hooks-mechanism check (the three `.claude/hooks/` guards cover remote-DB writes, force-pushes, CI secret writes); "a per-request judgment call like 'does a skill cover this' is not something a hook can make". Marker forms and both headings are **syntax** (ASCII in any language; marker text is prose).
- Capability -> code globs map at `specs/capability-map.json`; example `{"payments": ["packages/payments/**", "apps/*/src/**/payment/**"], "pricing": ["packages/pricing/**", { "glob": "config/tariffs.json", "couples": "shape" }]}`. Single-package repo writes `src/**/payment/**`. Globs must match the tree you actually have.
- **External code**: `{ "channel-sync": [{ "external": "acme/channel-connectors", "reason": "each connector is released from its own repository" }] }` - nothing enforced, spec still lives here, `--audit` names every external binding every run; `reason` required ("without it this is a way to move a capability out of the guard's reach").
- **Glob syntax** (`scripts/lib/glob.mjs`, one translator): `*` within one segment; `**` any number of segments **including none** (`**/payment/**` covers `payment/index.ts` at top level; `shared/**/payment*` covers `shared/payment.ts`); trailing `**` means directory contents (`src/**` matches `src/index.ts`, not a file named `src`).
- **Two capabilities in one folder**: `!` prefix **excludes** - `"payments": ["packages/payments/**", "!packages/payments/refunds/**"]` beside `"refunds": ["packages/payments/refunds/**"]`. "An exclusion narrows a claim and cannot replace one: a capability with nothing but exclusions is refused"; `--audit` reports an exclusion matching nothing and a file handed to nobody.
- **Map hygiene:** globs bind behavior-bearing source; dependency manifests/lockfiles (`package.json`, `pnpm-lock.yaml`, `go.mod`) SHOULD stay out (a version bump is a dependency diff, R21, changelog). When the guard fires on a behavior-free change: reconcile the spec or narrow the map - "never ... append a history note to the spec (R4, ADR-018)".
- **Data a capability reads** (rules table, tariff file, manifest): declare `{ "glob": "<glob>", "couples": "shape" }` - couples on **key shape** (adding/editing a value passes; a key path appearing/disappearing demands the spec); anything uncomparable (no earlier version, unparseable JSON) couples. Maps **keyed by data** (hash per file, rate per locale): `"dataKeys": ["files[].sha256"]` on the same entry (array indices collapse to `[]`) - "the path itself is shape, everything under it is data"; path disappearing still couples; `dataKeys` on a content-coupling entry is refused. "A gate that fires when nothing is wrong gets satisfied with a cosmetic spec edit, and once that is the habit the gate is decoration."
- Shipped: `scripts/spec-structure.mjs`, `scripts/spec-guard.mjs` (dependency-free), run by `.github/workflows/spec-guard.yml`.
- NOT mechanical: behavioral drift is semantic -> `/spec-reconcile` as an AI job reading diff + specs + tests; "run it as **advisory** on CI, or on demand - not a hard block."
- Where gates run: **pre-commit** (cheap, local): structure/lint + coupling **warn**. **CI** (on PR): structure/lint blocks at both profiles; coupling **blocks at `scale` and advises at `core`** (workflow reads the profile); full-tree `--audit` blocks at both; optional advisory `/spec-reconcile` comment.
- Setup cost: the coupling map is one-time per-repo config; "a repo adopting this layer must author `capability-map.json` before the gate is meaningful."

## specs/capability-spec.template.md — the capability spec template

- Header fields (syntax, grep-read): `**Spec tier:** buildable | behavioral` (declare one; guard warns while unfilled); `**Serves:** <persona from docs/personas.md>` (required, ADR-006); `**Status:** in-refinement | ready-to-develop | in-development | live | retired` (`/spec-reconcile` sets it; guard re-runs the clarify gate on `ready-to-develop`/`live` - "typing one early buys a failed PR, not a head start"); `**Success metric:** <KPI from PRODUCT's KPI tree>` (PDLC-2; "n/a" needs a why).
- Retiring: do not delete; flip Status to `retired` with a link to the deciding BDR/ADR (R5); never extend under this slug or a near-miss; a later need is specced fresh as a NEW capability; leave the capability-map entry in place; a retired spec is "frozen against gaining behaviour, not against being true" - later changes correct false statements with Status left `retired` (R4, ADR-036).
- Open markers (exact literal forms, ASCII in any language): `[NEEDS CLARIFICATION: <question>]`; `[NEEDS DECISION: <topic>; owner: <who>]` (missing ADR/BDR); `[NEEDS INPUT: <what>; owner: <who>]` (e.g. UX design); `[NEEDS ASSET: <what>; owner: <who>]` (e.g. credentials). Enabling work (tokens, access, agreements) goes in front-matter keys mirrored to the tracker as blocking Stories, never in prose. At live+reconciled, cleanup removes plan/tasks scaffolding; the spec stays.
- Sections in order: `## Purpose` (one or two sentences); CLARIFY-ANCHOR: `## Clarifications` goes immediately after Purpose, before Scope, each session as `### Session YYYY-MM-DD` (heading deliberately NOT shipped in the template because the gate greps for it); `## Scope`; `## Out of scope` (name the other capability); `## Core concepts`; `## Data contracts` (buildable REQUIRED, verbatim: tables/columns/types/constraints, enums, JSONB/message shapes, units, idempotency/correlation keys; content products: the artefact's own structure); `## Interface contracts` (buildable REQUIRED: every endpoint/public function - method+path or signature, auth/gate, request shape, success response, idempotency keys, side effects; errors as a **required table** `| Endpoint | Status | errorCode | Message / condition |`); `## Algorithms & rules` (numbered implementable steps incl. rounding, ordering, tolerances, concurrency/locking); `## State machine` (transition table `| From | To | Trigger | Guard |`, mark terminal states); `## Requirements` (`### <Area>`: MUST / MAY / MUST NOT); `## Invariants` ("Each invariant MUST be covered by at least one Given/When/Then ... an invariant nothing tests is a wish"); `## Config & flags` (`| Flag | Effect |`); `## Edge cases`; `## Trust boundaries` (OPTIONAL - REQUIRED for money/auth/personal-data); `## Cross-capability interactions` (`### <Other capability>`); `## Acceptance criteria` (buildable REQUIRED; `- **<name>.** GIVEN <state> WHEN <event> THEN <expected outcome>`); `## Open questions` (REQUIRED; passes only when it says there are none - keep `None known.`; a marker lives in exactly ONE place, never echoed here; a settled note goes to its section; a known gap not blocked on goes to the backlog).
- Rule: a dropped heading and an empty one "read identically to everyone downstream" - the three required sections keep their heading and say so in one line ("None - this capability persists nothing"). No change-log section (R4, ADR-018).

## specs/adoption-path/spec.md — Adoption path

- Tier **behavioral**; Serves `Adopting repo owner`, `Adoption agent`, `Greenfield starter`; Success metric: "a repository can follow the path entry by entry without the build going red between entries"; Status in-refinement.
- Tier justification (R9): "the deliverable is instructions executed by an agent against a repository this repository has never seen ... What can be asserted is the ordering property".

- Scope: `ADAPTING.md` (per-entry notes, what the agent reads to classify, `pnpm import` routes, app-shell picks); `QUICKSTART.md` (two entry sentences and what follows).

- Behaviour: each entry names what the repo probably has, what this ships, the ordered move; the order never requires a red build (an entry that cannot land green says so and names what it must land with); a pick already satisfied differently is recognised and the keep-decision recorded; the two entry sentences produce the same end state ("greenfield scaffolds and brownfield walks"); package-manager migration says plainly where a route does not exist; the run ends by recording provenance (this repo's commit into the adopter's stack manifest - "A path that is walked but not recorded cannot be walked again from where it stopped"); a part-way entry is recorded as an exception naming the step, and the note says when it comes out.
- Open questions: whether a partial adoption has a recorded resting state (= SELF-5).
- Not doing: "A migration codemod. The picks are configuration and conventions rather than API surface".

- Out of scope: being a template to copy; a Dockerfile or deploy target ("a starter that faked one would boot on nothing"); a datastore or query layer.
- Core concepts: **The marquee journey** (sign-up to dashboard - "the one path that must work end to end for the tree to count as booting"); **The heartbeat** (weekly run; "the core's stack policy makes a live boot CI a condition of staying listed"); **Real dependencies** ("a mock proves the mock").
- Behaviour: marquee journey passes on every change and weekly ("A red heartbeat is a claim this repository can no longer make, not a flaky test to re-run"); a pick changing in DECISIONS changes here in the same change; "The supply-chain policy is exercised rather than declared - the run checks that the cooldown and the exact-save survived, not merely that the file exists"; the tree stays small enough that a framework major is a contained change ("Growth that makes the reference implementation expensive to keep green is the failure mode, not a milestone").
- Open questions: what happens when the heartbeat is red for a sustained period (= SELF-4).
- Not doing: "Multiple reference implementations per adoption mode. Backend-only and friends are subtractive adoption modes over this one tree, never sibling trees."

## specs/stack-contract/spec.md — Stack contract (the one buildable spec)

- Tier **buildable**; Serves `Adoption agent`, `Stack maintainer`; Success metric: "an adopting repository's drift number counts this layer's entries in the same total as the core's, with no second compliance story to run"; Status in-refinement.
- Purpose: publish the stack in the one machine-readable form the core's align/verify machinery reads - "no new engine, no new vocabulary and no second drift number."
- Scope: `stack.manifest.json`; `SHIPPED.md`. Out of scope: the registry (`stacks.json` in core "is what makes a stack official; this repository points at it and cannot list itself"); a compatibility range.
- Core concepts: **Same schema, second file** (core schema plus `technology`; engine merges both); **`requiredKeys`** ("Presence is worthless for an entry whose whole point is a block inside a file the adopter also edits"); **Provenance is per layer**; **Required is about the check, not the calendar** (required = drift while absent, making a half-finished migration visible; optional = decision can be satisfied at a path the schema cannot name); **The guard** (a live command whose verdict is part of the drift number).
- Data contracts (`stack.manifest.json` top level): `technology` string; `version` string (own version, independent of core); `provenanceCommit` string|null; `registry` string (back-pointer to core's `stacks.json`); `files` array (core file-entry schema: `path`, `adapt`, `required`, `purpose`, `requiredKeys` for merge); `guards` array (core guard schema: `id`, `run`).
- Interface contracts (consumer is `scripts/self-verify.mjs`):

| Consumer | Trigger | Exit / effect |
|---|---|---|
| stack-manifest read | any file matching `^stack(?:\.[A-Za-z0-9][A-Za-z0-9._-]*)?\.manifest\.json$` (`STACK_MANIFEST`), read in filename order | valid JSON: `files`, `sections`, `guards`, `exceptions` concatenated onto the core manifest's arrays before checking. Unparseable: `fail("stack", "<file> is present but unparseable: <message>")` |
| profile resolution | `--profile` flag, else `manifest.profile`, else `"scale"` | no key: `warning`, falls back to `scale`; unknown value: `warning`, treated as `scale`; `core`/`scale`: `note`, used for both layers at once |
| a guard's `run` (e.g. `stack-check-all`) | executed as a shell command | exit 0 passes; nonzero is drift, not waivable by exception; a `requires` entry (`kind: "command"` or `"path"`) whose prerequisite is absent: reported as not run, counted as neither drift nor adoption |
| a `merge` entry's `requiredKeys` | checked once the path exists | a named key absent: drift on that entry, distinct from the file missing |

  - Errors surface through the same `note` / `warning` / `fail` calls - "no separate error channel for the technology layer, which is the mechanism behind the one-drift-number promise".
- Rules: a merge entry whose point is a policy block declares `requiredKeys`; a guard's failure is drift and cannot be waived ("waiving a live check removes it rather than recording a deviation from it"); the manifest carries no version range against the core; `provenanceCommit` ships `null` and is never a core commit ("nothing in this repository rewrites an adopter's copy"); an entry is `required` only where its absence is itself the deviation (otherwise optional, "because a required entry there manufactures drift for a repository that did nothing wrong, and an exception recording it buries the cases that mean something").
- Acceptance criteria: (1) both manifests -> one drift number, technology layer named; (2) merged `pnpm-workspace.yaml` without the policy block fails on `requiredKeys`, not passes on existence; (3) an exception targeting a guard is rejected as drift; (4) an adopter's recorded `provenanceCommit` makes the next update's delta commit-based with every entry enumerated; (5) a workspace with per-package test tiers and no root `vitest.config.ts` reports an unmet optional, not drift, and records no exception.
- Open questions: "This repository cannot satisfy its own stack manifest, and that is not yet decided either way" - three entries (`biome.json`, `tsconfig.base.json`, `pnpm-workspace.yaml`) fail and `stack-check-all` fails with `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND` because it runs `pnpm check:all` at a root with no `package.json`; schema has no publisher/consumer notion; guard cannot be excepted; options in the backlog. (SELF-1 is marked done in backlog via exceptions; this spec text still lists it open - SELF-10 asks a human to reconfirm the spec.)

## docs/decision-records/adr/ADR-001 — The technology picks ship as one document, not one decision record each

- Status Accepted (2026-08-06, "recorded retroactively - the shape was chosen when `DECISIONS.md` was written"); Author Łukasz Bodurka; Tags structure, layer-2, documentation.
- Context: two kinds of decision easy to confuse - the **picks** (the product) and decisions about **this repository** (ordinary engineering choices belonging in a decision record). Picks are 17 numbered sections in one `DECISIONS.md` behind one summary table; the difference from the core's convention "had never been recorded, so it read as an oversight rather than a choice - which is precisely the condition under which somebody 'corrects' it."
- Options: **A** one ADR per pick (17 records) - rejected: the audience "reads to **compare against their own conventions**, and comparison needs everything on one surface"; makes the summary table a generated artifact. **B** one document, no records - rejected: leaves this repo's own choices homeless. **C** one document for picks, a decision log for the repository - chosen.
- Decision: (1) a technology pick is a section of `DECISIONS.md` (choice, chosen-against, escape hatch; "no status field, because a pick is either the current pick or it is not in the document"); (2) a decision about this repository is a record under `docs/decision-records/`; (3) the boundary is stated in `AGENTS.md`.
- Consequences: + whole paved road on one page, picks keep the table as spine, repo decisions have a home; - two conventions in one repo (must be explained); "A pick that is genuinely contested over time has no supersession trail beyond the git history"; neutral: provisional picks' trailing section is the nearest thing to a status field.
- Confirmation: `AGENTS.md` states the boundary; `specs/stack-decisions/spec.md` scopes picks to `DECISIONS.md`; a pick appearing as an ADR or a repo decision as a numbered section contradicts this record.
- Revisit when: a pick is reversed and the reasoning for the reversal matters more than the current state.

## starter/scripts/perf-budget.sh — local Lighthouse perf-budget run (the ADAPT seam)

- CONTRACT: "get a PRODUCTION build of the app serving at PERF_WEBAPP_URL against representative data, then measure it (perf/run-perf.mjs) and print a baseline-vs-current report (perf/compare.mjs). Nothing here ever fails your push."

## starter/perf/run-perf.mjs — the runner

- Launches one headless Chrome (`chrome-launcher`, flags `--headless=new`, `--no-sandbox`, `--disable-gpu`); per route: warm (`WARMUP_HITS` = `PERF_WARMUP_HITS ?? 3` sequential GETs with `user-agent: perf-warmup`, `redirect: follow`, body drained, `PERF_WARMUP_DELAY_MS ?? 800` between; best-effort; "this is also why these numbers do NOT capture cold-start latency; that needs a separate cold probe"), then per profile measure `RUNS_PER_TARGET` runs via `lh-worker.mjs` in a child process (`execFile(process.execPath, [WORKER, url, profile, port], { maxBuffer: 64 MB })`), record the median per metric (`median()` sorts numbers; even count -> rounded mean of the two middle). A route failure is logged to stderr and skipped. Chrome killed in `finally`.
- Writes `{ generatedAt, origin, runsPerTarget, warmupHits, results }` to `LAST_RESULTS_FILE`, then `archiveHistory(payload)`.
- `archiveHistory`: file `history/<YYYY-MM-DD>-<TARGET>.json`; if it exists: "History snapshot ... already exists - left as is."; else writes `{ measuredAt, target, origin, runsPerTarget, warmupHits, deploy: { ref: "main", commit: <git rev-parse --short HEAD | "unknown">, note: "" }, changesSincePrevious, results }`.
- `changesSincePrevious(thisCommit, beforeDate)`: finds the latest prior same-target snapshot's `deploy.commit`; none -> `{ range: "n/a", summary: "First recorded run for this target.", likelyCause: "", keyCommits: [] }`; else `git log <prev>..HEAD --pretty=%h %s -- :(top)apps :(top)services :(top)packages` (root-relative pathspecs because cwd is the perf package), filtered by `PERF_SUBJECT_RX` = `/(perf|cache|lcp|ttfb|\btti\b|lazy|defer|prefetch|preload|fetchpriorit|n\+1|\bpool\b|\bindex\b|\bquery\b|latency|speed[- ]?index|batch|throttle|debounce|\bbound\b|progressive|standalone|bundle|tree[- ]?shak|exhaust)/i`, max 25; `summary`/`likelyCause` left empty for a human.

## starter/perf/compare.mjs — the report

- `WARN_PCT = 5`, `ALERT_PCT = 10`. Reads `LAST_RESULTS_FILE`; none -> "No latest run found. Run `pnpm test:perf` first." `--update` -> writes baseline from the latest run ("Commit the baseline file to record the accepted numbers.") and returns. No baseline -> "No baseline yet. ### src/index.ts — the instance
- "One instance, one config, imported by BOTH the Next.js proxy gate and the Fastify service". Sessions DB-BACKED and revocable ("Better Auth's default: every getSession() hits the database - no cookie cache, no JWT-blind gate"); short-lived with silent refresh: `updateAge` rolls expiry on activity, `expiresIn` is the cap.
- Storage: SQLite via `node:sqlite` (`DatabaseSync`) for zero-infra boot; "PRODUCTION SWAPS THIS TO POSTGRES: pass a `pg` Pool as `database` ... and set BETTER_AUTH_SECRET."
- **Lazy open**: the DB is opened on FIRST USE, not on import - "A module that opens a database as a side effect opens it for anyone who so much as imports it - a test, a script, and in particular a production build, where Next imports every route to collect its metadata and turbo runs two package builds at once. That is how two processes ended up racing to switch the same file to WAL". Implemented as `export const auth = new Proxy({} as AuthInstance, { get(_t, prop) { if (!instance) instance = open(); return Reflect.get(instance, prop, instance); } })` (bound through the instance so getters find `this`); `type AuthInstance = ReturnType<typeof open>` (taken from `open()` because `betterAuth`'s generic return type and the concrete instance are "assignable in neither direction").
- `open()`: `dbFile = process.env.AUTH_DB_PATH ?? path.resolve(process.cwd(), "../../data/starter.db")` ("Every workspace package sits two levels below the repo root ... Override with AUTH_DB_PATH when running from anywhere else (or in a container)"); `mkdirSync(dirname, { recursive: true })`; `new DatabaseSync(dbFile)`; pragmas in ORDER: `PRAGMA busy_timeout = 5000;` then `PRAGMA journal_mode = WAL;` ("switching to WAL takes an exclusive lock, so busy_timeout has to already be in force"); `betterAuth({ appName: "starter", baseURL: process.env.BETTER_AUTH_URL ?? "http://localhost:3000", secret: process.env.BETTER_AUTH_SECRET ?? "starter-dev-only-secret-do-not-deploy-me" ("Dev-only fallback ... Set BETTER_AUTH_SECRET in every deployed environment - session cookies are signed with it"), trustedOrigins: ["http://localhost:3000", "http://127.0.0.1:3000"], database, emailAndPassword: { enabled: true }, session: { expiresIn: 60*60*24*7 ("absolute cap: 7 days"), updateAge: 60*60*24 ("silent server-side refresh once a day of activity") } })`.
- `export type Session = typeof auth.$Infer.Session` - "The one session shape both gates share."
