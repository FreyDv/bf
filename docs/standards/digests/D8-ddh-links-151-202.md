## nest-event — npm (Yakup Cilesiz) — https://www.npmjs.com/package/nest-event
- Cited by README at line 1031 in section "Other things that can be a part of Infrastructure layer" to support: infrastructure-related events (a library for in-process events) belong in the infrastructure layer, not the domain.
- Fetch status: npmjs.com returned HTTP 403; package metadata and README were read from the npm registry JSON (registry.npmjs.org/nest-event) instead.
- What it is: a decorator-based event handling add-on for NestJS built on Node's `EventEmitter`; goal is letting Nest modules talk to each other without importing one another.
- Key API / idea:
  - Import `NestEventModule` into the root module; it ships an internal default emitter (not created if you register a named emitter without a default).
  - `@Emitter(name?)` on a class that extends `EventEmitter` registers it as an emitter; several named emitters are supported (e.g. a websocket client registered as `'ws-emitter'`).
  - `@On('event-name')` on a method of an `@Injectable()` provider subscribes that method (e.g. an `EmailService.onUserCreated(user)` handler).
  - `@From('emitter-name')` stacked above `@On` picks which named emitter a handler listens to.
  - `NestEventEmitter` is an injectable provider: `emit(name, payload)` on the default emitter, or `emitter('name').emit(...)` for a named one (example: a `UserController.signup()` emitting `'user-created'`).
- Metadata: v1.0.8, published 2019-11-15, MIT, depends on `@nestjs/common`/`@nestjs/core` ^6.7 and `@nestjs-plus/discovery`; README lists "add tests" as a future goal.
- Trade-offs, caveats: unmaintained since 2019 and pinned to Nest 6-era peer packages; README code samples import from a placeholder relative path and reference undefined symbols; no test suite.
- How it applies to a TypeScript/NestJS backend: the README cites it only as an example of "where in-process event plumbing lives" (infrastructure); the maintained equivalent today is the official `@nestjs/event-emitter` (`EventEmitterModule`, `@OnEvent`, `EventEmitter2`), which covers the same decorator-based pattern.

## Task Scheduling — NestJS documentation — https://docs.nestjs.com/techniques/task-scheduling
- Cited by README at line 1032 in section "Other things that can be a part of Infrastructure layer" to support: periodic cron jobs and task launchers are infrastructure-layer code.
- Fetch status: fetched (current docs; the page now also documents newer `@nestjs/locks` and "NestJS Observe" features).
- What it defines: scheduling = running code at a fixed time, at intervals, or once after a delay; `@nestjs/schedule` wraps the Node `cron` package.
- Recommendations and rules:
  - Install `@nestjs/schedule`; import `ScheduleModule.forRoot()` in the root module exactly once — every additional `forRoot()` import re-registers all handlers, so each job would fire once per import.
  - Declarative jobs are registered in `onApplicationBootstrap`, i.e. only after all modules load.
  - `@Cron(pattern)` on a provider method; pattern fields: optional seconds, minutes, hours, day-of-month, month, day-of-week; supports `*`, ranges/lists (`1-3,5`), steps (`*/2`). Examples: `45 * * * * *` = every minute at second 45; `0 */30 9-17 * * *` = every 30 min between 9 and 17; `0 30 11 * * 1-5` = weekdays 11:30.
  - Use the `CronExpression` enum for common schedules (e.g. `EVERY_30_SECONDS`).
  - Pass a JS `Date` instead of a pattern to run exactly once at that time (e.g. `new Date(Date.now() + 10_000)`).
  - Cron options (2nd argument): `name` (needed for dynamic access), `timeZone` (invalid zones throw), `utcOffset` (never combine with `timeZone`), `waitForCompletion` (skip ticks while a previous run is still executing), `disabled` (never runs).
  - `@Interval(ms)` / `@Interval(name, ms)` uses `setInterval`; `@Timeout(ms)` / `@Timeout(name, ms)` uses `setTimeout` (one-shot after startup).
  - Every `@Cron`/`@Interval`/`@Timeout` handler is wrapped in try/catch and exceptions are logged, so a throwing job does not crash the process.
  - Dynamic API through injected `SchedulerRegistry`: `getCronJob(name)` then `stop()`, `start()`, `setTime(CronTime)`, `lastDate()`, `nextDate()` (Luxon `DateTime`; call `toJSDate()`), `nextDates(n)`; `addCronJob(name, new CronJob(pattern, cb))` then `job.start()` (import `CronJob` from `cron`); `deleteCronJob(name)`; `getCronJobs()` returns a `Map` (wrap `nextDate()` in try/catch for jobs that already fired with no future date). Same pattern for intervals (`addInterval`, `getInterval` + `clearInterval`, `deleteInterval`, `getIntervals`) and timeouts (`addTimeout`, `getTimeout` + `clearTimeout`, `deleteTimeout`, `getTimeouts`).
  - Several instances: the scheduler runs every job in every process, so N replicas run a job N times per tick; add `@OnOneInstance({ key })` from `@nestjs/locks` (shared lock store such as PostgreSQL or Redis; first instance takes a lease, others skip the tick, another instance takes over if the owner dies) and `@WithoutOverlapping()` for jobs that can outlast their interval.
  - Knowing a job actually ran: a job can silently stop (crash, eviction, bad expression) with no error; the docs point to NestJS Observe ("job silence" alert rules from 2 minutes to 7 days, mute schedules) and to `TracerService` for spans/metrics from cron handlers.
- Examples: `TasksService` with `@Cron('45 * * * * *') handleCron()` logging via `Logger`; `@Cron('* * 0 * * *', { name: 'notifications', timeZone: 'Europe/Paris' })`; `@Cron('0 2 * * *') @OnOneInstance({ key: 'invoices:nightly-export' }) exportInvoices()`; official sample `sample/27-scheduling`.
- Trade-offs / caveats: in-process scheduling is per replica (needs distributed locking in multi-instance deployments); no built-in persistence of job history; dynamic jobs must be started explicitly.

## You aren't gonna need it (YAGNI) — Wikipedia — https://en.wikipedia.org/wiki/You_aren%27t_gonna_need_it
- Cited by README at line 1041 in section "General recommendations on architectures, best practices, design patterns and principles" to support: follow YAGNI and do not over-engineer; some patterns can be simplified or skipped per project.
- Fetch status: fetched.
- Definition: an Extreme Programming principle — implement functionality only when it is actually needed, never because you foresee needing it (Ron Jeffries' formulation).
- Context captured:
  - Arises from XP; named in Jeffries/Anderson/Hendrickson's *Extreme Programming Installed* and Beck's *Extreme Programming Explained* (ch. 17).
  - It is the principle behind the XP practice "do the simplest thing that could possibly work" (DTSTTCPW).
  - XP defines YAGNI as dependent on supporting practices: continuous refactoring, continuous automated unit testing, continuous integration; without continuous refactoring it can produce disorganized code and rework (technical debt).
- Related principles listed: DRY, feature creep, "if it ain't broke, don't fix it", KISS, minimum viable product, MoSCoW, Muntzing, overengineering, SRP, SOLID, Unix philosophy, lazy evaluation/loading.
- Caveats: the article gives no explicit exceptions; its only stated cost of misuse is technical debt when refactoring is neglected.

## KISS principle — Wikipedia — https://en.wikipedia.org/wiki/KISS_principle
- Cited by README at line 1043 in section "General recommendations on architectures, best practices, design patterns and principles" to support: complex architecture and SOLID can conflict with YAGNI and KISS; a pragmatic programmer balances them.
- Fetch status: fetched.
- Definition: a design principle that treats simplicity as a primary goal and unnecessary complexity as something to avoid; "Keep it simple, stupid".
- Origin captured: attributed (not firmly established) to Kelly Johnson of Lockheed Skunk Works; a "Keep It Short and Simple" variant appears in 1938; in use by the US Navy by 1960 and popular by 1970. Johnson's rationale: a combat aircraft must be repairable in the field by an average mechanic with a small set of basic tools — "stupid" refers to the gap between how things break and the sophistication available to fix them, not to the designer.
- Variants: "keep it simple, silly / soldier / sweetie", "keep it simple and straightforward", "keep it short and simple".
- Software-development links the article makes: DRY, minimalism (computing), Unix philosophy, rule of least power, "worse is better", YAGNI, RISC, chartjunk (visual clutter analogy), and the contrasting Perl motto "there's more than one way to do it".
- Related maxims listed: Occam's razor; Saint-Exupéry's "perfection is reached when there is nothing left to remove" idea; Einstein's "as simple as possible, but not simpler" (attributed); Chapman's "simplify, then add lightness"; Stroustrup's "make simple tasks simple"; Rube Goldberg / Heath Robinson machines as anti-examples; "perfect is the enemy of good"; overengineering as the opposite tendency.

## SOLID Principles and the Arts of Finding the Beach — Sebastian Kübeck — https://sebastiankuebeck.wordpress.com/2017/09/17/solid-principles-and-the-arts-of-finding-the-beach/
- Cited by README at line 1061 in section "General recommendations on architectures, best practices, design patterns and principles" to support: principles are hint signs that require experience; they do not tell you when you have found a good solution or gone too far (the README quotes this article's conclusion).
- Fetch status: fetched (published 2017-09-17, updated 2021 with a reference to Dan North's CUPID).
- What it argues:
  - Guidance in software is hard to communicate across backgrounds; principles such as SOLID are direction signs, not precise rules or stopping criteria.
  - Metaphor: the sign = a principle/heuristic; the beach = a good solution; the sea = having gone too far (outside the principle's scope, where the expected benefits vanish).
- Argument structure (sections): Logic & Mathematics (deduction: axioms → provable, repeatable conclusions); Science (induction from observations; theories hold until falsified — Popper's swans); The Engineering Method (engineers face many feasible implementations; physical constraints narrow options in other disciplines, software's flexibility makes its solution space much larger, so engineers navigate with heuristics/rules of thumb — Koen's *Discussion of the Method*); Back on the Beach (SOLID = Martin's OO design principles, 2005); Conclusion.
- Recommendations and rules:

  - Gain real-project OO experience before expecting SOLID to help; without it the principles are of little use.
  - Judge for yourself when a solution is good enough and when a principle has been over-applied; the principle will not tell you.
  - Learn by cycles of trying, failing, analysing, discussing with people, fixing and learning again; the author knows no shortcut.
  - Do not treat heuristics as laws comparable to mathematical proofs or scientific theories; they are weaker, provisional helpers that stop you doing things you would regret.
- Vocabulary: deduction, induction (and mathematical induction as a form of deduction), falsifiability, heuristic / rule of thumb / "law of engineering", scope of a principle.

## Yagni — Martin Fowler (bliki) — https://martinfowler.com/bliki/Yagni.html
- Cited by README at line 1062 in section "General recommendations on architectures, best practices, design patterns and principles" to support: avoid over-engineering; evaluate the cost of every pattern before adding it.
- Fetch status: fetched (26 May 2015).
- What it argues: "You Aren't Gonna Need It" — do not build a capability now because you presume you will need it later; it names the XP practice of simple/incremental design and originated with Kent Beck and Chet Hendrickson on the C3 project.
- Worked example: an insurance start-up building storm-risk pricing now while piracy-risk pricing is "needed in six months"; a "presumptive feature" is any code supporting a feature not yet usable; if piracy pricing takes two months, yagni says do not start it for another four.
- The four costs of ignoring yagni:
  - Cost of build — analysis, programming and testing effort that may be wasted if the presumed need is wrong (and agile assumes needs change; Fowler cites Kohavi et al.: only about a third of carefully analysed Microsoft features improved their target metric, so the odds a presumptive feature is unnecessary are at least two-thirds).
  - Cost of delay — even a correct presumptive feature displaces work that could ship value now (storm-risk sales two months earlier = two months of revenue).
  - Cost of carry — extra code adds complexity that slows every other feature until the presumptive one is used or removed (removal has its own cost).
  - Cost of repair — the "right feature built wrong": built before you understood users, codebase or tools, so it needs redesign (technical debt) or workarounds.
- Recommendations and rules:
  - Compare "build now" against "build later" honestly: include the cost of delay and the probability (≥ 2/3) that the feature is never needed.
  - Mentoring technique: ask the developer to imagine the refactoring needed to add the capability later; usually the later cost is not much higher.
  - Prefer cheap enablers that add no complexity now but reduce later cost (e.g. a lookup table for error messages instead of inline literals, easing future translation).
  - Apply the same reasoning to speculative abstractions (parameterising the storm calculator "for piracy"); any abstraction that makes current requirements harder to understand is presumed guilty.
  - Apply yagni at small scale too: do not add fields, methods or a general-purpose option until it is needed; many small "sure to be needed" hours add up.
  - Yagni applies only to capabilities added to support presumptive features and only when they add complexity now; it never applies to work that makes code easier to change — refactoring, self-testing code and continuous delivery are enabling practices, not yagni violations.
  - Yagni is not an excuse to neglect code health; it requires malleable code and in turn makes code more malleable (it both enables and is enabled by evolutionary design).
- Caveats: occasionally an expensive change arrives that an earlier change would have made cheap; such failures are memorable (availability bias) but rare, and their cost is outweighed by yagni's successes. Quoted idea from Jeremy Miller: unused extensibility points tend to get in your way.
- Related reading it names: Fowler's "Is Design Dead?" (enabling practices for evolutionary design); Ward's Wiki discussion.

## Model–view–controller — Wikipedia — https://en.wikipedia.org/wiki/Model%E2%80%93view%E2%80%93controller
- Cited by README at line 1076 in section "Recommendations for smaller APIs" to support: for data-centric CRUD applications with little business logic, MVC (software as mostly a view of the database) is a better fit than DDD-style layering.
- Fetch status: fetched.
- Definition: a UI architectural pattern splitting program logic into Model (internal representation of information, data, logic and rules, independent of the UI), View (presentation of the model; many views per model possible) and Controller (accepts input and turns it into commands for the model or view).
- History captured: created by Trygve Reenskaug at Xerox PARC in the late 1970s for Smalltalk-79 (as a way for users to control a large, complex data set); Smalltalk-80 shipped abstract view/controller classes; Krasner & Pope's 1988 description differs (controllers as invisible objects linking one model to many views); later variants HMVC, MVA, MVP, MVVM.
- Web usage captured:
  - WebObjects (1996) enforced MVC server-side; Spring (2002) cemented Java+MVC; Rails (2004) and Django (2005, "model-template-view") popularised it for rapid development.
  - In these frameworks a model type usually maps to a database table (ORM); views are HTML templates, often one per controller action; the controller (Rails) or "view function" (Django) handles the request and prepares the response.
  - Thin-client era: all three parts ran on the server, requests arrived as links/form posts, responses were full pages; later frameworks moved parts of MVC to the client with Ajax synchronisation.
- Advantages listed (LaLonde & Pugh): presentation and data independent (multiple simultaneous views); composable widgets; swappable input modes via controllers; separate input and output processing.
- Caveats: the pattern has been interpreted so variously that it is ambiguous (Moore et al.); Django's naming (controller called "view", view called "template") departs from the standard; the article has no explicit criticism list.
- Related patterns named: action–domain–responder, entity–control–boundary, PAC, observer, strategy, front controller, active record, DAO, DTO, inversion of control.

## Behavior-driven development — Wikipedia — https://en.wikipedia.org/wiki/Behavior-driven_development
- Cited by README at line 1084 in section "Behavioral Testing" to support: behavioral (black-box) testing of external behaviour, and BDD's natural fit with DDD's ubiquitous language.
- Fetch status: fetched.
- Definition: an agile method centred on collaboration between business and technical people to reach a shared understanding of the problem, expressed in a natural-language DSL whose statements become executable tests ("living documentation" / acceptance tests). It grew out of TDD combined with DDD and OOAD ideas; Dan North's "Introducing BDD" is the usual origin reference.
- Principles captured:
  - Name tests after desired behaviour, not implementation; derive behaviour from business requirements with business value (outside-in).
  - Specifications are written in business language with real data: intention-revealing, essential, focused.
  - Scenarios should be declarative (business language, no UI references), not imperative.
- Specification format: a user story with Title; Narrative "As a <role> I want <feature> so that <benefit>"; acceptance criteria as scenarios of Given (initial context, one or more clauses) / When (triggering event) / Then (expected outcome, one or more clauses). BDD does not mandate exact formatting but teams should standardise a simple version; Cucumber calls this Gherkin. Unit-level "specifications" (When/Then on a stack, etc.) are the more technical complement to story-level tests.
- Ubiquitous language link: borrowed from DDD — a semi-formal language shared by developers and non-technical members, used and developed by all; some formality is needed so tools can process it; the specifications form a domain model that can be reasoned about.
- Tooling principles: a BDD tool is a test framework tied to the ubiquitous language; it reads the spec, recognises keywords (Given…), splits scenarios into clauses, maps each clause to developer-written step code and runs each scenario; if the tool cannot make the documents executable, change the writing style or the tool. Named tools: Cucumber/Gherkin, Behat, RSpec, Concordion, Gauge, Jasmine, Squish, FitNesse.
- The Three Amigos (specification workshop): product owner, QA and developer discuss requirements as specification-by-example; business defines the problem (not the solution), development proposes solutions, testing questions them with what-if scenarios.
- Caveats: the two-step process (parse, then locate and run step code) is more laborious; value depends on keeping the readable documents maintained; the article carries a promotional-content banner.

## Gherkin Reference — cucumber.io docs — https://cucumber.io/docs/gherkin/reference/
- Cited by README at line 1088 in section "Behavioral Testing" to support: Gherkin syntax for human-readable feature files (the README's `create-user.feature`).
- Fetch status: fetched.
- What it defines: Gherkin structures executable specifications with keywords; most lines start with a keyword; keywords are localised into 70+ languages.
- Syntax rules:
  - Comments only as whole lines starting with `#` (no block comments); indent with spaces or tabs, two spaces recommended.
  - Some keywords take a colon, some do not; a stray colon after a step keyword makes the step be ignored.
  - Primary keywords: `Feature`, `Rule` (Gherkin 6+), `Example`/`Scenario`, `Given`/`When`/`Then`/`And`/`But`/`*`, `Background`, `Scenario Outline`/`Scenario Template`, `Examples`/`Scenarios`. Secondary: `"""` doc strings, `|` data tables, `@` tags, `#` comments.
  - Free-form descriptions may follow Feature/Rule/Example/Background/Scenario Outline lines (ignored at runtime, shown in reports, may use Markdown) as long as no line starts with a keyword.
- Keyword rules and advice:
  - `Feature`: first primary keyword in the file, one per `.feature` file; high-level description grouping related scenarios; tags above it group features independently of directory layout; name/description have no runtime meaning.
  - `Rule`: optional; one business rule, grouping one or more illustrating examples; may have its own Background.
  - `Example`/`Scenario`: a concrete example of a rule, made of steps; recommended 3-5 steps — long scenarios lose value as specification; pattern = context (Given) → event (When) → outcome (Then); examples double as tests, forming an executable specification.
  - Steps: executed in order; Cucumber matches the text after the keyword against step definitions ignoring the keyword, so identical text under Given and Then collides — write unambiguous domain language ("my account has a balance of £430" vs "my account should have a balance of £430").
  - `Given`: put the system in a known state (create objects, seed data); like use-case preconditions; avoid describing user interaction; several Givens are fine, use And/But after the first.
  - `When`: an event or action by a person or another system; describe it without technology/UI assumptions (the "imagine it's 1922" test); implementation details belong in step definitions.
  - `Then`: an expected, observable outcome (report, UI, message) checked by an assertion; do not inspect databases or internal state — verify only what a user or external system can observe.
  - `And`/`But`: readability replacements for repeated keywords; `*` can replace any step keyword, useful for bullet-like lists.
  - `Background`: Given steps shared by all scenarios of a Feature (or Rule); runs before each scenario after Before hooks; one per Feature/Rule. Tips: do not set up complicated state the reader does not need (use higher-level steps like "I am logged in as a site owner"); keep it short (more than ~4 lines → push details into steps); make it vivid with memorable names rather than "User A"; keep scenarios short and few so the Background stays visible; conditional hooks are an alternative.
  - `Scenario Outline` with `Examples`: template steps with `<param>` placeholders run once per table row (header excluded); parameters may also appear in descriptions and multiline arguments; avoids copy-pasting near-identical scenarios.
  - Doc strings: `"""` (or ```` ``` ````) blocks passed as the last argument to the step; dedented relative to the opening delimiter; optional content-type annotation (e.g. `markdown`); editor support varies.
  - Data tables: `|`-delimited rows passed as the last argument; escapes `\n`, `\|`, `\\`; a Data Table API exists for manipulating them in step code.
  - Spoken languages: write in the users'/domain experts' language rather than translating; `# language: xx` on line 1 (default `en`); some runners allow a configured default.
- Examples shown: "Guess the word" feature (Maker/Breaker), "Highlander" rules, blog-posting Background, "eating cucumbers" outline, user table, Norwegian feature.

## Vertical Slice Architecture — Jimmy Bogard — https://jimmybogard.com/vertical-slice-architecture/
- Cited by README at line 1192 in section "Folder and File Structure" to support: vertical slicing — each use case folder contains most of what it needs (controller, service, DTOs, command).
- Fetch status: fetched (19 Apr 2018).
- What it argues:
  - Organise a system around individual requests/use cases rather than technical layers; couple code along the axis of change.
  - Origin: a long project that began as an onion architecture cracked within months; the team moved to what became CQRS and then to request-centred slices, which the author has used for 7-8 years across application types.
- Problems it attributes to layered / n-tier / onion / clean approaches: monolithic in approach; suited to only a minority of typical requests; mock-heavy; rigid dependency rules (controller → service → repository) that rarely help; unnecessary abstractions around things that should not be abstracted; feature changes touch every layer (UI, models, validation, …) because coupling runs across layers instead of along features.
- Definition: take an n-tier/hexagonal design, remove the gates between layers, and group everything a request needs from front end to back end into one slice; the request is the unit of organisation and each request is a distinct use case; commands (POST/PUT/DELETE) and queries (GET) separate naturally, so CQRS comes "for free".
- Recommendations and rules:
  - Minimise coupling between slices; maximise coupling within a slice, so changes stay local.
  - Keep cross-slice sharing minimal to limit side effects; new features should add code, not modify shared code.
  - Drop shared layer abstractions (repositories, services, controllers) except where a tool forces them (web framework controllers, ORM units of work).
  - Let each slice decide how to fulfil its request; domain-logic style (Fowler's PoEAA patterns) is chosen per slice, not application-wide.
  - Start each slice as a Transaction Script; refactor towards richer patterns only when code smells in the business logic appear; push complex logic into the domain model when it emerges (what DDD services "should have been").
  - Use the Fowler/Kerievsky refactoring catalogue as the toolkit.
- Trade-offs / caveats: the approach presupposes a team that recognises code smells and can refactor; if a team cannot tell when a service does too much, this style is probably not for them; claimed to scale beyond layered/concentric architectures, but only with refactoring skill.

- How it applies to a TypeScript/NestJS backend: the README's `commands/<use-case>/` and `queries/<use-case>/` folders are this idea — each folder owns its controller, handler, DTOs and command, while entities/repositories shared across slices live at module level.

## Approximate string matching — Wikipedia — https://en.wikipedia.org/wiki/Approximate_string_matching
- Cited by README at line 1197 in section "File names" to support: descriptive dotted type suffixes (`*.service.ts`, `*.entity.ts`) make files easy to find with an editor's fuzzy search (Ctrl/Cmd+P).
- Fetch status: fetched.
- Definition: finding strings that match a pattern approximately rather than exactly ("fuzzy search"); two sub-problems — approximate substring matching inside a text, and finding dictionary strings close to a pattern.
- Core concepts bearing on the README's claim:
  - Closeness = edit distance: the number of primitive operations (insert, delete, substitute; sometimes adjacent transposition) needed to turn one string into the other; Hamming distance when only substitutions are allowed; costs may be uniform with a limit (e.g. "coil" matches "foil", "coils", "oil" at distance one but not "foal"), per-operation, or weighted.

- Caveat: unsuited to binary data such as images/audio.

## Composition over inheritance — Wikipedia — https://en.wikipedia.org/wiki/Composition_over_inheritance
- Cited by README at line 1244 in section "Prevent massive inheritance chains" to support: use composition instead of deep inheritance.
- Fetch status: fetched.
- Definition: an OOP principle (from *Design Patterns*, 1994) favouring polymorphic behaviour and code reuse by composing objects from components that implement the desired behaviour ("has-a") rather than inheriting from a base class ("is-a"); calls are forwarded to the component ("method forwarding"/delegation). Inheritance and composition usually work together; Go and Rust rely on composition only.
- Rationale: business classes are easier to assemble from components than to fit into one family tree (accelerator pedal and steering wheel share few traits yet both are car parts); behaviours become separate interfaces, which simplifies initial design and avoids restructuring hierarchies when requirements change; composition can change at run time, subtyping is static.
- Example (C++): inheritance approach — `GameObject` with virtual `update/draw/collide`, subclasses `Visible`, `Solid`, `Movable`, and concrete `Player` (all three), `Cloud` (visible+movable), `Building` (visible+solid), `Trap` (solid) → needs multiple inheritance (diamond problem) or hand-written combination classes with duplicated code. Composition approach — delegate interfaces `VisibilityDelegate` (`NotVisible`/`Visible`), `UpdateDelegate` (`NotMovable`/`Movable`), `CollisionDelegate` (`NotSolid`/`Solid`); `GameObject` owns one of each and forwards; `Player` = Visible+Movable+Solid, `Smoke` = Visible+Movable+NotSolid; new combinations need no new hierarchy.
- Benefits listed: flexibility; more natural domain modelling; long-term stability; simpler initial design via behaviour interfaces; accommodates requirement changes without restructuring; avoids ripple effects of small changes in deep hierarchies; run-time reconfiguration.
- Drawbacks listed: forwarding boilerplate — a composing type may have to re-implement every component method just to delegate, whereas inheritance only overrides what differs (C# `Employee` / `HourlyEmployee` / `SalariedEmployee` example); hence the principle is a selectively applicable suggestion, not a law. Mitigations by language: default interface methods (Java 8+, C# 8+), traits (PHP, Rust, Scala exports), mixins (Dart), type embedding (Go), Kotlin delegation syntax, Lombok `@Delegate`, D `alias this`, Swift protocol extensions, Raku `handles`.
- Empirical note: Tempero et al. (2013, 93 Java projects) found only limited scope for replacing inheritance with composition (median 2% of inheritance uses purely for internal reuse, 22% for reuse only) and no broad abuse.
- Related: delegation pattern, Liskov substitution, State and Strategy patterns, role-oriented programming.

- What it argues: flexibility comes from good abstractions (interfaces), not from inheritance; use `final` whenever possible; TL;DR — a class should be final when it implements an interface and declares no public methods beyond that interface.
- Eight reasons to use `final` (with rationale):
  - Prevents "inheritance chains of doom" (example chain: Db ← Core ← User ← Admin ← Bot ← BotThatDoesSpecialThings ← PatchedBot) that arise from fixing inadequate classes by subclassing.
  - Encourages composition instead of stuffing features into existing code (haste, feature creep).
  - Forces thought about the public API: subclasses adding setters/accessors outside the interface often hide a different problem, violate the contract, change dependencies at run time, or mask a bug.
  - Forces a small public API: many public methods usually means an SRP violation.
  - A final class can always be opened later at no cost except having to justify it to the team — which often produces a better solution.
  - `extends` breaks encapsulation: treat any class not designed for extension as final, because subclassing it risks unforeseen behaviour and BC breaks.
  - The flexibility people fear losing is rarely needed — ask why a custom implementation of the contract or composition will not do; needing to drop `final` is a smell.
  - Freedom to change internals: with `final`, only the public API matters, so refactoring is safe.
- When to avoid `final`: it only works if (1) an interface abstraction exists that the class implements and (2) the class's whole public API is in that interface; otherwise the class will likely be opened up later. Exception: classes representing immutable, system-wide concepts (a calculator's `sum(a, b)`) may be final without an interface. Adding `final` to an existing published class is a BC break requiring a major semver bump.
- Examples (PHP): `EmailingRegistrationService extends RegistrationService` overriding `registerUser()` to send mail → replace with `final class EmailingRegistrationService implements RegistrationServiceInterface` that wraps an injected `RegistrationServiceInterface` (decorator/composition); `SwitchableDbRegistrationService` adding `setDb()` via subclassing → flagged as hiding a need (e.g. master/slave connection), coupling to the concrete class, unsupported run-time dependency change, symptom-fixing.
- Vocabulary: inheritance-oriented programming (anti-pattern name), contract/interface, public API, encapsulation, feature creep, SRP, semver/BC break.
- How it applies to a TypeScript/NestJS backend: TypeScript has no `final`; the README's `@final` decorator throws when a subclass is instantiated; the interface-first rule maps to "export an interface/abstract port, keep the implementation class non-extensible, inject through DI".

## Final classes by default, why? — Matthias Noback — https://matthiasnoback.nl/2018/09/final-classes-by-default-why/
- Cited by README at line 1253 in section "Prevent massive inheritance chains" to support: classes should be final by default; extension is a deliberate design decision.
- Fetch status: fetched (11 Sep 2018, PHP).
- What it argues: if none of the reasons to add an interface apply, use a class and make it `final`; subclassing should be an explicit, separate use case rather than the default (credits Marco Pivetta's influence).
- Problems with non-final classes (each a reason): subclass overrides can break the integrity the original designer assumed; inherited state may become inconsistent; the subclass may stop being a proper substitute (Liskov); subclasses inherit internals they do not need and must work around; subclasses depend on implementation details and break as the parent evolves; parent and child futures become intertwined; refactoring the parent becomes risky because you cannot know which subclasses rely on which detail; the kinship suggested by inheritance may be false.
- Recommendations and rules:
  - Replace behaviour instead of overriding it: reconfigure an object by passing different constructor arguments (dependency inversion + open/closed), especially when the original code cannot be modified (used elsewhere or in a vendor package).
  - Template Method (abstract base with abstract hooks, e.g. Symfony's abstract `Voter` with `supports()`/`voteOnAttribute()`) is better than free overriding but still unnecessary: express the varying part as an interface (`AttributeVoter`) and make the algorithm holder a `final class Voter` that delegates — no inheritance, private internals, every class final, each reusable as a building block rather than a template; the outer interface may even be dropped if the algorithm never varies.
  - Prefer composition over inheritance in most cases; to change part of an algorithm, create a new class and compose it.
  - Inheritance may fit when modelling a true hierarchy whose subclasses are proper substitutes, and even then prefer inheriting from abstractions; the author regrets most of his earlier inheritance-based designs.
  - Treat "allow extension" as a distinct use case of a class, separate from instantiate/call/query/mutate; it has limiting consequences and should not be the default.
  - Making `final` the default yields smaller classes, fewer maintenance issues, easier refactoring and reusable building blocks.
  - On "you can always remove final later": true, but adding it is equally cheap and closing down is safer than opening up; when extension seems needed, look for a composition-based replacement instead.
  - On mocking tools that cannot mock final classes: the tools are right (test doubles extend the class); either do not replace the real class (entities and value objects) or introduce an interface and mock that — if a class "should have had an interface", add one.
  - Practical: add `final` to the IDE's new-class template; make it a code-review item; the burden of proof is on the author of a non-final class.
- Vocabulary: reconfiguration, test double, Template Method, dependency inversion, open/closed.
- How it applies to a TypeScript/NestJS backend: same guidance — vary behaviour through injected interfaces (Nest providers bound to tokens) rather than subclassing services; keep aggregates/value objects unmocked in tests.

## DDD, Hexagonal, Onion, Clean, CQRS, … How I put it all together (Explicit Architecture #1) — Herberto Graça — https://herbertograca.com/2017/11/16/explicit-architecture-01-ddd-hexagonal-onion-clean-cqrs-how-i-put-it-all-together
- Cited by README at line 1265 in section "Articles" to support: the main reference architecture the whole README synthesises (its diagram, layer names, ports/adapters and CQRS flow).
- Fetch status: fetched in full (16 Nov 2017, updated Mar 2020; part of "The Software Architecture Chronicles"; used in production on a multi-tenant e-commerce SaaS handling 20M+ bus messages/month).
- Fundamental blocks (from EBI and Ports & Adapters): user interface (any delivery form), application core (the business logic — what actually matters; it should not care which UI triggers it), infrastructure (code connecting the core to tools). Flow: UI → core → infrastructure → core → UI.
- Tools: external software the app uses (DB engines, search engines, web servers, CLI). Key split: tools that tell the app to do something (web server, CLI) vs tools the app tells to do something (database); this decides how the connecting code is built.
- Ports and adapters:
  - Port = specification of how a tool uses the core or how the core uses a tool; an interface, possibly several interfaces plus DTOs. Rule: ports live inside the business logic; adapters outside. Rule (stated as paramount, repeated): design ports to fit the core's needs, never to mimic the tool's API.
  - Primary/driving adapters wrap a port and translate delivery input into core calls: controllers, console commands receiving a port implementation by constructor injection; the port may be a service interface, a repository interface, or a command/query bus (controller builds a command/query and hands it to the bus).
  - Secondary/driven adapters implement a port and are injected wherever the core type-hints it; example: a persistence interface with "save array" and "delete row by id", a MySQL adapter now, a PostgreSQL/MongoDB adapter later with no core change.
  - Inversion of control at architecture level: adapters depend on a tool and a port; the core depends only on ports; all dependencies point to the centre.
- Application core organisation (Onion Architecture brings DDD layers into the hexagon; dependencies still inward):
  - Application layer: use cases (processes triggered by one or more UIs — a CMS may expose some use cases to admin UI, CLI, API); contains application services and their interfaces, ports for ORM/search/messaging, and command/query handlers if a bus is used. An application service / command handler: (1) finds entities via a repository, (2) tells them to perform domain logic, (3) persists via the repository. Command handlers either hold the use-case logic or merely delegate to an application service — choose by context (do application services already exist? does the bus need handler interfaces?). Application events live here: they represent use-case outcomes and trigger side effects (emails, third-party notifications, push, use cases in other components).
  - Domain layer: data and logic specific to the domain, unaware of the application layer and of what triggers it.
  - Domain services: for logic spanning several entities that belongs to none; do not put it in an application service (not reusable; domain logic must stay out of the application layer); a domain service receives entities, performs the logic, may use other domain services and domain objects, knows nothing of application services or repositories.
  - Domain model: the centre, depends on nothing outside; entities, value objects, enums; domain events fire when data changes and carry the changed properties/new values (well suited to event sourcing).
- Components (coarse-grained segregation by sub-domain/bounded context, cutting across layers; based on Martin's Screaming Architecture and Simon Brown's "package by component", which the author prefers over package-by-layer and package-by-feature): examples Authentication, Authorization, Billing, User, Review, Account. Rule: treat contexts like authentication/authorization as external tools — wrap them in an adapter behind a port.
- Decoupling components: DI and dependency inversion are not enough at component level — a component must not reference any code unit of another component, not even interfaces; use events, a shared kernel, eventual consistency and a discovery service.
  - Triggering logic in another component: never call B from A directly; A dispatches an application event, B's listener reacts (A depends only on the dispatcher). Caveat: if the event class lives in A, B depends on A → put shared events, specification objects etc. in a Shared Kernel library both depend on; keep it minimal because any change hits every component; in polyglot systems make it language-agnostic (e.g. JSON event descriptions from which each service generates classes). Works for monoliths and microservices. When the trigger must be synchronous, A makes a direct call (HTTP) to B via a discovery service (ask where B is, or let the discovery service proxy the request) — components are coupled to the discovery service but not to each other.
  - Getting data from another component: a component may read any data but may change only data it owns. Shared storage: read non-owned data via read-only queries (billing reading the account's client name). Segregated storage per component: each store holds the data it owns (single source of truth) plus read-only copies of others' data, kept current by listening to the owner's domain events.
- Flow of control (after Uncle Bob's Clean Architecture diagrams; every cross-boundary dependency points inward):
  - Without a bus: controller depends on an application service or on a query object. Query path: query returns raw data from an optimised query as a DTO → view model (may hold view logic) → view. Command path: application service holds use-case logic, depends on repositories (which return entities holding the logic), may use a domain service (rare), may use an event dispatcher to announce the use case happened. Persistence interface = abstraction over the ORM (swap ORM with no core change); repository interface = abstraction over the persistence engine (switching MySQL→MongoDB may keep the persistence adapter if the ORM is the same, but repositories must change because the query language differs). The application-service interface may be unnecessary (internal code unlikely to be swapped).
  - With a command/query bus: controller depends on the bus and on a command/query class, instantiates the message and hands it over; the bus finds the handler; the handler holds the use case (extract an application service only when logic must be reused by another handler); bus, commands, queries and handlers must not reference each other — mapping is configured.
- Conclusion / trade-offs: goal is loose coupling and high cohesion so change is easy, fast and safe; the patterns are guidelines, not rules; how far to go depends on functional requirements, time frame, application lifespan and team experience; "the map is not the territory" — the concrete use case decides. The infographic is a planning concept map; a follow-up post ("More than concentric layers", 2018) and a later one on reflecting architecture in code are promised.
- Sources it builds on: EBI; Ports & Adapters; Onion; Clean Architecture; DDD (layers, bounded contexts, shared kernel); Screaming Architecture; Brown's package-by-component; CQRS/command bus; event sourcing.
- Author clarifications from the comment thread (labelled as comments, not article text): he rarely uses aggregates; usually no application-service interfaces except for test doubles; two valid repository placements (repository interface as the port with implementations in infrastructure, or a persistence port in front of an ORM adapter with repositories in the core); incoming third-party HTTP callbacks are driver adapters whose payload interpretation is delegated to infrastructure via a per-caller strategy; split "decide which entities to load" (domain service) from loading (repository) and acting (domain service again); a hardware "sensors" component is a legitimate component; pragmatic exceptions (UI reading infrastructure directly) are acceptable if architecture tests flag them for discussion.

## Hexagonal Architecture — QWAN (Marc Evers, Willem van den Ende, Rob Westgeest) — https://www.qwan.eu/2020/08/20/hexagonal-architecture.html
- Cited by README at line 1266 in section "Articles" to support: a practitioner introduction to ports & adapters with explicit trade-offs.
- Fetch status: fetched (20 Aug 2020).
- What it argues: Hexagonal Architecture (Cockburn, 1990s) structures a component/service and manages its dependencies; it is explicitly "not a best practice" — a pattern with trade-offs that in the authors' 10+ years of use usually pays off.
- Critique of layering: presentation → business → data layers with downward dependencies ("gravity": everything transitively depends on the bottom layer, which must be sturdy; a shared-code-base team built many unused features and other teams struggled to integrate its releases) and leaking abstractions (database entities permeate the codebase).
- Definitions: the hexagon = domain logic in domain language (build domain models, agree a ubiquitous language, make concepts explicit → an "executable model" to discuss with stakeholders); port = a set of interactions with the outside world sharing one intent; primary ports drive the system (web UI, API), secondary ports are driven by it (database, messaging); adapter = maps the outside world to the inside and back. Guiding principle: dependencies point outside-in — the domain never depends on adapters or technicalities (dependency inversion at architecture level); at run time everything is assembled.
- Heuristics and rules:
  - For primary ports, put an interface/facade between adapter and domain so each adapter sees only what it needs (interface segregation).
  - For secondary ports, the domain defines the abstraction (e.g. an `OrderRepository` with store / get all / get by id); the adapter is a single class holding the SQL and schema (and can own schema migration); the domain knows nothing of tables or queries.
  - A port may have multiple implementations as long as they honour its contract; adapters range from one class to a subsystem.
  - ORM entities (JPA) belong inside the database adapter: a model good for business rules is not necessarily good for relational storage — keep multiple models optimised for different purposes.
  - Frameworks "want to be in control": isolate them in adapters and keep the domain free of them; libraries that do not seize control may be tolerated in the centre.
  - Wrap low-level library concepts — logging, date/time, UUIDs — because they hinder unit testing (timestamps, randomness) and because teams otherwise expose a whole library while using a sliver of it.
  - Use dependency injection but avoid DI frameworks: wire all adapters explicitly in one `main` unit (explicit, clear, "a bit boring").
  - Use the structure as a "what to put where" guide; finding the right place for code is half the effort of keeping it habitable.
- Benefits: focus on domain logic (good DDD fit); placement guidance; fast focused domain tests plus separate integration tests for databases/external services; clutter-free domain model; independent incremental evolution of API, domain and persistence (adapter mappings decouple them).
- Trade-offs and pitfalls: you must write adapter mappings even though domain, storage and API objects look almost identical — do it from the start anyway, because the models turn out similar but not the same; a new feature (e.g. discounts on an order) touches UI, API, domain and database — controlled but spread out; adapter properties can leak into the domain (database transactions forcing a transaction notion into the repository port); the pattern leaves many decisions open (how to implement an adapter, data classes vs mapping functions); testing secondary-port interactions may need mock objects.
- Further reading it lists: Freeman & Pryce *Growing Object-Oriented Software, Guided by Tests* (uses ports & adapters); Cockburn's 2017 three-part talk; OCTO's "three principles and an implementation example"; Pierrain's "don't get lost on your right side"; Goeschel's "Hexagon, Schmexagon?"; Garlan & Shaw's architecture intro.

## Clean architecture for the rest of us — Suragch (Pusher tutorials) — https://pusher.com/tutorials/clean-architecture-introduction
- Cited by README at line 1269 in section "Articles" to support: an accessible summary of Martin's *Clean Architecture*.
- Fetch status: fetched (8 Jan 2019, updated Apr 2021; a summary with commentary by a self-described non-expert, to be read critically).
- Thesis: organise code so it stays understandable and changeable as it grows by separating it into components that change independently — a plugin architecture where the stable domain is the core and volatile infrastructure plugs in.
- Layers and dependency rule: concentric circles — domain (business rules, changes rarely) inside, infrastructure (UI, DB, web APIs, frameworks, devices; changes often) outside; UI and DB depend on business rules, never the reverse; the domain knows nothing of infrastructure, so UI may be web/desktop/mobile and storage SQL/NoSQL/cloud.
- Four parts: Entities (business rules that exist independently of software, e.g. a bank's loan-interest rule; depend on nothing); Use cases (application-specific rules that automate the system — e.g. "Gather info for new loan": validate name/address, get credit score, deny below 500 else create customer and start estimation; depend on entities only; define interfaces that outer layers implement); Adapters (translate GUI input into forms convenient for use cases and translate output for display or storage); Infrastructure (all I/O; most volatile; swappable).
- SOLID as applied (with reasons): SRP (one reason to change — split a class serving finance and HR); OCP (extend without modifying via single-responsibility components behind interfaces); LSP (swap lower-level implementations, e.g. MySQL→MongoDB, without affecting higher-level behaviour); ISP (depend on interfaces exposing only needed methods); DIP (stable components must not depend on volatile ones — Java example where `StableClass` declares an interface that `VolatileClass` implements; abstract factories).
- Component principles: REP (release cohesive, versioned units); CCP (group classes that change together, split those that change for different reasons — SRP for components); CRP (do not force dependence on unused classes — ISP for components); REP/CCP/CRP are in tension, balance per situation; ADP (no dependency cycles — break them with an interface/DIP or separate team-owned releases); SDP (depend in the direction of stability); SAP (stable components should be abstract so they do not become rigid).
- Recommendations and rules:
  - Testing: the plugin structure lets you mock the database; UI tests break on every UI change, so put formatting into a Presenter in the adapter layer and test it without the view; expose a dedicated testing API for business rules so tests survive structural changes.
  - Divide components by use case (vertical slices across the horizontal layers — viewer/publisher/admin slices each with use case, presenter, view) and group them for deployment however makes sense.
  - Enforce layer boundaries with the compiler (Java package-private) or with third-party dependency checkers, because one boundary-crossing dependency defeats the architecture.
  - Add complexity only as needed: keep boundaries that allow later extraction, progressing monolith-with-boundaries → modules → separately deployed services.
  - Database, UI, OS, web and frameworks are details: start with business rules, defer those decisions as long as possible, then write adapters.
  - Do not pass entity objects to outer layers as data structures; create separate data-model objects.
  - Top-level project organisation should say what the system is about (screaming architecture).
  - Exercise: draw a dependency graph of components; ask where the business rules are, whether they depend on anything, how many components a DB/UI/framework change touches, whether cycles exist, and what refactoring yields a plugin architecture.
- Further study it recommends in order: *Clean Code*, *Agile Software Development*, *Clean Architecture*.

## An illustrated guide to 12 Factor Apps — Bob Reselman (Red Hat) — https://www.redhat.com/architect/12-factor-app
- Cited by README at line 1270 in section "Articles" to support: operational best practices for deployable services.
- Fetch status: fetched (18 Feb 2021).
- Framing: the 12 factors (published 2011 by Adam Wiggins) let companies release reliably, scale quickly and maintain software predictably under web-scale pressure; adoption can be incremental — start with the first factor and keep going.
- Factor-by-factor (rule + this guide's reasoning/illustration):
  - I Codebase — one codebase in revision control, many deploys; all assets (source, provisioning scripts, config) live in one repo accessible to dev, test, ops and CI/CD.
  - II Dependencies — declare and isolate explicitly; only code unique to the app belongs in source control, external artifacts (npm packages, jars, DLLs) are declared in a manifest and loaded at dev/test/prod; anti-pattern: committing third-party artifacts.
  - III Config — store config in the environment; inject ports, dependency URLs, flags like DEBUG at run time via env vars or external files (Java properties, Kubernetes manifests, docker-compose) so each target gets its own settings; code may hold defaults but not environment-specific values.
  - IV Backing services — treat databases, mail servers, brokers and other team-managed services as swappable attached resources for flexibility across the SDLC.
  - V Build, release, run — build artifacts into a repository (Docker Hub, Maven); release = build + config; run = provision the runtime (e.g. Ansible) and deploy; the pipeline is ephemeral and fully reproducible from source control.
  - VI Processes — stateless processes that track no other process's state and store no session/workflow state, so instances can be added/removed under load without side effects.
  - VII Port binding — export services via ports because hostnames/IPs change (manual edits, discovery) while port numbers are stable; use port forwarding to avoid collisions; conventional ports 80/443/22/3306/27017.
  - VIII Concurrency — scale out via the process model: group processes by purpose (web tier behind a load balancer calling a business-service tier behind its own) and scale each group independently; otherwise you can only scale the whole app.
  - IX Disposability — fast startup (finish housekeeping, verify DB/network connections before accepting traffic) and graceful shutdown (close DB/broker connections, log everything); Node.js example handler disconnects the broker and database, builds a SHUTDOWN status with signal and PID, closes the server and exits 0.
  - X Dev/prod parity — every release goes through the same build/release/run path to each target; never "leapfrog" by copying artifacts from one environment into production; the difference from factor V is that parity guarantees prod uses the same process as dev.
  - XI Logs — treat logs as an event stream separate from its consumers (one wants errors, one request/response data, one archives everything); the stream survives an app crash.
  - XII Admin processes — one-off tasks are first-class SDLC citizens: a `dataSeeder` for an `Orders` container gets the same build/release/run, codebase and parity treatment.

## The Twelve-Factor App — Adam Wiggins (Heroku) — https://12factor.net/
- Cited by README at line 1274 in section "Websites" to support: the canonical methodology for SaaS/cloud-deployable apps.
- Fetch status: fetched — the index page and all twelve factor pages (last updated 2017; source on GitHub; available in 19 languages).
- Purpose: a methodology for software-as-a-service apps that use declarative setup to onboard developers quickly, keep a clean contract with the OS for portability, deploy on modern cloud platforms without sysadmin work, minimise dev/prod divergence for continuous deployment, and scale without changes to tooling or architecture; language- and backing-service-agnostic; distilled from Heroku's experience with hundreds of thousands of apps; format inspired by Fowler's PoEAA and *Refactoring*; aimed at developers of service-style apps and the ops engineers who run them.
- I. Codebase — one codebase tracked in revision control, many deploys. Codebase = one repo (centralised) or set of repos sharing a root commit (decentralised); app ↔ codebase is one-to-one; a deploy = a running instance (production, staging, each developer's machine), all on the same codebase at possibly different commits. Multiple codebases = a distributed system whose components are each an app; multiple apps sharing code violates the factor → extract libraries and pull them in through the dependency manager.
- II. Dependencies — explicitly declare and isolate. Never rely on implicit system-wide packages; declare everything exactly in a manifest (Gemfile, pip requirements) and isolate at execution (bundle exec, virtualenv, static linking in C) — both halves are required; one deterministic build command (`bundle install`, `lein deps`) lets a new developer start with just runtime + dependency manager; never shell out to system tools (curl, ImageMagick) assumed present — vendor them if needed.
- III. Config — store config in the environment. Config = everything that varies between deploys: backing-service handles, credentials (S3, Twitter), per-deploy values (canonical hostname); not internal wiring like Rails routes or Spring module config. Litmus test: could the codebase be open-sourced right now without leaking credentials? Anti-patterns: constants in code; config files outside version control (easy to commit by mistake, scattered formats); grouped named environments (`development/test/production`) that do not scale and explode combinatorially. Env vars are per-deploy, language/OS-agnostic, hard to commit accidentally, and managed as independent granular controls.
- IV. Backing services — treat them as attached resources. Any network-consumed service (MySQL, CouchDB, RabbitMQ, Beanstalkd, Memcached, SMTP, S3, New Relic, Loggly, Twitter, Google Maps, Amazon RDS) is a resource addressed by a URL/credentials in config; the code makes no distinction between local and third-party; swapping a local MySQL for RDS or local Postfix for Postmark changes only the handle; resources can be attached/detached at will (e.g. replacing a failed database from a backup with no code change); two sharded databases are two resources.
- V. Build, release, run — strictly separate the stages. Build turns a commit into an executable bundle (fetch dependencies, compile assets); release = build + config, ready to run; run launches processes against a release. Releases are append-only and immutable with unique IDs (timestamp or incrementing version) so rollback is possible (Capistrano `releases/` + `current` symlink); runtime code changes are impossible by design; keep the run stage minimal because it may be triggered unattended (reboots, process-manager restarts), while the build stage can be complex since a developer is watching.
- VI. Processes — execute the app as one or more stateless, share-nothing processes. Persistent data belongs in a stateful backing service (database); memory/filesystem may serve only as a single-transaction cache (download file → process → store result); assume nothing cached survives to the next request (many processes, restarts on deploy/config change/relocation). Sticky sessions violate the factor; keep session state in Memcached/Redis with expiry; compile assets at build time (Rails asset pipeline, Jammit), not at run time (django-assetpackager anti-pattern).
- VII. Port binding — export services via port binding. The app is self-contained: it does not rely on a web server injected at run time (PHP-in-Apache, Java-in-Tomcat) but bundles a web-server library (Tornado, Thin, Jetty) as a dependency, binds a port and serves HTTP; locally that is `localhost:5000`, in deployment a routing layer forwards from the public hostname to the port; any protocol works (ejabberd/XMPP, Redis); port binding lets one app be a backing service of another through a URL in config.
- VIII. Concurrency — scale out via the process model. Processes are first-class, after the Unix daemon model (contrast: PHP child processes under Apache, the JVM "uberprocess" with threads); assign work types to process types (web for HTTP, worker for background jobs); scale = number of processes, workload diversity = process types, the process formation = types × counts; in-process threads/async (EventMachine, Twisted, Node.js) are fine, but a VM only grows so far, so the app must span machines; share-nothing processes partition horizontally. Processes never daemonise or write PID files; rely on the OS process manager (systemd), a platform's distributed manager, or Foreman in development to manage output streams, crashes and restarts.
- IX. Disposability — maximise robustness with fast startup and graceful shutdown. Processes can start or stop at any moment (elastic scaling, fast deploys, resilience); aim for readiness within seconds; on SIGTERM a web process stops listening, finishes in-flight requests (assumes short requests; long-polling clients reconnect) and exits; a worker returns its job to the queue (RabbitMQ NACK, Beanstalkd auto-requeue on disconnect, Delayed Job lock release) so all jobs must be reentrant — wrap in transactions or make idempotent; also tolerate sudden death (hardware failure) via a robust queue that requeues on timeout; crash-only design (CouchDB) is the logical extreme.
- X. Dev/prod parity — keep development, staging and production as similar as possible. Three gaps: time (weeks between deploys → hours), personnel (devs write, ops deploy → the same people deploy and watch), tools (Nginx/SQLite/macOS vs Apache/MySQL/Linux → the same stack). Adapters (ActiveRecord, Celery, ActiveSupport::Cache) ease porting but do not justify different backing services between dev and prod — SQLite-vs-PostgreSQL or memory-vs-Memcached mismatches cause failures that passed tests, discourage continuous deployment and cost a lot over the app's lifetime; modern packaging (Homebrew, apt), provisioning (Chef, Puppet) and lightweight virtualisation (Docker, Vagrant) make real services cheap to run locally; use the same type and version of each backing service everywhere.
- XI. Logs — treat logs as event streams. Logs are a time-ordered stream of events from all processes and backing services with no beginning or end; the app never routes or stores them and never writes log files — each process writes unbuffered to stdout; in development the developer watches the terminal, in staging/production the execution environment captures, collates and routes the streams (Logplex, Fluentd) to files, live tail, indexing systems (Splunk) or warehouses (Hadoop/Hive) for search, trend graphs (requests/minute) and alerting (errors/minute thresholds), none of which the app configures.
- XII. Admin processes — run admin/management tasks as one-off processes. Migrations (`manage.py migrate`, `rake db:migrate`), a console/REPL against the live database (`rails console`, `irb`, `python`), one-time scripts committed to the repo; run them against a release in the identical environment with the same codebase, config and dependency isolation (`bundle exec rake db:migrate`, the virtualenv's `bin/python manage.py`); ship admin code with app code to avoid synchronisation issues; locally run via a shell in the checkout, in production via SSH or the platform's remote-execution facility; prefer languages with a built-in REPL.
