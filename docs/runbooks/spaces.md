# Runbook: Spaces (DO Object Storage)

Serves: владелец-оператор и агент, действующий за него. Что и как настроено в хранилище, как выпускаются и меняются ключи,
что владелец сверяет с консолью DO (ADR-017, ADR-042, backlog RUNBOOK-1, RUNBOOK-2).

Состояние записи на 2026-11-12: Spaces создан руками вместе с кластером, и ни одного факта о нём в репозитории нет (ADR-042,
контекст). `doctl` бакеты и ключи Spaces не показывает, агент к хранилищу не ходит. Поэтому ниже два рода текста:
**целевое состояние** (решение владельца 2026-11-12, ADR-042) и **проверки владельца** с точными командами. Пока проверка не
выполнена, факт считается неизвестным, а не принятым. Команды ниже не выполнялись.

## Ключи: создание, хранение, ротация

Ключи создаются, меняются и удаляются **только в панели DO** (раздел Spaces Object Storage, вкладка Access Keys); по документации DO
через API и CLI это невозможно, `doctl` ключей Spaces не видит. Секрет показывается один раз при создании. Перегенерация секрета
необратима и сразу отключает всё, что использует старое значение. У аккаунта по умолчанию до 200 ключей. Источник:
https://docs.digitalocean.com/products/spaces/how-to/manage-access/ (читалась 2026-11-12; перед шагами перечитать).

Тип ключа - в самой панели: Limited (права на выбранные бакеты: Read или Read/Write/Delete) и Full access (все бакеты, создание и
настройка бакетов). Limited-ключи несовместимы с политиками бакета (`PutBucketPolicy`), поэтому политики не используются (ADR-042).

### Создать ключ приложения

1. Панель DO -> Spaces Object Storage -> Access Keys -> Create Access Key -> Limited access.
2. Имя - по смыслу: потребитель и бакет (например `backend-media`, `loki-chunks`; имена не рассчитаны на разбор скриптом).
3. Права: **один** бакет; для медиа - Read/Write/Delete (загрузка по presigned PUT, показ, удаление), для Loki - Read/Write/Delete
   (компактор удаляет чанки по ретеншну, ADR-043). Меньшие права для Loki ломают ретеншн.
4. Секрет скопировать сразу и положить в менеджер паролей одной записью с идентификатором ключа; на диск и в чат он не попадает.
5. Запечатать: значение идёт в Sealed Secret потребителя (`pnpm secrets:seal` после SECRETS-1; до этого `kubeseal --raw`, см.
   [malinina-kubernetes.md](malinina-kubernetes.md), «Sealed Secrets»). Имена секретов и ключей внутри них задают строки DEPLOY-1
   и OBS-2; здесь они не фиксируются. Открытое значение в репозиторий не попадает (ADR-020).
6. Очистить буфер обмена, если секрет копировался через него.

### Ключ владельца (Full access)

Создаётся тем же путём (Full access), живёт только в менеджере паролей. Нужен для: проверки 2-5 ниже, настройки CORS, правила
multipart. Работа с ним руками, через `s3cmd`, который ставит владелец на своей машине (не зависимость репозитория, ADR-005 не
затрагивается):

1. `s3cmd --configure -c ~/.s3cfg-bf-spaces`: ключ и секрет вводятся в диалоге из менеджера паролей, адрес сервиса
   `<регион>.digitaloceanspaces.com`, шаблон адреса бакета `%(bucket)s.<регион>.digitaloceanspaces.com`. Файл лежит вне репозитория,
   `chmod 600`.
2. Все команды ниже идут с `-c ~/.s3cfg-bf-spaces`.
3. После работы файл удаляется (`rm ~/.s3cfg-bf-spaces`): Full-access ключ постоянно на диске не хранится.

### Ротация и утечка

- Плановой ротации нет: ADR-042 её не требует. Менять ключ - при утечке и при подозрении на утечку (ADR-042 п. 3.4).
- Утечка Limited-ключа: в панели создать новый ключ с теми же правами, запечатать его, применить, убедиться, что потребитель работает
  (backend: загрузка; Loki: запись и чтение чанков), затем удалить старый ключ (DO советует сначала добавить новый, потом убрать
  старый). Перегенерация секрета проще, но между ней и выкатом нового значения потребитель без доступа.
- Утечка Full-access ключа: удалить его в панели, создать новый в менеджере паролей; Limited-ключи не затрагиваются.
- Утечка приватного ключа Sealed Secrets - отдельный порядок: сначала новые значения (в том числе ключи Spaces), затем новый ключ
  контроллера ([malinina-kubernetes.md](malinina-kubernetes.md), «Ротация»).

## Настройка бакетов (целевая)

Выполняет владелец Full-access ключом. Порядок: проверки 1-3, затем настройка, затем проверка 6.

### CORS на бакете медиа

Панель DO не умеет `ExposeHeader`, поэтому CORS задаётся файлом (`cors.xml` лежит вне репозитория):

```xml
<CORSConfiguration xmlns="http://s3.amazonaws.com/doc/2006-03-01/">
  <CORSRule>
    <AllowedOrigin>https://malinina.ca</AllowedOrigin>
    <AllowedMethod>PUT</AllowedMethod>
    <AllowedMethod>GET</AllowedMethod>
    <AllowedMethod>HEAD</AllowedMethod>
    <AllowedHeader>Content-Type</AllowedHeader>
    <ExposeHeader>ETag</ExposeHeader>
    <MaxAgeSeconds>3600</MaxAgeSeconds>
  </CORSRule>
</CORSConfiguration>
```

Применить: `s3cmd -c ~/.s3cfg-bf-spaces setcors cors.xml s3://<бакет медиа>`. Источник формата и команды:
https://docs.digitalocean.com/products/spaces/how-to/configure-cors/ (2026-11-12).

`AllowedHeader` `Content-Type` нужен presigned PUT с типом файла, `MaxAgeSeconds` 3600 кеширует предзапрос на час (агент по поручению владельца, 2026-11-12). Если проверка 6 покажет, что предзапрос отвергается из-за другого заголовка, его добавляют сюда и в таблицу выше.
Если CDN Spaces включён, после смены CORS очистить его кэш (по документации DO ответы из кэша остаются без заголовков CORS);
presigned-ссылки через CDN-адрес не работают (ADR-042), CDN для медиа не включается.

Если CORS у Spaces не заработает, загрузка идёт через backend, и это условие пересмотра ADR-042, а не отказ.

### Отмена незавершённых multipart-загрузок, оба бакета

`s3cmd -c ~/.s3cfg-bf-spaces expire --expiry-mpu-days=7 s3://<бакет>` - для каждого из двух бакетов. Источник:
https://docs.digitalocean.com/products/spaces/how-to/configure-lifecycle-rules/ (там в примере 1 сутки; 7 выбрано решением владельца,
чтобы не оборвать медленную загрузку большого видео). Неполные части стоят места до отмены.

Не выяснено: заменяет ли эта команда весь lifecycle бакета или добавляет правило. Поэтому до неё - `s3cmd getlifecycle s3://<бакет>`
(правил быть не должно, проверка 4), после неё - снова, и в выводе должно остаться только это правило. Правило не является сроком
хранения: объекты она не удаляет (ADR-043 п. 3.3).

## Не заявлено и не проверено

- Шифрование бакета, версионирование, Object Lock: по документации DO шифрования уровня бакета нет (только SSE-C), версионирование
  включается через API, Object Lock не заявлен. Runbook ничего из этого не утверждает; проверка и решение - BACKUP-1 (ADR-042, ось
  Data at rest).
- Сроки хранения медиа курсов: решает спека курсов.
- `media-src` в CSP для показа медиа: правка `apps/frontend/next.config.ts` вместе с функцией (ADR-055 п. 2, ADR-042 п. 2.2).
- Цена и потолок расхода: BUDGET-1, ADR-043 п. 2.

## Diagnose

- Бакеты и их содержимое: `s3cmd -c ~/.s3cfg-bf-spaces ls`, `s3cmd -c ~/.s3cfg-bf-spaces du s3://<бакет>`.
- Загрузка из браузера не идёт: сначала проверка 6 (CORS), затем срок presigned-ссылки и права Limited-ключа на бакет (Read/Write/Delete), затем
  часы на стороне, выдавшей ссылку.
- Loki не пишет чанки: ключ Loki (права, не перегенерирован ли секрет), имя и регион бакета в значениях Loki, логи пода Loki.
- Три вероятные причины, по убыванию: перегенерированный или удалённый ключ; CORS не сходится с origin; неверный регион или имя бакета.

## Rollback

- Настройки бакета: CORS снимается `s3cmd delcors s3://<бакет>`, правило жизненного цикла - `s3cmd dellifecycle s3://<бакет>`; до этого сохранить вывод
  `info` и `getlifecycle` в запись владельца.
- Ключ: старый секрет после перегенерации не вернуть (необратимо), поэтому сначала новый ключ, потом удаление старого.
- Потеря бакета или аккаунта DO - вне этого runbook (границы: [recovery.md](recovery.md)); сохранность данных Spaces - BACKUP-1.
