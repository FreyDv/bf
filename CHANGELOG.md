### Filter toolkit, second half: drizzle entry and Postgres tests (2026-11-13)

For the owner: QUERY-1 closes, with ADR-051 for what ADR-050 did not hold (decided by the agent on your delegation of 2026-11-12; overrule it by a new record). `@bf/query-filter` gets its third entry, `drizzle`: `defineBinding(spec, columns)` binds every field of a filter spec to a column (a field without a column, or a column without a field, does not compile), `related(table, on, binding)` binds a relation, and `compile(binding, filter)` returns a SQL fragment built with the `sql` template, `exists()` and `notExists()`: values are always parameters, no `sql.raw`, relations are EXISTS and NOT EXISTS for both cardinalities so the root row is never multiplied, `every` is `NOT EXISTS (... IS NOT TRUE)` (true on an empty relation, a NULL counts as a violation), NOT over a relation is NOT EXISTS, NULL follows plain SQL. The QRY-16 limits are checked again in `compile`; scope stays outside (`and(scope, compile(...))`). The package has its own `test:e2e` on `bf_test` behind the TST-3 guard (the database name must contain the word `test`, checked on the URL and on `current_database()`), with tables created and dropped by the test in a schema of its own; the CI e2e step, which had nothing to run, now runs it. New boundary rules with fixtures: the drizzle entry only from `infrastructure/` (a compiler in a module's `public/` is left to QUERY-4), another module's filter compiler only imported by infrastructure, the drizzle entry imports only `drizzle-orm`. Defaults you may want to overrule, in ADR-051: an empty `in` matches nothing and an empty `nin` matches every row where the field is not NULL (both keep NULL rows out, so `NOT in []` equals `nin []`); `compile` throws on a hand-built filter that does not fit its spec; a relation to the same table, or to one table on two levels of a path, is not supported yet (new row QUERY-6). QUERY-2 and TEST-2 are no longer blocked. Not verified: CI on GitHub, an image of the backend with `drizzle-orm`.

### Filter toolkit, first half: core and zod (2026-11-13)

For the owner: QUERY-1 lands its first half, recorded as ADR-050 (decided by the agent on your delegation of 2026-11-12; overrule it by a new record). New package `@bf/query-filter` in `packages/query-filter`, ESM built to `dist/`, with two entries: `core` (the operator table `Op.*`, the value builders `str`, `int`, `decimal`, `bool`, `date`, `datetime`, `uuid`, `oneOf`, `relation.one` and `relation.many`, `defineFilter`, the type `FilterOf<S>` and the QRY-16 limits) and `zod` (`toZod(S)`: a strict schema, conditions as a sum type on `operator`, QRY-5 violations as Zod issues, all together). The drizzle entry, the Postgres tests and the QRY-12 rules are the second half; the QUERY-1 row stays live, marked doing. The ADR-024 gate was run on the real `toZod(S)` with a temporary router that was not committed: `pnpm contracts:generate` exposes the schema, the type reaches `RouterInputs` in the frontend (a bad operator and an unknown field fail to compile), the built ESM validates over HTTP as the type promises, a backend image with the toolkit starts and answers. No superseding of ADR-012 or ADR-035 is needed. Two findings from the spike, both recorded in ADR-050: a procedure without `output` makes the generated file import the router class, which breaks the frontend type check (new row QUERY-5); and the frontend image fails with `TS2307` until the Turborepo graph has an edge from the frontend to the toolkit, which `@bf/query-filter` in the dependencies of `@bf/contracts` provides, so CONTRACT-3 is answered for the zod entry and the edge arrives with the first module. New boundary rules: the zod entry only in adapters, `core` without libraries, entries independent of each other, the domain imports nothing from the toolkit, by package name as well as by path; `pnpm deps:test` proves them on fixtures. Defaults you may want to overrule, all in ADR-050 item 4: `int` is a safe JavaScript integer, `decimal` a string compared as a number, `datetime` needs a zone and ranges compare as instants, `in` with an empty list is accepted. Not verified: CI on GitHub, the frontend image was built but not started. New rows: QUERY-3 (client enum layout), QUERY-4 (suffixes in the boundary regexes), QUERY-5 (`output` in the slice skills).

### Domain may import only the kernel from packages (2026-11-13)

For the owner: BOUND-2 closes the three gaps ADR-048 item 6 left in the boundary check, recorded as ADR-049 (decided by the agent on your delegation of 2026-11-12; overrule it by a new record). `dep-3-domain-no-libraries` only sees npm imports, so a `domain/` file could import any workspace package, `@bf/contracts` included (forbidden by QRY-20). The new rule `domain-packages-only-kernel` allows `domain/` of any app, test files too, to import nothing from `packages/` except `packages/kernel/`. The kernel may import from npm only `neverthrow`, plus `vitest` in its test files, and no workspace package at all. Packages that export from `dist/` now stay in the graph as leaves: `dist/` left `options.exclude`, and `packages/*/dist/` went into `doNotFollow`, so the import is judged and the build output is not read. A side finding: the old `exclude` also hid every npm library whose entry lives in `dist/`, `neverthrow` among them, so `dep-3` never saw it; the real graph grew from 28 to 35 modules and `pnpm deps` stays green. `pnpm deps:test` proves it on fixtures, including a tree where the kernel and the contracts both export from `dist/`, and fails if `dist/` returns to `exclude`. The `contracts`-from-`domain/` ban of QRY-19 is no longer part of QUERY-1. No package was created: the real `@bf/kernel` still arrives with LOG-2, and its first day runs `pnpm deps` and `pnpm deps:test`. Not covered: Node built-in modules in the kernel (no decision yet, listed in ADR-049 Revisit when).

### Frontend image survives the first router (2026-11-13)

For the owner: CONTRACT-2 fixes a failure that was hidden. The generated `packages/contracts/src/generated/server.ts` imports backend `*.request.dto.ts`, `*.response.dto.ts` and `*.enum.ts` by relative path (ADR-035), and `turbo prune @bf/frontend` does not take `apps/backend`, because `package.json` declares no such dependency (the risk ADR-027 Consequences already names). CI stayed green only because the file is empty today. Reproduced on a throwaway copy outside the tree with a temporary router, a DTO importing a schema from a second file, and a frontend page using `RouterInputs`: `docker build` failed at `next build` with `TS2307: Cannot find module '../../../../apps/backend/src/demo/demo.request.dto.js'`. The fix is one line in `apps/frontend/Dockerfile`: `turbo prune @bf/frontend @bf/backend --docker`. On the same copy the image then built, served `200` on `/`, and the runtime stage held only the Next standalone output (`/app/apps/frontend`, no backend files, no Nest). The cost is a longer `build` stage, which now installs the backend dependencies too. `scripts/image-check.ts affected` now also selects the frontend image when a pull request changes `apps/backend/src/**/*.request.dto.ts`, `*.response.dto.ts` or `*.enum.ts`, because backend is not a frontend dependency in the Turborepo graph. No new ADR and ADR-027 is not edited: this refines it by pointing from the Dockerfile comment at ADR-027 Consequences and ADR-035. Not covered, filed as CONTRACT-3: the types and builds of the packages a backend DTO imports (the filter toolkit of QUERY-1) and the frontend `typecheck` on a DTO-only change.

### NetworkPolicy in the app chart (2026-11-12)

For the owner: CHART-3 gives the shared chart `deploy/charts/app` the ingress policy that ADR-037 item 4 accepted. Every application now renders a standard `networking.k8s.io/v1` NetworkPolicy by default (`networkPolicy.enabled: true`): it selects the pods of the release, restricts ingress only, and opens the application port to the namespace `traefik` (`networkPolicy.ingressControllerNamespace`, only when `ingress.enabled`) and to the peers listed in `networkPolicy.allowFrom` (standard NetworkPolicyPeer items; the chart refuses a non-list and an empty peer, which would admit every pod). With no ingress and no neighbours the pods accept no incoming connection. It carries no sync wave, so it lands in wave 0 before the workloads of wave 1 (ADR-047); egress is not restricted (new row CHART-4). The migration and cron pods carry the same labels as the Deployment pods, so the policy selects them too, which is harmless for ingress only. `pnpm charts:test` gained a section on what renders and what is refused. No ADR: ADR-037 already decided the policy. Nothing was applied: whether Cilium enforces it on the cluster is your check at the first rollout, step 5 of `docs/runbooks/argocd.md` (DEPLOY-1 now carries it). NATS-4 stays its own row, because NATS comes from a third-party chart.

### Write durability on bfdb decided (2026-11-12)

For the owner and every future spec author: ADR-044 closes DBSEC-2. DigitalOcean runs `bfdb` with `synchronous_commit=off`, so after a node crash the last few hundred milliseconds of confirmed commands can vanish together with their outbox rows (the data stays consistent). The cluster stays as it is; a command that meets the criterion (losing its confirmed result brings back revoked access or cannot be undone outside the system) turns `synchronous_commit=on` on for its own transaction with `SET LOCAL`, inside the infrastructure `TransactionManager`, invisible to the domain and the handler. The initial list is the auth commands of ADR-040: session revocation, operator password reset, permission grants and revocations; the failed-attempt counter is on it with a caveat, because ADR-025 rolls a transaction back on a business error (DBSEC-6). Money and order commands fall under the criterion when they appear. Worth knowing: every command outside the list can still answer "success" and lose its outbox row after a crash, and none of this is verified on DO under `doadmin` yet (DBSEC-5); on one node without a replica `on` protects only against losing the last WAL, not the disk. The agent decided this on the owner's blanket delegation of 2026-11-12, not item by item. Implementation row: DBSEC-4.

### Logging gaps closed (2026-11-12)

For the owner and every future spec author: ADR-043 fills what ADR-032 left open for logs, without editing it. Loki keeps logs for 30 days through its compactor, with no Spaces lifecycle rule on the Loki bucket; the technical ceiling is $10 a month on top of what is already paid, with no new nodes, load balancer or subscription, subordinate to BUDGET-1, and the first lever when it is exceeded is a shorter retention. Grafana Alloy collects the logs (Promtail is end-of-life) from the `bf`, Traefik and ArgoCD namespaces, not `kube-system`; Traefik access logs stay off until client IP and query string are redacted. Grafana is reachable only by `kubectl port-forward`, with no Ingress. Loki labels must be low-cardinality; correlation id, `MODULE.REASON` code and actor id go in the JSON body, and the field list lives in the logger port and the pino adapter, not in the record. The agent decided this on the owner's blanket delegation of 2026-11-12. Worth knowing: the $10 figure has no measured baseline (Spaces state and log volume are unknown), one Loki replica loses unflushed data with its node, and certificate expiry and retained WAL cannot be alerted from logs. New rows: MON-1, LOG-2. Open in OBS-2: how Alloy reads logs (Kubernetes API token versus node files), ingestion limits, production log level, PVC size.

### Object storage recorded (2026-11-12)

For the owner and every future spec author: ADR-042 records DigitalOcean Spaces (S3 API) as the object store for course media and Loki chunks. Buckets are private, one per purpose, with a Limited key per bucket and consumer held per ADR-020; the Full-access key that sets CORS, lifecycle and multipart abort stays in the owner's password manager and never enters the cluster or the repo. Uploads go straight from the browser with a presigned PUT; playback, link TTLs, size limits and multipart order are left to the courses spec, and if CORS on Spaces does not work, upload goes through the backend without a new record. The app reaches storage through an intent-shaped port in the courses module with an in-memory double; no S3 client or emulator is chosen and no dependency is added. Presigned URLs are secrets and stay out of logs. The agent decided this on the owner's blanket delegation of 2026-11-12. Worth knowing: the actual bucket (name, region, ACL, CORS) was not verified and is an owner check in RUNBOOK-1, and Spaces declares no bucket-level encryption (BACKUP-1). New rows: SPEC-2, STORAGE-1, LOG-1.

### AI provider recorded (2026-11-12)

For the owner and every future spec author: ADR-041 records OpenAI as the AI provider (the owner's choice of 2026-11-11) and the rules around it. Any call to the provider goes through a port in `application/ports/` with its adapter in `infrastructure/` and an in-memory double; the first spec that calls it names the port, the module and the process. The key is `OPENAI_API_KEY`, held per ADR-020, and only the process that calls the provider receives it (a separate secret if that is a worker apart from the public API). The official `openai` package is pre-approved for the adapter only and is not added yet. The cost ceiling belongs to BUDGET-1 and personal data sent to the provider to PRIVACY-1; the record carries no numbers or models. No separate BDR was written for the vendor; switching provider is a revisit signal. The agent decided the rules on the owner's blanket delegation of 2026-11-12. Worth knowing: until BUDGET-1 exists the key has no spending ceiling, and nothing but review stops an `openai` import outside the adapter (OPENAI-1). Content rights for uploaded courses are COURSES-1.

### Authentication and authorization recorded (2026-11-12)

For the owner and every future spec author: ADR-040 decides how Danya and Valeria sign in and what they may do. Passwords are hashed with argon2id from `node:crypto` (no new dependency), sessions live in Postgres behind a `__Host-` cookie (7 days idle, 30 absolute), accounts are created and reset by an operator command that the owner runs, and permissions are data: Danya's account holds all of them, Valeria starts with none until Danya grants them. The check runs in the handler through a port, with the scope in `WHERE` outside the caller's filter (QRY-17). The buyer stays account-less and tracks an order by phone; how the phone proves ownership goes to the orders spec. ChatGPT through MCP gets a revocable token bound to a person's account, with the protocol left to the first MCP spec. It closes the AUTH-1 deferrals of ADR-037. The agent decided this on the owner's blanket delegation of 2026-11-12, not item by item. Worth knowing: without a second factor the admin rests on a password, limits and a failed-attempt counter (AUTH-2), and `synchronous_commit=off` (DBSEC-2) can bring back a just-deleted session after a node crash. Implementation rows: AUTH-3, AUTH-4.

### Testing strategy recorded (2026-11-12)

For every future spec author and agent: ADR-039 names the test levels and where each runs. `test` holds domain unit, use-case (in-memory port doubles) and type-level tests and needs no Docker; `test:e2e` holds behavioural tests through the driving adapter against `bf_test` and NATS. Test files sit next to the slice (`*.test.ts`, `*.e2e.test.ts`), port doubles are `*.in-memory.ts`. Money, access, personal data, external contracts, query filters and the outbox transaction need a behavioural test; there is no numeric coverage threshold. Nothing is wired yet: the Vitest preset, the `test:e2e` script, the database-name guard and the boundary-check exemption for test files are backlog rows TEST-2 and TEST-3.

### Security baseline recorded (2026-11-12)

For the owner and every future spec author: ADR-037 answers all 16 axes of the standard's security baseline in one table (secrets, input validation, CI permissions, dependencies, data at rest, threat model and the rest), linking decisions already taken and naming the row that owns each deferral (authentication and authorization - AUTH-1). ### CI builds, checks and publishes images; migrations and e2e are wired (2026-11-12)
