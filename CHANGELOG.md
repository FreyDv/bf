### Turborepo inputs for backend contract files instead of --force (2026-11-13)

For the owner: CONTRACT-5 closes with ADR-058 (decided by the agent on your delegation of 2026-11-12 and 2026-11-13; overrule it by a new record). It replaces item 2 of ADR-057 in the part about the cache; the rest of ADR-057 stands. The Turborepo cache was blind to backend DTO files: after a DTO-only edit `typecheck` and `lint` of `@bf/contracts` and `@bf/frontend` kept the same hash and replayed a cached green result, which `pnpm typecheck` locally and a run on `main` with a restored cache would have hit too (CI worked around it with `--force`). Now `packages/contracts/turbo.json` and `apps/frontend/turbo.json` (`extends` the root file, which keeps the task graph) give those two tasks `inputs`: `$TURBO_DEFAULT$` plus `$TURBO_ROOT$/apps/backend/src/**/*.{request.dto,response.dto,enum,filter-spec}.ts`. `--force` is gone from `scripts/contracts-typecheck.ts`; the CI step `Contracts of a DTO-only change` stays as the selector, because `turbo --affected` still selects only `@bf/backend` on such an edit (`affectedUsingTaskInputs` is not enabled). ### Content-Security-Policy in the frontend (2026-11-13)

For the owner: CSP-1 closes with ADR-055 (decided by the agent on your delegation of 2026-11-12; overrule it by a new record). `apps/frontend/next.config.ts` now sends `Content-Security-Policy` (enforce, no report-only, no report endpoint) on every route: `default-src 'self'`, `script-src` and `style-src` with `'unsafe-inline'`, `img-src`, `font-src` and `connect-src` on `'self'`, `object-src 'none'`, `base-uri` and `form-action` on `'self'`, `frame-ancestors 'none'`; production adds `upgrade-insecure-requests`, development adds `'unsafe-eval'` to `script-src` (React refresh). ADR-038 is not edited. ### Failed-login counter against rollback (2026-11-13)

For the owner: DBSEC-6 closes with ADR-054 (decided by the agent on your delegation of 2026-11-12 and 2026-11-13; overrule it by a new record). The problem: a failed login is a business outcome, ADR-025 item 3 rolls the transaction back on `Result.err`, so the failed-attempt counter write would be rolled back with it. The answer: the login command returns `ok` with an outcome `accepted` or `rejected`, so the counter write commits in the same transaction; `TransactionManager` and ADR-025 are unchanged, and ERR-2 is narrowed in the record by name (`err` for refusals that must leave no trace, `ok` with an outcome for refusals that must leave one). The counter is a separate persistence record behind its own port, not a field of the Account aggregate, and raises no domain event, so brute force writes no outbox row and no NATS message per attempt. The driving adapter generates the session token (`node:crypto`) and passes it in the command, the handler stores only its hash, the command returns only the outcome (APP-7); this refines the "token issue" part of ADR-040 item 1, hash and comparison stay in infrastructure. The record complements ADR-025 and ADR-044 and edits neither. One call you may want to overrule: the counter write stays in the ADR-044 item 4 list of critical commands (the whole login commits with `synchronous_commit` on). Excluding it would weaken an authentication control, and the agent does not make that call for you; ADR-040 and PRODUCT.md keep security with a human. Left to AUTH-3: nonexistent accounts, the delay curve and where it applies, increment and reset of the counter. Not verified: there is no code, the record is review only; `SET LOCAL` on DO is still DBSEC-5. The alignment scope count goes from 5 to 4. No new rows.

### Filter toolkit, second half: drizzle entry and Postgres tests (2026-11-13)

For the owner: QUERY-1 closes, with ADR-051 for what ADR-050 did not hold (decided by the agent on your delegation of 2026-11-12; overrule it by a new record). `@bf/query-filter` gets its third entry, `drizzle`: `defineBinding(spec, columns)` binds every field of a filter spec to a column (a field without a column, or a column without a field, does not compile), `related(table, on, binding)` binds a relation, and `compile(binding, filter)` returns a SQL fragment built with the `sql` template, `exists()` and `notExists()`: values are always parameters, no `sql.raw`, relations are EXISTS and NOT EXISTS for both cardinalities so the root row is never multiplied, `every` is `NOT EXISTS (... IS NOT TRUE)` (true on an empty relation, a NULL counts as a violation), NOT over a relation is NOT EXISTS, NULL follows plain SQL. The QRY-16 limits are checked again in `compile`; scope stays outside (`and(scope, compile(...))`). The package has its own `test:e2e` on `bf_test` behind the TST-3 guard (the database name must contain the word `test`, checked on the URL and on `current_database()`), with tables created and dropped by the test in a schema of its own; the CI e2e step, which had nothing to run, now runs it. New boundary rules with fixtures: the drizzle entry only from `infrastructure/` (a compiler in a module's `public/` is left to QUERY-4), another module's filter compiler only imported by infrastructure, the drizzle entry imports only `drizzle-orm`. Defaults you may want to overrule, in ADR-051: an empty `in` matches nothing and an empty `nin` matches every row where the field is not NULL (both keep NULL rows out, so `NOT in []` equals `nin []`); `compile` throws on a hand-built filter that does not fit its spec; a relation to the same table, or to one table on two levels of a path, is not supported yet (new row QUERY-6). QUERY-2 and TEST-2 are no longer blocked. Not verified: CI on GitHub, an image of the backend with `drizzle-orm`.

For the owner: SEALED-1 delivers everything for the Sealed Secrets controller that can be done without touching the cluster. `deploy/argocd/sealed-secrets.yaml` is an ArgoCD Application for chart `sealed-secrets` 2.22.0 (appVersion 0.41.2, published 2026-10-26, past the ADR-005 window), installed in `kube-system` as `sealed-secrets-controller` so `kubeseal` needs no flags, with `ServerSideApply` and automated sync without prune. ADR-045 records the departure from the upstream default: automatic key renewal is off (`keyrenewperiod: "0"`), because a 30-day renewal would silently stale the one-copy private-key backup of ADR-020 in a two-person team; the key is rotated by hand yearly and on any suspected leak. The Application, the commands and the key-count behaviour after a controller restart were not run on the cluster: SEALED-2 (apply, `pub-cert.pem`, key copy in the password manager) is the owner's, SEALED-3 is the first yearly rotation, and SECRETS-1 waits on SEALED-2.

### Write durability on bfdb decided (2026-11-12)

For the owner and every future spec author: ADR-044 closes DBSEC-2. DigitalOcean runs `bfdb` with `synchronous_commit=off`, so after a node crash the last few hundred milliseconds of confirmed commands can vanish together with their outbox rows (the data stays consistent). The cluster stays as it is; a command that meets the criterion (losing its confirmed result brings back revoked access or cannot be undone outside the system) turns `synchronous_commit=on` on for its own transaction with `SET LOCAL`, inside the infrastructure `TransactionManager`, invisible to the domain and the handler. The initial list is the auth commands of ADR-040: session revocation, operator password reset, permission grants and revocations; the failed-attempt counter is on it with a caveat, because ADR-025 rolls a transaction back on a business error (DBSEC-6). Money and order commands fall under the criterion when they appear. Worth knowing: every command outside the list can still answer "success" and lose its outbox row after a crash, and none of this is verified on DO under `doadmin` yet (DBSEC-5); on one node without a replica `on` protects only against losing the last WAL, not the disk. The agent decided this on the owner's blanket delegation of 2026-11-12, not item by item. Implementation row: DBSEC-4.

### Logging gaps closed (2026-11-12)

For the owner and every future spec author: ADR-043 fills what ADR-032 left open for logs, without editing it. Loki keeps logs for 30 days through its compactor, with no Spaces lifecycle rule on the Loki bucket; the technical ceiling is $10 a month on top of what is already paid, with no new nodes, load balancer or subscription, and the first lever when it is exceeded is a shorter retention. Grafana Alloy collects the logs (Promtail is end-of-life) from the `bf`, Traefik and ArgoCD namespaces, not `kube-system`; Traefik access logs stay off until client IP and query string are redacted. Grafana is reachable only by `kubectl port-forward`, with no Ingress. Loki labels must be low-cardinality; correlation id, `MODULE.REASON` code and actor id go in the JSON body, and the field list lives in the logger port and the pino adapter, not in the record. The agent decided this on the owner's blanket delegation of 2026-11-12. Worth knowing: the $10 figure has no measured baseline (Spaces state and log volume are unknown), one Loki replica loses unflushed data with its node, and certificate expiry and retained WAL cannot be alerted from logs. New rows: MON-1, LOG-2. Open in OBS-2: how Alloy reads logs (Kubernetes API token versus node files), ingestion limits, production log level, PVC size.

### Object storage recorded (2026-11-12)

For the owner and every future spec author: ADR-042 records DigitalOcean Spaces (S3 API) as the object store for course media and Loki chunks. Buckets are private, one per purpose, with a Limited key per bucket and consumer held per ADR-020; the Full-access key that sets CORS, lifecycle and multipart abort stays in the owner's password manager and never enters the cluster or the repo. Uploads go straight from the browser with a presigned PUT; playback, link TTLs, size limits and multipart order are left to the courses spec, and if CORS on Spaces does not work, upload goes through the backend without a new record. The app reaches storage through an intent-shaped port in the courses module with an in-memory double; no S3 client or emulator is chosen and no dependency is added. Presigned URLs are secrets and stay out of logs. The agent decided this on the owner's blanket delegation of 2026-11-12. Worth knowing: the actual bucket (name, region, ACL, CORS) was not verified and is an owner check in RUNBOOK-1, and Spaces declares no bucket-level encryption (BACKUP-1). New rows: SPEC-2, STORAGE-1, LOG-1.

### AI provider recorded (2026-11-12)

For the owner and every future spec author: ADR-041 records OpenAI as the AI provider (the owner's choice of 2026-11-11) and the rules around it. Any call to the provider goes through a port in `application/ports/` with its adapter in `infrastructure/` and an in-memory double; the first spec that calls it names the port, the module and the process. The key is `OPENAI_API_KEY`, held per ADR-020, and only the process that calls the provider receives it (a separate secret if that is a worker apart from the public API). ### Authentication and authorization recorded (2026-11-12)

For the owner and every future spec author: ADR-040 decides how Danya and Valeria sign in and what they may do. Passwords are hashed with argon2id from `node:crypto` (no new dependency), sessions live in Postgres behind a `__Host-` cookie (7 days idle, 30 absolute), accounts are created and reset by an operator command that the owner runs, and permissions are data: Danya's account holds all of them, Valeria starts with none until Danya grants them. The check runs in the handler through a port, with the scope in `WHERE` outside the caller's filter (QRY-17). The buyer stays account-less and tracks an order by phone; how the phone proves ownership goes to the orders spec. ChatGPT through MCP gets a revocable token bound to a person's account, with the protocol left to the first MCP spec. It closes the AUTH-1 deferrals of ADR-037. The agent decided this on the owner's blanket delegation of 2026-11-12, not item by item. Worth knowing: without a second factor the admin rests on a password, limits and a failed-attempt counter (AUTH-2), and `synchronous_commit=off` (DBSEC-2) can bring back a just-deleted session after a node crash. Implementation rows: AUTH-3, AUTH-4.
